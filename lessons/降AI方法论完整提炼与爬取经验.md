## 二、方法论核心提炼（逐条对应博客）

### 核心认知（贯穿5篇博客的元原则）
**同义词替换无效。** 真正影响AI特征的不是几个词，而是整篇文章的表达规律——句子排列、段落组织、信息顺序、完整度分布。只换词不改结构，检测结果不会变化。
- 来源: 博客4"为什么换词、删句、调整语序，朱雀AI率还是降不下来？"
- 博客2: 简单"去除AI味"指令只换词不改变结构 = 无效

### 10条核心规则

**规则1: 直接进入主题，不要空泛开头**
- 博客1方法一: 删除没有必要的背景铺垫
- 博客3: 开头是不是太像行业报告？
- 博客5: 先删除明显套话
- 典型AI开头: "随着...不断发展""在当今...的时代""近年来...不断进步"

**规则2: 句长要有快有慢**
- 博客1方法二: 不要让所有句子保持同一种长度
- 博客4: 把长句拆短不等于自然，机械拆分会变生硬
- 重点: 连续三句差异<30% = 趋同，需要插入短句(5字以下)或长句(30字以上)

**规则3: 用具体替代抽象**
- 博客1方法三: 加入具体经历，不要只讲抽象观点
- 博客3: 想让文章更自然，可以先增加"具体"
- 博客4: 把抽象观点换成具体过程
- 博客5: 加入具体经历是核心修改之一
- 错误: "AI能够有效提高内容创作效率。"
- 正确: 用具体工作、具体时间、具体动作替代

**规则4: 允许段落没有结论**
- 博客1方法四: 允许文章保留一点"不规则"
- 博客3: 不要让每一段都必须有结论
- 博客4: 减少没有信息的总结
- 典型总结句: "总的来说""由此可以看出""因此我们需要"

**规则5: 打破信息均匀**
- 博客1: 每个问题都解释得太完整 = AI特征
- 博客4: 很多文章真正的问题是"太平均"
- 博客3: 知识总结写得太完整也不像个人表达
- 核心: 熟悉的一笔带过，有经验的多讲，没测过的可以不提

**规则6: 连接词不要按固定顺序**
- 博客1: 连接词使用过于规律
- 博客4关键洞察: 删掉"首先其次"但信息顺序不变 = 无效
- 核心: 信息顺序比连接词更重要

**规则7: 观点要有个人判断**
- 博客1: 观点太正确，但没有个人判断
- 博客3: 文章太"正确"有时也是一种问题
- 博客4: 加入个人判断和取舍
- 不要: "我们应该合理使用""只有不断学习才能适应时代"

**规则8: 段落结构不要统一**
- 博客1: 段落结构过于统一 (总分总模式)
- 博客4: 不要让每一段都采用同一种结构
- 变化: 有些段直接进案例，有些段先讲问题，有些段说完就停

**规则9: 不要制造错误**
- 博客1: AI率降到0不等于文章没问题
- 博客3: 保留个人表达不等于故意写错
- 博客4: 减少AI感不是故意制造错误
- 核心: 自然 = 加入真实经历和轻重变化，不是加语病和错别字

**规则10: 小说正文特殊保护**
- 博客1,3,4,5反复强调: 小说需要保护人物、剧情、设定
- 不能改变: 人物名字、地点、时间、等级体系、金手指设定、关键剧情、伏笔
- 对白要符合人物性格，动作和场景不能随意打乱
- 这是本应用(小说工坊)最需要关注的一条

## 三、双层架构实现

### 第一层: 硬规则层 (js/de-ai.js - process函数)
纯字符级强制修正，100%执行，不依赖模型理解

**自动执行层(4条):**
1. AI套话删除 - 86个正则模式(原66+新增20)
   - 套话: "值得注意的是""综上所述""总的来说"等
   - 偏好词: "进行了""做出了""存在着"等
   - 空泛修饰: "极大的""显著的""深刻的"等
   - 新增: "由此可以""换句话说""也就是说"等
2. 段首句号修正 - 段落开头15字以内句号改逗号
3. 连续短句合并 - 50字窗口内3+个句号合并
4. 段落总结句删除 - 19个总结句模式(原11+新增8)

**检测建议层(9条):**
5. 空泛开头检测 - 17个模式(原10+新增7)
6. 句长趋同检测 - 连续3句差异<30%
7. 连接词序列检测 - 9组序列
8. 信息均匀度检测 - 连续5段字数相近(需段落>20字)
9. 总分总结构检测 - >50%段有总结句
10. 通用正确观点检测 - 10个模式
11. 连接词密度检测 - 每千字>8个
12. 过度正式表达检测 - 10个模式
13. 列举过完整检测 - >40%段在列举

### 第二层: 方法论注入层 (DEAI_METHODOLOGY_PROMPT)
完整方法论作为创作约束，注入到正文生成的system prompt中
- 字符数: 989字符(原676)
- 规则数: 10条带案例(原9条无案例)
- 新增核心认知: "同义词替换无效"元原则
- 新增规则10: 小说正文特殊保护
- 新增案例: 每条规则配具体对错示例
- 注入点: renderer_v2.js line 1063-1064, type==="body"时注入

### 两层配合
- 注入层: 模型生成时尽量遵守方法论(治本但有遗漏)
- 硬规则层: 生成后强制清除残留惯性(治标但100%执行)
- 双管齐下: 生成阶段+后处理阶段

## 六、爬取经验总结

### 网站分析方法
1. 先下载全部JS文件(10个), 搜索关键词如"humanize""prompt""api"
2. 判断降AI逻辑在客户端还是服务端
3. 如果在服务端, 转向提取公开的方法论内容(博客/帮助文档)
4. 博客内容用Get-Content逐段读取, 保存为纯文本

### 关键发现
- 降得快的降AI逻辑100%在服务端 /api/humanize
- 客户端JS不含任何prompt或降AI规则
- 但5篇博客完整公开了方法论原理
- 方法论中的机械规则(删套话、改句号)可以用脚本100%执行
- 方法论中的语义规则(具体化、个人判断)只能靠prompt引导模型

### 限制
1. 服务端prompt无法获取(需要登录+付费)
2. 方法论只覆盖了公众号/自媒体文章, 小说/剧本的降AI方法只在博客中提及"需要不同处理"但没有给出具体规则
3. 硬规则层是通用规则, 不区分内容类型(公众号vs小说)
4. 方法论注入层的prompt长度有限, 不能把68066字符全文注入
5. 无法验证降AI效果(没有朱雀检测接口)

### 后续建议
1. 考虑按内容类型(小说/公众号/剧本)分别加载不同的方法论prompt
2. 硬规则层可以增加小说专用模式: 对白中的套话不删除, 叙述中的套话删除
3. 可以增加"降AI强度"选项: 低强度只删套话, 中强度+改句号, 高强度+全检测
4. 长期目标: 如果能获取服务端prompt, 可以更精准地复制降得快的处理逻辑
