# 第一章: 什么有效

## 1.1 Node.js fs.writeFileSync 写中文文件 -- 100%可靠

这是整个项目中唯一从未失败过的写文件方法。

适用场景: 写含中文的源代码、经验文件、配置文件。

示例:
```javascript
const fs = require("fs");
fs.writeFileSync("target.md", content, "utf8");
```

为什么有效: Node.js的fs模块直接操作Buffer，不经过PowerShell的编码层，UTF-8无BOM写入。

## 1.2 apply_patch Add File 模式 -- 创建新文件可靠

适用场景: 一次性写入长文本文件（经验文件、新源文件）。

注意事项:
- Add File模式可靠，Update File模式对含Unicode转义的上下文匹配不可靠
- 失败时改用Node.js fs脚本
- 对Vue SFC文件的空格敏感，失败率较高

## 1.3 PowerShell here-string + node stdin -- ASCII脚本可靠

适用场景: 执行不含中文的Node.js脚本。

示例:
```powershell
@"
const fs = require("fs");
console.log(fs.readdirSync(".").length);
"@ | node -
```

限制: 脚本内不能含中文字符串，否则编码崩溃。

## 1.4 CDP行为验证 (Input.dispatchMouseEvent) -- 真实验证

适用场景: 验证按钮点击、面板切换、功能链路。

正确实现: 用Node.js 20内置WebSocket连接CDP端口，通过Input.dispatchMouseEvent模拟真实鼠标点击（mouseMoved -> mousePressed -> mouseReleased三步）。

为什么有效: 走完整DOM事件链路，和用户真实操作一致。

## 1.5 Node.js脚本做字符串查找替换 -- apply_patch失败时的备选

适用场景: apply_patch Update File匹配失败时的fallback。

模式: 读取文件 -> 字符串split/join替换 -> 写回。

## 1.6 增量续生成+防断网 -- 章节生成核心机制

每生成一章就保存到磁盘，断网后从断点续跑，不从头重来。这个机制在章节层和正文层都有效。

## 1.7 check_css.js 花括号平衡检查 -- 简单有效

33行脚本，检查style.css的花括号深度是否为0。每次改CSS后必用，规则19要求。应该集成到封装前检查流程。

## 1.8 .NET UTF8Encoding(false) 写中文 -- PowerShell环境可靠

适用场景: 在PowerShell中写含中文的文件。

示例:
```powershell
$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText("path.md", $content, $utf8NoBom)
```

为什么有效: 直接调用.NET API，绕过PowerShell的编码层，UTF-8无BOM写入。

# 第二章: 什么无效

## 2.1 node -e 内联含多行代码 -- 转义地狱

失败原因: PowerShell的引号转义和Node.js的字符串转义规则冲突，含双引号/反斜杠/中文必然失败。

正确做法: 写独立.js文件再node执行。

## 2.2 PowerShell Set-Content / Out-File 写中文 -- 双重编码

失败原因: PowerShell的-Encoding UTF8参数实际写入BOM，且经过PowerShell编码层导致双重编码。

规则13/22明确禁止。但开发过程中违反了4次以上。

## 2.3 Runtime.evaluate 替代真实点击 -- 假阳性最大来源

失败原因: Runtime.evaluate直接调用JS函数（如app._toggleScBind），绕过DOM事件链路。验证永远"通过"，但用户真实点击会失败。

教训#22和#56记录了这个问题，但全程都在使用。

正确做法: 用Input.dispatchMouseEvent模拟真实点击。

## 2.4 只做 node --check 就声称完成 -- 写完代码不等于功能完成

失败原因: node --check只验证语法，不验证功能。代码语法正确不代表功能正常。

正确做法: 语法检查 -> CDP行为验证 -> 截图存证 -> 才能声称完成。

## 2.5 CSS自动批量去重 -- 误删有效规则

失败原因: "保留最后定义，删除前面重复"策略无法区分"冗余重复"和"有意为之的层叠覆盖"（如响应式断点、主题变体）。

教训#95: v2.7.49的CSS去重删了282块，导致UI全面错乱，不得不从备份恢复。

正确做法: 逐个选择器人工审查，不做自动批量去重。

## 2.6 apply_patch Update File 对含分号/Unicode转义的上下文 -- 匹配失败

失败原因: apply_patch的@@上下文匹配对分号和Unicode转义字符敏感，容易匹配失败。

正确做法: 失败时改用Node.js fs脚本做字符串替换。

## 2.7 假设UI状态写测试脚本 -- 找不到元素

失败原因: 测试脚本假设应用处于某个UI状态（如流水线在卷纲步骤），但实际可能在其他步骤。

正确做法: 测试脚本开头先检测当前状态，导航到目标状态，再测试。

## 2.8 测试脚本选择器凭猜测 -- 不匹配HTML

失败原因: 写测试脚本前不读renderer.html确认实际DOM结构，凭记忆写选择器。ERROR_LOG记录了6次。

正确做法: 写测试脚本前先用CDP Runtime.evaluate扫描实际DOM结构，确认ID/class存在。

# 第三章: 反复踩坑清单

## 3.1 同一功能写多个版本不删旧版 -- 违反7次以上

典型案例:
- verify_ui系列: v2 -> v3 -> all -> all4 -> fix5，5个版本全堆积在根目录
- CDP截图脚本: cdp_screenshot -> cdp_shot -> test_shot -> test_shot2 -> cdp_interact，4个版本
- lockOutline修复: 8次Git提交，每次声称修复
- API下拉菜单: 5次声称修复，每次只修一个环节

根因: 每次写新版本时复制旧脚本改个名字，旧的忘了删。

铁律: 新版本必须直接覆盖旧文件名，不创建新文件名。

## 3.2 CSS只加不删 -- 规则19违反3次

时间线:
- 教训#2 (v2.0.0): CSS重复选择器堆积
- 教训#76 (v2.7.36): 128个重复选择器
- 教训#93 (v2.7.49): 282个重复CSS块
- 教训#95 (v2.7.51): 自动去重误删有效规则，UI全面错乱

根因: 每次修改CSS都是新增规则而非修改已有规则。规则19"先搜后改"写了但不执行。

铁律: CSS修改三步法 -- (1)全文搜索选择器 (2)找到所有定义 (3)合并到最后一处、删除前面的。禁止自动批量去重。

## 3.3 PowerShell写中文文件 -- 规则13/22违反4次以上

时间线:
- 教训#38: PowerShell here-string嵌套双引号导致SyntaxError
- 教训中多次记录: Set-Content -Encoding UTF8写中文导致双重编码/BOM
- v2.7.0后又重新违反一次
- COMMERCIAL_PACKAGING_PLAN.md整个文件是GBK双重编码乱码

根因: PowerShell的编码层和Node.js/Vue文件的UTF-8无BOM要求冲突。

铁律: 修改含中文的源文件时，必须使用Node.js fs或apply_patch。禁止PowerShell Set-Content/Out-File/Add-Content。

## 3.4 "写完代码"跳过验证就声称完成 -- 系统性缺陷，20次以上

表现:
- 代码写完 -> node --check通过 -> 声称完成
- 跳过了CDP行为验证、截图存证、功能链路测试
- 用户打开后发现大量BUG

典型案例:
- 流水线7-Phase重构: 声称24/24 PASS，实际7个都有BUG
- 商业封装: 声称21/21 PASS，用户发现无限转圈圈、API乱码、API Key硬编码

根因: 把"代码存在"等同于"功能完成"，把"测试通过"等同于"功能正常"。

铁律: 代码写完 -> 语法检查 -> CDP行为验证 -> 截图存证 -> 四步全过才能声称完成。

## 3.5 临时脚本堆积不清理 -- 全程存在

数据: 24天内写了50+个临时脚本，80%已删除，20%堆积在根目录。高峰期根目录有15个临时脚本共1688行90KB。

根因: 一次性脚本（探针、调试）用完不删。

铁律: 一次性脚本用完当天删除。有用脚本放到scripts/目录，不放根目录。

## 3.6 测试只检查元素存在不验证功能 -- 全程存在

表现: 测试脚本检测getElementById返回非null就标记PASS，不验证点击后面板是否弹出、数据是否写入、状态是否变化。

后果: 132个按钮中120个只检查"存在"，deepVerify只覆盖12个。所有"100%通过"的测试报告都是假的。

铁律: 不验证"元素存在"，验证"操作 -> 预期行为 -> 实际结果"三元组。

## 3.7 不调用Agent协作 -- 规则17多次违反

用户多次要求调用Agent，以"线程限制"为由拒绝。真相: Agent工具是延迟加载的，需要先用tool_search搜索加载。429失败后没有重试。

铁律: 遇到429按30s->60s->90s->120s->150s->180s->210s->240s递增重试，共8次。重试期间做不依赖API的本地工作。

## 3.8 每次遇错加规则但不执行 -- 规则从1条增长到23条

模式: 遇到错误 -> 加一条铁律 -> 下次不执行 -> 再加一条 -> 还是不执行。

根因: 规则没有检查点，变成了"写给自己看的安慰剂"。

铁律: 规则必须有强制执行机制。封装前检查清单必须逐项执行，任何一项FAIL禁止封装。

# 第六章: 验证方法论

## 6.1 验证三铁律 (规则14)

1. 外部裁判: 改动完成后不能靠读代码判断通过。必须用CDP实际操作应用，截图+JSON日志+时间戳三者缺一视为未验证。
2. 行为验证: 不验证"元素存在"，验证"功能能用"。必须验证"操作->预期行为->实际结果"三元组。
3. 强制执行: 每个阶段有验证清单，任何一项FAIL禁止进入下一阶段。

## 6.2 CDP验证正确实现

连接方式: Node.js 20内置WebSocket连接CDP端口（如9223）。

点击模拟 (正确):
```javascript
await cdp.send("Input.dispatchMouseEvent", {
  type: "mouseMoved", x: rect.x+5, y: rect.y+5
});
await cdp.send("Input.dispatchMouseEvent", {
  type: "mousePressed", x: rect.x+5, y: rect.y+5,
  button: "left", clickCount: 1
});
await cdp.send("Input.dispatchMouseEvent", {
  type: "mouseReleased", x: rect.x+5, y: rect.y+5,
  button: "left", clickCount: 1
});
```

点击模拟 (错误 -- 假阳性):
```javascript
await cdp.send("Runtime.evaluate", {
  expression: "app._toggleScBind()"
});
```

## 6.3 验证覆盖范围

- 3个去AI味模式都要验证 (chain/split-merge/multi-step)
- 全部132个按钮都要有handler (不只是deepVerify的12个)
- 端到端数据流: 创建项目 -> 导入大纲 -> 锁定 -> 生成卷章 -> 写作

## 6.4 验证中的常见误判

1. 自动化脚本模式匹配过严: 按钮ID命名不统一（btn-get-models vs btn-fetch-models），需要扩展正则模式做二次验证
2. global:to是@keyframes关键字的误报，检测脚本需排除动画关键帧
3. CDP验证中复杂引号转义会导致返回undefined，用String()包装或JSON.stringify传参
4. window._app是全局对象名，不是App

# 第七章: 编码安全经验

## 7.1 编码规则总结

| 操作 | 允许 | 禁止 |
|------|------|------|
| 写含中文的源文件 | Node.js fs / apply_patch / .NET UTF8Encoding(false) | PowerShell Set-Content/Out-File |
| 写纯ASCII脚本 | PowerShell here-string + node | node -e含多行代码 |
| 修改含中文的源文件 | Node.js fs字符串替换 / apply_patch | PowerShell -replace |
| 检查文件编码 | Node.js fs读取首字节 | PowerShell Get-Content -Encoding |

## 7.2 BOM头问题

UTF-8 BOM (EF BB BF)会导致Electron主进程语法错误，exit code 1。

检查方法: Node.js读取文件前3个字节，如果是0xEF 0xBB 0xBF则有BOM。

## 7.3 TextDecoder流式解码

API回复乱码根因: TextDecoder.decode()用了{stream:false}，多字节UTF-8字符在chunk边界被截断。

正确做法: 用{stream:true}，每次decode传入剩余bytes。

# 第十章: 核心教训

## 教训1: 凭印象工作，不凭证据

所有脚本错误的根本原因: 写脚本前不读DOM结构、不删旧脚本、不用正确的验证方法。和经验总结的教训一样: 凭印象工作，不凭证据。

## 教训2: 规则没有执行机制等于没有规则

23条规则，核心问题从未解决。根因: 规则没有检查点，变成了"写给自己看的安慰剂"。

## 教训3: "写完代码"不等于"功能完成"

代码语法正确不代表功能正常。必须经过行为验证才能声称完成。

## 教训4: 同一个错误反复犯是因为没有真正的代价

每次犯错后加一条规则，但没有强制执行机制。下次还会犯。

## 教训5: 测试框架本身可能是错的

如果测试只检查"元素存在"而不验证"功能能用"，100%通过率是假的。

## 教训6: 外部视角有价值

第三方审计能发现开发者自己看不到的架构问题。教训#96的5项修复都是第三方发现的。

## 教训7: 自动化不等于正确

CSS自动去重误删有效规则。自动化脚本只能辅助，不能替代人工判断。

## 教训8: 编码问题不是偶发的，是系统性的

PowerShell和UTF-8无BOM的冲突贯穿整个项目。唯一可靠的方案: Node.js fs或.NET UTF8Encoding(false)。
