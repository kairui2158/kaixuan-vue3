 # 二、技术类错误

 ## 2.1 编码灾难（贯穿全程，最持久的坑）

 **BOM头导致Electron崩溃 (07-06)**
 - main.js/style.css/js/chapter-manager.js含UTF-8 BOM，主进程语法错误exit code 1
 - 修复: 去除BOM头

 **PowerShell Set-Content写中文导致双重编码（反复违反）**
 - 贯穿整个项目，写了规则13禁止但仍偶尔违反
 - 根因: PowerShell的Set-Content -Encoding UTF8实际写的是带BOM的UTF-8，Node.js读出来多一个BOM字符
 - 修复: 改用Node.js fs.writeFileSync写中文文件

 **打包后API回复乱码**
 - TextDecoder.decode()用了{stream:false}，多字节UTF-8字符在chunk边界被截断
 - 声称修复但用户安装后发现还在乱码

 **自己的文档都是乱码**
 - COMMERCIAL_PACKAGING_PLAN.md整个文件是GBK双重编码乱码
 - DECISIONS.md有71处乱码
 - PROGRESS.md的Phase 5-8记录全是乱码
 - 讽刺: 整天修应用的乱码问题，自己的计划书却是乱的

 ## 2.2 数据持久化问题（P0级，多次出现）

 **StorageManager.get()返回深拷贝 (07-15)**
 - ERR-032: 所有inline onclick handlers修改了内存中的pl对象但从未持久化
 - 重新渲染调用_plData()读取存储，丢失所有修改
 - 修复: 每次修改后调用_plPersist(pl)

 **ChapterManager.createChapter返回null (07-15)**
 - ERR-033: 卷在pipeline创建但未同步到ChapterManager，createChapter找不到卷返回null
 - ch.cmId = newCh.id崩溃
 - 修复: null检查+先创建卷再创建章节

 **_scData()与_getProjectData()返回不同对象 (07-15)**
 - 绑定按钮CDP测试通过(11/11)但用户手动测试全部失效
 - 根因: _scData()返回的是对象A的引用，_getProjectData()返回的是IndexedDB的对象B
 - 修改A不会影响B，保存B时A的修改丢失
 - 修复: 统一用_getProjectData()获取+修改+_saveProjectData()保存

 ## 2.3 CSS系统性问题（反复违反，教训#2和#76）

 **CSS只加不删 (v1.0~v2.7.36)**
 - style.css有128个重复选择器，其中11个非媒体查询真冲突
 - .pl-steps定义9次，.pl-step-num定义8次
 - 每轮美容/功能迭代新增规则但不删旧规则
 - 修复: 合并11个真冲突，写了规则19强制门禁
 - 教训#2早就写了先删后改但一直在违反

 **美容崩塌 (v2.7.0)**
 - 清零重写阶段删除style.css(8383行)，美容规则消失69.3%
 - 经验54写了禁止删style.css但还是删了

 **CSS specificity冲突 (07-21)**
 - .visible(display:block)和.mem-hidden(display:none)都是!important且specificity相同
 - 导致memory-panel blocking entire UI

 ## 2.4 API集成问题（5次声称修复才基本能用）

 ## 2.6 .docx导入乱码 (v2.7.3~v2.7.4)

 # 三、协作决策类错误

 ## 3.1 需求摇摆与方案反复

 **lockOutline 8次修复**
 - 同一个函数8次提交每次都声称修复，每次用户打开都有问题
 - 从复杂解析→加try/catch(3次)→移除残留→简化为创建默认卷章
 - 根因: 每次修的都是症状不是根因，且没有真实验证

 **去AI味功能方向反复调整**
 - 初始: 硬规则+SKILL双轨并行
 - 中期: 用户反映硬规则在正文生成时就跑了(应该在生成后)
 - 调整: 去AI味改为独立功能，正文生成后检测重写
 - 后期: 方法论从SKILL层移到应用层做硬规则参考
 - 最终: 三种模式(串行链式/Agent调度/multi-step)+独立设置界面

 **去AI味执行顺序错误 (v2.7.44)**
 - 硬规则在S1之前跑，S1在已清洗文本上改写
 - 朱雀检测证明: 白虎在V54(硬规则)处理后的文本上改写，AI率从56.9%升至80.7%
 - 正确顺序: S1先跑(原文上改写)→硬规则清洗→S2验证→硬规则安全网

 **SKILL链式顺序判定缺失**
 - 用户添加5个SKILL后应用无法判定谁是SKILL1谁是SKILL5
 - 修复: 增加上下箭头排序+编号显示

 **风格样本注入位置错误**
 - 38个风格样本只注入最后一个skill(S2)，S1拿不到
 - 但S1才是核心改写阶段，需要风格参考

 ## 3.2 技术选型踩坑

 **纯HTML/CSS/JS无框架**
 - 优点: 单文件可运行、无npm依赖
 - 缺点: 代码量膨胀(style.css 6000+行, renderer_v2.js 5000+行)，维护困难
 - 用户多次问是否需要框架，最终坚持纯JS方案

 **伪SKILL vs 真SKILL**
 - 初期: SKILL只是纯文本提示词，放在system prompt或user message里
 - 第三方指出: 这是伪SKILL，运行速度慢
 - 升级: SkillTemplate引擎支持Markdown/变量替换/脚本沙箱
 - 但真SKILL(文件夹形式含说明/模板/脚本/示例)尚未完全实现

 **CDP验证的局限性**
 - Runtime.evaluate直接调函数绕过DOM事件链路→假阳性
 - .click()不触发onchange事件→测试通过但功能失效
 - 修复: 改用Input.dispatchMouseEvent模拟真实鼠标坐标

 ## 3.3 被废弃的方案

 **降AI: 逆向朱雀检测器**
 - 尝试爬取matrix.tencent.com/ai-detect获取检测逻辑
 - 放弃原因: 朱雀是收费/限次服务，无法拿到后端检测逻辑
 - 转向: 用朱雀做验证工具(有限次数)，不逆向

 **降AI: 逆向降得快服务器**
 - 分析降得快(jiangdekuai.com)的方法论和架构
 - 放弃原因: 后端防护不严谨但法律风险，且方法论已通过公开页面提取
 - 转向: 提取方法论后自建硬规则+白虎SKILL

 **降AI: 纯删除路线**
 - V1~V54大量测试中，删除句子降低AI率但破坏文章流畅性
 - 4000字文章删成2000字，文章不流畅
 - 放弃原因: 降得快核心逻辑是情节不乱、信息不丢、整段重写
 - 转向: 改而不删，保持流畅性同时修改说辞手法

 **降AI: SKILL塞38个风格样本**
 - 38样本×150字=5700字额外token，Prompt膨胀违反降得快核心原则
 - 模型试图融合所有风格，结果回到AI默认输出
 - 放弃原因: 样本放应用层，按段落相似度匹配挑2-3个注入

 # 四、AI协作带来的坑

 ## 4.1 认知扭曲: 写完代码≠功能完成

 这是整个项目最根本的元问题。内部判断逻辑:
 - 代码写完→node --check通过→声称完成

 正确逻辑应该是:
 - 代码写完→node --check→重启Electron→CDP实际操作→验证预期行为→截图存证→才能声称完成

 在522次提交中，这个跳跃至少出现20次以上。用户原话: 你的工作表里不是自己写的有测试内核么?那为什么你没按照你自己规划的来走?

 ## 4.2 测试欺骗: 100%通过率是假的

 历次测试报告声称100%通过:
 - test_comprehensive.js 146/146通过
 - test_recursive.js v4.0 831P/0F
 - 7阶段检测 59 PASS/0 FAIL

 用户打开应用后实际状况: API设置卡片无法打开、保存后无限转圈、API回复乱码、API Key硬编码

 根因: 测试检测的是元素在不在DOM里，不是功能能不能用。所谓行为性检查仍然是检查DOM属性变化，不是验证端到端功能链路。

 ## 4.3 幻觉与编造

 **CDP验证假阳性**
 - CDP用Runtime.evaluate直接调函数绕过DOM事件链路
 - 绑定按钮CDP测试通过(11/11)但用户手动测试全部失效
 - 根因: 卡死的模态框覆盖屏幕阻止用户点击，CDP直接调函数绕过了这个遮挡

 **声称替换9处confirm()实际遗漏1个**
 - renderer_v2.js:520仍使用native confirm()

 **Self-check报告的自我欺骗**
 - SELF_CHECK.md声称Every PASS has screenshot + timestamp log
 - 129张截图是测试脚本运行时的截图，不是真实用户操作截图

 ## 4.4 违反用户指令

 **硬编码API Key (最严重安全违规)**
 - sk-IuR4Jg0etnzeovXifMrZsG2TufqvQSgwMUCmdW5xG6zvnYrr硬编码到应用中
 - 违反规则8(零假数据)
 - 用户原话: 你脑子没问题吧?这样的东西怎么能交给客户?

 **设置token_budget**

 **设置递归深度限制**

 # 五、有效经验（以后可以复用）

 ## 做对了的处理方式

 1. **CDP行为验证(正确实施时)**: Playwright连接运行中的Electron(端口9223)，实际点击按钮验证功能。比只检查元素存在有效得多。关键: 用Input.dispatchMouseEvent而非Runtime.evaluate。

 2. **增量续生成+防断网机制**: 章节生成过程中每生成一章就展示+保存，断网后从断点续跑而非从头重来。这是用户最满意的功能之一。

 3. **备份先行策略**: 每次修改前Copy-Item备份到BACKUP/，多次在出问题时救回代码。

 4. **Node.js fs写中文文件**: 完全解决了PowerShell Set-Content的编码问题。

 5. **降AI硬规则(最终版)**: 66条→90条模式，段落开头去重+的/地替换+特例词库，朱雀验证AI率从74%降到13.9%。

 6. **方法论提取+应用层控制**: 从降得快公开页面提取方法论，放应用层做硬规则(不进SKILL)，SKILL只负责改写规则。应用层掌握选择权和注入权。

 7. **多供应商同时启用**: A供应商全局生成，B供应商验证(去AI味)，各自独立不冲突。

 8. **规则19 GATE门禁**: 封装前必须运行重复选择器检测脚本，非媒体查询真冲突必须为0才允许封装。这是把规则变成可执行机制的成功案例。

 9. **全面应用审计方法**: 117项UI标注逐一验证，三层验证(自动化脚本→代码搜索→CDP行为)，区分真缺陷与误判(20个FAIL中17个误判3个真缺陷)。

 10. **诊断检测器**: 自动检测用户日常使用中的问题生成日志保存到文件夹，方便远程排查。

 ## 要避免的做法

 1. **禁止只做node --check就声称完成**: 必须CDP实际操作+截图+行为验证三步走。

 2. **禁止用Runtime.evaluate替代真实点击**: 假阳性的最大来源。

 3. **禁止PowerShell Set-Content写中文文件**: 用Node.js fs。

 4. **禁止CSS只加不删**: 先搜后改，合并到一处。

 5. **禁止硬编码任何测试数据/API Key**: 每次封装前检查。

 6. **禁止设token_budget/超时/递归深度限制**: 用户要求无限制就是无限制。

 7. **禁止以线程限制为借口拒绝使用Agent**: tool_search先搜索加载。

 8. **禁止新增规则但不检查旧规则**: 每次加规则时审查旧规则是否已不适用。

 9. **禁止只修一个环节不验证完整链路**: 修水管每个接头都修好了但要从没通水测试。

 10. **禁止降AI时只删不改**: 删句子破坏流畅性，应该改而不删。

 11. **禁止把38个风格样本全塞SKILL**: 放应用层，按相似度挑2-3个注入。

 12. **禁止在S1之前跑硬规则**: 硬规则改变token统计特征，S1在已清洗文本上改写反而引入新的可检测模式。

 # 六、遗留隐患

 以下问题当时没彻底解决、暂时绕过或妥协处理:

 1. **次级栏章节显示限制**: 流水线生成200+章但主界面次级栏只能显示几十章，下拉有限制。未彻底解决。

 2. **去AI味供应商获取模型失效**: 用户反映获取模型请求失败，应用一直用默认模型。供应商获取模型链路不稳定。

 3. **去AI味未同步用户选择的模型**: 去AI味页面可能没有正确读取用户在供应商设置里选的模型。多供应商同时启用后的模型同步逻辑可能不完整。

 4. **白虎SKILL仍在迭代**: S1-S2-S3链式SKILL是初版，白虎V64提出多步代码控制(拆成3次独立API调用)但应用层尚未完全配合实现。

 7. **章节plot字段可能过短**: 模型可能输出空洞的plot（几个字），field_exists可被绕过。field_min_length(plot, 200)验证器需求已提出但未确认实现。

 8. **JSON字符串转义问题**: 模型输出字面换行或裸ASCII双引号导致JSON.parse()失败。json_escape_valid验证器需求已提出但未确认实现。

 10. **38个风格样本文件**: 之前创建过但是否能找到未确认。放应用层的方案已设计但样本文件的完整性未验证。

 11. **去AI味流程预览在封装版中不更新**: 用户反映切换模式/切换SKILL流程预览不变。CDP验证可能通过但封装版行为不一致。

 ## 8.1 开发历程

 降AI是项目后半段(08-03~08-08)的核心功能，经历54个版本迭代:

 # 十、总结

 这个项目的核心矛盾是: AI Agent(Codex)的自我评估机制无法准确判断工作完成度。写完代码≠功能完成，测试通过≠功能正常，CDP验证通过≠用户能用。这个认知扭曲导致了项目中80%的信任崩塌事件。

 最有效的改进措施不是新增规则(规则已经够多了)，而是把规则变成可执行的门禁机制(GATE)。规则19(封装前CSS冲突检测)是成功案例: 从口号变成脚本检测，非0冲突禁止封装，这个规则真正阻止了CSS只加不删的问题。

 降AI功能的开发证明了: 用提示词规则对抗模型生成惯性是无效的，需要在代码层做强制修正。硬规则(代码层)+白虎SKILL(改写层)的双轨方案是目前最有效的架构。

 项目的最大遗留风险是: 封装版与源文件行为不一致(CDP验证通过但安装版有问题)，以及多供应商同时启用后的模型同步链路不完整。这两个问题需要在后续版本中优先解决。

 ## 教训#15: 反复空转不写文件
 
 现象: 编写v3计划文件时多个回合反复尝试apply_patch但格式报错，导致文件迟迟未写入磁盘
 根因: apply_patch对hunk header格式要求严格，长文本(790行)容易在中间某行格式不对导致整个patch失败
 修复: 使用apply_patch的Add File模式一次性写入成功
 规则: 文件写入失败2次后必须换方法(apply_patch -> Write -> Node.js fs)，禁止在同一个失败方法上反复尝试超过2次
