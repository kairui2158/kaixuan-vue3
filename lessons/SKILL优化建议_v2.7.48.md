# 对SKILL层的优化建议 v2.7.48

## 背景

应用已升级为真SKILL架构（SkillExecutionEngine），代码层已实现：自动验证、失败重试、切分并行、多步控制流。以下是对各层级SKILL的优化建议，帮助SKILL更好地配合新引擎工作。

## 一、通用建议（适用所有层级）

### 1. 不需要在template中做格式验证
**现状**：很多SKILL在template中写了"输出必须是合法JSON""数组长度必须等于N"等格式约束。
**建议**：这些约束现在由引擎的验证器自动执行（json_array、exact_count、field_exists）。SKILL可以把这些篇幅用来写更具体的语义约束。
**例外**：如果SKILL需要约束的是非标准格式（如自定义XML、特定字段顺序），仍需在template中说明。

### 2. 输出纯净度要求可以降低
**现状**：SKILL写了"必须绝对纯净——只能是一个合法的JSON数组，不能包含任何其他文字"。
**建议**：引擎的 `_tryParseJSON` 会自动从文本中提取JSON数组（找第一个`[`到最后一个`]`），所以模型输出前后有少量说明文字不会导致解析失败。但保持纯净输出仍然是好习惯，只是不需要用大量篇幅强调。

### 3. 可以利用验证反馈
**现状**：验证失败后引擎会自动重试，重试时把验证失败原因附加到prompt末尾。
**建议**：SKILL可以在template中预留一段"如果收到验证反馈，请优先修正"的说明，帮助模型在重试时更精准地修正问题。

## 二、各层级具体建议

### 大纲层SKILL
**当前状态**：无需改动，chain模式默认执行。
**建议**：
- 可以在template中增加对大纲结构化程度的约束（如"大纲应包含至少3卷的结构"），因为引擎目前没有为大纲层挂载自动验证器
- 大纲层的输出是纯文本（非JSON），引擎不会做格式验证，SKILL需要自行约束输出格式

### 设定层SKILL
**当前状态**：自动验证器已挂载（json_array + field_exists(name)）
**建议**：
- SKILL不需要再强调"输出JSON数组"和"每项含name字段"——验证器会自动检查
- 可以把节省的篇幅用来写更详细的attrs字段约束（如"attrs应包含core、mechanism、limits三个key"）
- 伏笔ID（F001格式）的完整性目前没有自动验证器，SKILL仍需自行约束

### 卷纲层SKILL
**当前状态**：自动验证器已挂载（json_array + min_length(50)）
**建议**：
- min_length(50)是一个较低的门槛，SKILL可以自行设定更高的内容质量约束
- 卷纲的字数分配逻辑（如"本卷约X万字"）仍需SKILL在template中约束，引擎不做字数分配验证
- 卷纲间的连续性（卷1结尾→卷2开头）没有自动验证器，SKILL需要在template中强调

### 章节层SKILL
**当前状态**：自动验证器已挂载（json_array + field_exists(title,plot) + exact_count）
**建议**：
- **最重要**：exact_count验证器会确保章节数精确匹配expectedCount，SKILL不需要再大量强调"必须恰好生成N章"。但保留一句提醒仍然有助于模型在第一次就生成正确数量，减少重试
- plot字段中的换行符转义（\n）和双引号转义（\"）目前没有自动验证器，SKILL仍需约束
- 章节间的因果推进链条没有自动验证器，SKILL需要在template中强调
- 建议在template中明确："如果收到'expected exactly N items but got M'的验证反馈，请增减章节使其精确匹配"

### 正文层SKILL
**当前状态**：自动验证器已挂载（min_length(500)）
**建议**：
- min_length(500)是防止空输出的最低门槛，SKILL应自行约束更合理的内容质量
- 正文层的感知流规则（句号落点、POV锚定、感官通道）仍需SKILL在template中约束
- 引擎不会对正文做语义验证（如"是否覆盖了章节plot的所有要点"），SKILL仍需约束

### 去AI味层SKILL（白虎SKILL）
**当前状态**：支持三种模式（chain/splitMerge/multiStep）
**建议**：

#### 对白虎S1（重述师）的建议
- **chain模式**：当前template完全兼容，无需改动
- **splitMerge模式**：template会被应用于每个切分段落（约1000-2000字），建议确保template对短文本也有效
- **multiStep模式**：如果要从单文件拆为S1A/S1B/S1C三文件：
  - S1A（事件核提取）：只负责提取事件核，输出结构化文本
  - S1B（偏转视角）：只负责选偏转方法，输出事件核+偏转标注
  - S1C（重组输出）：只负责从零重组，输出重述文章
  - 引擎会代码控制三步的输入输出，模型无法跳步
  - S1C后有首句主语对比验证，如果与原文首句主语相同会自动重试

#### 对白虎S2（验证师）的建议
- S2作为multiStep的第4步（可选），引擎会自动传入S1C的输出
- 如果配置了verify供应商，引擎会在S2之前做跨模型语义验证
- S2的template可以更专注于表层修正（词汇替换、句式微调），因为深层结构变化由S1A-S1C负责

## 三、引擎能力边界（SKILL需要自行处理的）

| 能力 | 引擎是否支持 | 说明 |
|------|--------------|------|
| JSON格式验证 | 是 | json_array验证器 |
| 字段存在性验证 | 是 | field_exists验证器 |
| 数量精确匹配 | 是 | exact_count验证器 |
| 最小长度验证 | 是 | min_length验证器 |
| 首句主语对比 | 是 | first_subject_different验证器 |
| 跨模型语义验证 | 是 | cross_model_check验证器（需配置verify供应商） |
| 朱雀AI检测 | 是 | zhuque_check验证器（需配置detect供应商） |
| 伏笔ID完整性 | 否 | SKILL需自行约束 |
| 章节因果链条 | 否 | SKILL需自行约束 |
| 卷纲连续性 | 否 | SKILL需自行约束 |
| 感知流规则 | 否 | SKILL需自行约束 |
| 字数分配逻辑 | 否 | SKILL需自行约束 |
| plot字段转义 | 否 | SKILL需自行约束 |

## 四、未来演进方向

1. **自定义验证器**：未来可以支持SKILL在template中声明自定义验证规则，引擎自动执行
2. **条件分支**：未来可以支持SKILL根据上一步输出内容选择不同的下一步SKILL
3. **多采样择优**：未来可以支持对同一步骤调用多次API，取验证结果最优的输出
4. **进度反馈**：引擎已支持onProgress回调，未来可以在UI上展示更详细的执行进度

## 总结

引擎已覆盖了格式验证、数量验证、长度验证、主语验证等硬性约束。SKILL应将精力集中在引擎覆盖不到的领域：语义连贯性、伏笔追踪、感知流规则、字数分配、因果链条等。两者各司其职，代码管硬约束，SKILL管软约束。
