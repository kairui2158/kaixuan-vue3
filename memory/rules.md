# 用户规则

## 规则1: 全程中文
所有对话使用中文，技术术语可用英文但需解释。

## 规则2: 纯文本标记
控制台输出使用 [OK]/[ERR]/[WARN]，禁止使用 emoji 特殊符号。

## 规则3: 最小改动
只修改与当前任务直接相关的代码，禁止批量大修。

## 规则4: 精准修复
遇到错误逐处修复，禁止批量正则替换。

## 规则5: 备份先行
每次修改前用 Copy-Item 备份到项目目录下的 BACKUP 文件夹。根目录保持绝对干净，所有备份文件只存在于 BACKUP 文件夹内。需要读取备份文件时从 BACKUP 文件夹读取。

## 规则6: 修改后验证
每次改完立即 node --check 验证语法。

## 规则7: 网络重试
下载被中断重试最多5次，超过后换替代方案。

## 规则8: 零假数据
禁止添加默认 API Key、示例供应商数据、硬编码模型名。

## 规则9: 用户小白
所有操作需用最直白详细的步骤说明，用户是编程新手。

## 规则10: 超时坚持
应用开发中遇到任何超时现象，必须严格按照计划方案持续执行。超时时间超过20分钟后才能考虑换取替代方案。禁止在20分钟内因超时而放弃当前方案。
## 规则11: GitHub 自动备份
每次完成项目功能更新后，自动将当前代码、开发日志(DECISIONS.md, PROGRESS.md, CONTEXT.md)和项目记忆(memory/)一起提交推送到 GitHub 仓库 kaixuan (kairui2158/kaixuan)。每完成一个功能点就提交一次，保持提交历史清晰。

## 规则12: GitHub Token 安全存储
GitHub 个人访问令牌通过 gh CLI 安全存储在 Windows 凭据管理器（keyring）中，不写入任何项目文件。代码中通过 gh CLI 或 GitHub API 读取令牌时从凭据管理器获取。禁止将令牌明文写入 rules.md、.env 或任何可被 git 追踪的文件中。

## 规则13: 测试报告留存

- 每次测试生成的报告必须保存到 tests/reports/ 目录,文件名含时间戳,禁止覆盖旧报告
- 修复后必须重新测试并生成对比报告(test_diff_*.txt)
- 报告格式: JSON + TXT + DIFF
- FAIL 项按 8 大类别分类: garbled/function_failure/interaction_break/data_persistence/conditional_render/security/layout/state_consistency

## 规则14: 清理安全

- 执行任何清理操作前,先 Copy-Item 备份当前所有源文件到 BACKUP/cleanup_YYYYMMDD/
- 清理时绝对不要修改 renderer.html 中的 meta charset UTF-8 和任何编码相关代码
- 清理后立即启动应用验证中文正常,乱码则立即回退备份


## 规则15: Agent协作强制使用

当用户明确要求使用 Agent 分工合作时，必须遵守：

- 禁止以"线程限制"、"并发上限"、"工具不可用"为借口拒绝使用 Agent。这些工具默认是延迟加载(defer_loading)，必须先用 tool_search 搜索加载后再使用。
- 禁止自己一个人干所有工作。能并行的任务必须拆分成不重叠的写文件范围，派 worker Agent 并行执行。
- 验证阶段必须派 explorer Agent 作为外部裁判，不参与代码修改，只负责 CDP 行为验证。
- 每次 spawn_agent 前必须明确：任务描述、负责的文件、不与其他 Agent 重叠的范围。
- Agent 完成后及时 close_agent 释放并发额度。
- 违反此规则 = 偷懒行为，任务无效需重做。

## 规则16: 验证三铁律

1. 外部裁判：每个改动完成后，不能靠读代码判断通过。必须用 Playwright CDP 实际操作应用，截图+JSON日志+时间戳三者缺一视为未验证。
2. 行为验证：不验证"元素存在"，验证"功能能用"。必须验证"操作→预期行为→实际结果"三元组。
3. 强制执行：每个 Phase 有验证清单，任何一项 FAIL 禁止进入下一 Phase。FAIL 修复后重跑完整清单。用户可随时抽查，不符则全部重测。

## 规则17: 错误实时记录

在启用检测计划表(VERIFICATION_PLAN_V3)执行期间，每遇到一个错误/FAIL，必须立即将其记录到 lessons/ERROR_LOG.md 错误总结表中。记录格式:
- 时间戳(精确到秒)
- 所在阶段(Phase X)
- 错误描述
- 根因分析
- 修复方案
- 修复验证结果
- 是否闭环(已修复/待修复)

禁止在检测完成后才补记错误。错误必须在发现的当下实时写入。错误总结表与 DETECTION_LOG.md 并行维护，但 ERROR_LOG.md 专门只记错误，不记通过项。



## 规则18: 检测执行时Agent透明报告

在执行 VERIFICATION_PLAN_V3 检测计划期间，每次 spawn_agent 必须向用户明确报告:
- Agent 类型(explorer / worker)
- Agent 昵称(系统分配的)
- 任务描述
- 负责的文件范围
- 与其他 Agent 不重叠的声明
禁止静默启动 Agent。用户有权随时查看哪些 Agent 正在工作、各自负责什么。Agent 完成后报告结果并 close_agent。违反此规则 = 隐瞒行为，检测结果无效。

## 规则20: 429限流应对（含标准操作SOP）

### 429 的本质
- 429 是 API 硬限制，不是客户端状态问题
- 目标模式(防断网)解决不了 429 本身，只能帮 429 解除后从断点恢复
- 子 Agent 和主 Agent 共享同一份配额，子 Agent 触发 429 也会阻塞主 Agent

### 强制应对流程(遇到 429 时执行)
1. 不放弃，按递增间隔重试: 30s -> 60s -> 90s -> 120s -> 150s -> 180s -> 210s -> 240s
2. 重试期间不空等，做不依赖新 API 调用的本地工作(读文件、跑已写好的脚本、整理审计结果)
3. 如果是子 Agent 触发的 429，关闭旧子 Agent 释放配额再试
4. 总等待约 15 分钟后才考虑换替代方案
5. 重试成功后从断点继续，不从头重来

### 重试上限耗尽后的处理（exceeded retry limit）

当 8 次重试全部失败、系统报出 exceeded retry limit 时，按以下流程执行：

1. 目标模式继续运行，不被 429 阻塞。目标模式防的是网络中断后从断点恢复，不防 API 限流。429 持续期间目标模式照常推进本地工作。
2. 立即切换到不依赖被限流资源的本地工作：CSS 编辑、文件读取、CDP Runtime.evaluate 验证、整理审计结果、清理技术债务。不空等。
3. 不标记任务为 blocked 或失败。429 是临时状态不是终态，配额恢复后即可继续。
4. 每 5 分钟静默重试一次被限流的操作（Agent spawn / API 调用 / GitHub 搜索），不阻塞主线工作流。
5. 当 429 解除后，从断点继续执行被暂停的工作，不从头重来。
6. 向用户如实报告当前状态：429 持续中，已切换到本地工作 N 项完成，每 5 分钟重试，第 X 次重试中。
7. 如果 429 持续超过 30 分钟，向用户报告并建议：关闭 VPN 释放 IP 限流 / 更换 API 端点 / 等待配额窗口重置。由用户决定是否暂停。

### 目标模式与 429 的关系（明确）
- 目标模式 = 防断网机制，网络断开时自动从断点恢复，不丢工作进度
- 429 = API 配额限流，与网络无关，目标模式解决不了 429
- 两者独立：429 持续时目标模式照常运行，只是被限流的具体操作暂停，本地工作继续
- 禁止因 429 把目标模式标记为 blocked
- 禁止因 429 终止目标模式

### 禁止事项
- 禁止因 429 跳过当前步骤
- 禁止因 429 放弃任务
- 禁止用简化方法绕过需要 API 的验证步骤
- 禁止把 429 当作任务失败的借口

### 标准操作SOP（遇到429时按此顺序执行，不得跳步）

遇到 exceeded retry limit, last status: 429 Too Many Requests 时的正确做法：

1. 不放弃不简化 — 429是临时状态，禁止跳过步骤、禁止用简化方法绕过、禁止标记任务失败
2. 目标模式继续运行 — 429不阻塞目标模式，防断网机制照常工作，从断点恢复
3. 递增重试 — 按 30s->60s->90s->120s->150s->180s->210s->240s 间隔重试，共8次约15分钟
4. 重试期间做本地工作 — 读文件、CSS编辑、CDP Runtime.evaluate验证、整理审计、清理技术债务，不空等
5. 子Agent触发429时 — 关闭旧子Agent释放配额，再重新spawn
6. 8次重试全部失败后 — 不终止任务，切换纯本地工作，每5分钟静默重试一次被限流操作
7. 429解除后 — 从断点继续，不从头重来
8. 超时持续等待 — 任何超时(CDP/API/Agent spawn)都持续等待，禁止跳过，禁止用简单方法
9. 递归不限深度 — 递归到最低层，禁止限制5层
10. 必须真实交互 — 截图+DOM操作验证，禁止只检查元素存在不验证功能正确

禁止事项：
- 禁止用 --no-verify 绕过门禁
- 禁止因429把目标模式标记为blocked
- 禁止因429终止目标模式
- 禁止用简化方法绕过需要API/截图的验证步骤
- 禁止把429当作任务失败的借口


## 规则21: 模块清零优先，先删后改仅用于无法清零的模块（用户铁律·2026-07-20调整）

### 核心策略（用户调整后）
默认策略是`模块清零`：能整体清零的模块直接全删旧CSS，用15维度token重新编写。`先删后改`降级为备选策略，仅用于无法整体清零、必须精准修改的模块（如@media响应式覆盖块、功能性特殊覆盖）。

### 策略选择决策树
1. 判断模块能否整体清零：看该模块的CSS是否是独立功能块（如按钮系统/卡片系统/表单控件/面板头部等）
2. 能清零 → 模式A模块清零：全删旧块 → 用统一token重新编写 → CDP逐属性验证
3. 不能清零（与功能逻辑强绑定、涉及@media/@supports等条件块） → 模式B先删后改：逐选择器删除冗余 → 每删一个CDP验证 → 用token精准修改
4. 禁止混合两种策略：一个模块要么全清零，要么精准修，不能清零一半又改一半

### 强制执行流程
1. 修改前：先用CDP或源码扫描定位该模块的所有相关规则，判断属于模式A还是模式B
2. 删除阶段：模式A全删旧块；模式B逐选择器删除冗余、死代码、被覆盖的旧规则
3. 重写/修改阶段：在删干净的基础上，用统一的令牌系统编写（模式A）或精准修改（模式B）
4. 验证阶段：CDP行为验证修改生效（规则16），逐属性验证不是整块验证
5. 体积检查：每次修改后检查文件行数，如果行数增长说明在叠加，必须回头删减

### 统一规格原则（美容专用·用户铁律）
- 美容不是各处各规格，是定好一套统一规格全部使用
- 卡片大小长宽高必须统一（同类卡片用同一套尺寸令牌）
- 卡片内字体格式必须统一（同类卡片用同一套字号/字重/行高令牌）
- 按钮间距/宽度/高度必须统一（同类按钮用同一套尺寸令牌）
- 不允许一个面板一个规格，必须全局统一

### 禁止行为
- 禁止在已有规则上加 !important 覆盖（应该删除冲突规则而不是叠加覆盖）
- 禁止保留死代码和死规则（修改后立即清理被替代的旧规则）
- 禁止保留无用的备份文件堆积（BACKUP/ 目录定期清理，只保留最近3个版本）
- 禁止生成大量临时审计脚本堆积（scripts/ 下的 r*_*.cjs 用完即删或归档）
- 禁止边删边改（模式A必须先删干净再重写，模式B逐选择器删改）

### 体积红线
- style.css 行数不得超过 10000 行（当前超标，必须删减）
- 每次美容轮次后，如果文件行数增长，必须回头删减至少等量的冗余
- 发现重复声明（同一选择器同一属性多次出现）必须合并为1条

### 经验依据
- R56 focus 失效：3层 !important 互相覆盖，加规则不生效，根因是叠加太多
- 用户多次反馈：修复来修复去问题越来越多，应用没变化，全是冗余堆积
- R43-R55 累计 55 轮美容，style.css 从约 9000 行涨到 10746 行，增长 1746 行无删减
- 用户2026-07-20明确调整：能清零的模块直接全删重写，先删后改只适用于无法清零必须精准修改的模块
## 规则22: 编码安全（规则13编码冲突修复）

## 规则23: PowerShell 7.6.3 强制使用（用户铁律）

### 核心原则
本地已安装最新版 PowerShell 7.6.3，路径为 C:\Program Files\PowerShell\7\pwsh.exe。今后所有 PowerShell 操作强制使用此版本，替换旧版 Windows PowerShell 5.1。

## 规则23: 文本过滤层使用规范

### 背景
模型生成惯性(语义完整即句号)无法用提示词规则对抗。需用确定性代码过滤。

### 规则
1. 文本过滤开关默认关闭，用户自行决定是否启用
2. 过滤只在链式Skill执行(多Skill)时生效，单Skill追加模式不过滤
3. JSON输出(以[或{开头)自动跳过过滤，保护结构化数据
4. 规则1: 段落开头句号前文本<=30字才改逗号，长句不误伤
5. 规则2: 合并前检查seg0(第一个句号前文本>15字时不合并)
6. 修改过滤函数后必须Page.reload(ignoreCache:true)才能在运行中生效
