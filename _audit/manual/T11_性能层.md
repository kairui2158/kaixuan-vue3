# T11 - 性能层 (Performance Layer)

> 旧架构行为手册 第十一层 | 源码权威参考 | Vue3迁移差异检测驱动依据

## 1. 层级定位与职责边界

性能层负责应用的响应速度、内存使用和渲染效率。旧架构作为纯HTML+CSS+JS应用无虚拟DOM无框架开销，性能优化主要靠手动防抖节流和惰性渲染。

职责范围：防抖（debounce）机制；节流（throttle）机制；大列表渲染优化；编辑器性能；API调用性能追踪；内存管理。

## 2. 防抖机制

### 2.1 编辑器内容变化防抖

源码位置: renderer_v2.js 编辑器事件绑定

编辑器input事件使用防抖，避免每次按键都触发自动保存和字数统计。典型防抖延迟300-500ms。

行为契约：用户停止输入300ms后才触发回调；连续输入只触发最后一次；防抖期间不阻塞UI。

### 2.2 设置面板表单防抖

设置面板的输入框（如baseUrl、apiKey、temperature）使用防抖保存，避免每次按键都触发StorageManager.set写入文件。

### 2.3 窗口大小变化防抖

窗口resize事件使用防抖保存窗口状态，避免频繁写入window-state.json。

源码位置: main.js L100-101

mainWindow.on("resize", function() { if (!mainWindow.isMaximized()) saveWindowState(); });
mainWindow.on("move", function() { if (!mainWindow.isMaximized()) saveWindowState(); });

注意：旧代码实际没有对resize/move做防抖，每次事件都直接调用saveWindowState()。这是性能隐患，高频resize会频繁写入文件。

## 3. 节流机制

### 3.1 流式输出节流

AI流式输出通过onChunk回调更新UI。每次收到chunk都更新DOM会导致频繁重绘。旧架构没有显式的节流机制，依赖浏览器的requestAnimationFrame自然节流。

### 3.2 进度条更新节流

去AI味流程的进度条更新使用百分比计算，每完成一个步骤更新一次，不需要节流。

## 4. 大列表渲染优化

### 4.1 章节列表渲染

旧架构的章节列表（可能数百章）直接用innerHTML拼接HTML。没有虚拟滚动，所有章节DOM节点同时存在。当章节数超过200时会出现明显卡顿。

问题根因：每个章节DOM节点包含标题、字数、状态等元素，200章=1000+DOM节点。DOM操作是同步的，大量节点插入会阻塞主线程。

### 4.2 聊天消息列表

聊天消息使用append方式逐条添加，不重新渲染整个列表。这是正确的做法，避免了全量重渲染。

## 5. 编辑器性能

### 5.1 编辑器实现

旧架构使用contenteditable div作为编辑器，不是textarea。优点：支持富文本格式。缺点：大文本时性能差（浏览器需要对contenteditable做复杂的布局计算）。

### 5.2 撤销重做

使用document.execCommand('undo'/'redo')，这是废弃API但在旧架构中仍然工作。大文本时撤销栈可能消耗大量内存。

### 5.3 自动保存

自动保存使用setInterval定期触发，间隔由AppearanceSettings.autoSaveInterval控制。每次保存都全量写入StorageManager。

## 6. API调用性能追踪

源码位置: _aiRequest方法内

var _diagKey = "api-" + Date.now() + "-" + Math.random().toString(36).substr(2,5);
if (window.DiagLogger) DiagLogger.perfStart(_diagKey);
// ... API调用 ...
var _el = DiagLogger.perfEnd(_diagKey, "api", "API");
DiagLogger.trackApiCall(reqBody.model || "?", 0, _el, "ok");

每次API调用都记录：模型名、耗时、成功/失败。可用于分析API响应速度趋势。

## 7. 内存管理

### 7.1 数据缓存策略

旧架构的Manager每次读取都从StorageManager获取最新数据，不在内存中缓存。优点：数据始终最新。缺点：频繁的IPC调用和文件IO。

### 7.2 流式响应内存

流式响应的fullText和reasoningText在内存中持续增长。对于长文本生成（如5000字正文），内存占用约10-20KB，不是问题。但多个并发流式请求可能累积。

### 7.3 事件监听器清理

旧架构在面板切换时使用innerHTML替换，旧的DOM节点被GC回收。但没有显式移除事件监听器，可能导致内存泄漏（闭包引用的DOM节点无法被GC）。

## 8. GPU加速

源码位置: main.js L40

app.commandLine.appendSwitch("remote-debugging-port", "9223");

注释说明：保持硬件加速启用以获得流畅渲染。之前禁用GPU合成会导致严重卡顿（软件合成）。如果特定GPU驱动出现黑屏，使用--use-angle=d3d11替代。

## 9. Vue3迁移差异检测要点

### 9.1 必须保留的行为

1.编辑器防抖300ms 2.设置表单防抖保存 3.聊天消息append方式 4.API调用性能追踪 5.DiagLogger trackApiCall 6.GPU硬件加速保持启用

### 9.2 可改进的行为

1.章节列表虚拟滚动（只渲染可视区域）2.resize/move事件防抖 3.编辑器改用CodeMirror或Monaco 4.数据缓存减少IPC调用 5.事件监听器显式清理 6.用IntersectionObserver做惰性加载

### 9.3 差异检测规则

编辑器防抖延迟300ms应保持；API性能追踪格式应保持；GPU加速策略应保持；DiagLogger trackApiCall应保持。

## 10. 已知问题

1.章节列表无虚拟滚动200+章卡顿 2.resize/move无防抖频繁写文件 3.contenteditable大文本性能差 4.execCommand已废弃 5.无事件监听器清理可能内存泄漏 6.Manager无缓存频繁IPC调用
