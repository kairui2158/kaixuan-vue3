## 0. 审计边界与判定规则

本轮是审计和计划复核，不是修复执行。

- 本轮未修改生产源码。
- 本轮未启动 Vite/Electron。
- 本轮未执行 CDP、Playwright 或截图。
- 本轮未封装安装包。
- `PASS` 只表示本轮有足够的当前源码或新鲜行为证据；历史报告中的 PASS 不自动继承。
- `PARTIAL` 表示有实现，但链路、边界或真实行为仍不完整。
- `UNVERIFIED` 表示可能存在实现，但本轮没有运行证据。
- `MISSING` 表示当前源码没有对应生产入口或实现。
- `BLOCKED` 表示存在明确阻塞条件，必须先处理才能继续验收。

本轮严格沿用经验文件中的原则：代码存在不等于真实行为通过；服务存在不等于下游接入；新字段必须贯穿加载、保存、迁移、重启；导入合并与覆盖必须分开；evidence 必须对应正文；`recordMemoryChange()` 后必须等待保存；空状态不能冒充真实数据验证。

## 1. 当前真实架构总览

当前主链路是：

```text
正文保存
  -> AI 单阶段抽取五类记忆
  -> JSON 解析与 chapterId/evidence 基础过滤
  -> mergeMemory 增量合并
  -> 用户预览、拒绝、锁定
  -> recordMemoryChange 写入 projectStore.memories
  -> saveProject 持久化
  -> MemoryPanel 响应式显示
```

当前读取链路是：

```text
projectStore.memories
  -> retrieveContext 字符串筛选/拼接
  -> PipelinePanel 正文生成请求
  -> ChatPanel 聊天请求
```

这个架构已经具备“基础记忆库”，但还不是完整的“记忆线对齐与影响传播中枢”。当前不存在可核对的动画/短剧生产板块；`memoryExport.ts` 只是导出服务，不能算下游板块已接入。

## 3. 发现的系统性根因

### 3.1 把“记忆对象”当成了“记忆事实”

当前实体、事件、关系等对象可以展示和合并，但没有不可变事实层。没有原子事实、来源片段、正文版本、有效时间和状态，就无法可靠回答“这条记忆来自哪一版正文”“后文是否推翻它”“修改卷 2 后哪些卷受到影响”。

### 3.2 抽取、合并、检索之间缺少同一条来源主键

抽取结果主要依赖 `chapterId` 和字符串 evidence；合并后对象没有统一 `sourceEpisodeId`、`sourceRange`、`sourceVersionId`。这会导致跨卷、跨章、正文重写和来源跳转只能做近似处理。

### 3.3 生成入口有统一趋势，但记忆入口仍有两套调用路径

`EditorPanel` 通过 `getAiService().callAi`，`PipelinePanel` 另有 `callMemoryApi`/`callApiWithAgent` 路径。两边都能请求 AI 不等于供应商、超时、重试、purpose、日志和错误恢复已经统一。

### 3.4 UI 是“新模型只读 + 旧模型可编辑”的过渡态

这解释了为什么面板看起来有实体、关系、事件等内容，但用户无法对它们进行统一修改、删除、锁定、查看来源和审计。继续在旧 `items` 上补按钮不能解决模型层缺口。

### 3.5 历史验收把静态证据和行为证据混在一起

既有报告同时出现“前段 UNVERIFIED、后段最终 PASS”的矛盾写法。今后必须按本报告五种状态逐项核销；没有真实样本、真实点击、真实请求、真实落盘和重启恢复，就只能保持 `PARTIAL` 或 `UNVERIFIED`。

## 4. 三版计划复核与重排

旧的三版方向是正确的，但第一版需要扩大为“可靠基础闭环”，第二版才进入记忆线语义，第三版负责跨板块和扩展。不能直接拿旧计划的勾选项执行，因为旧计划把部分静态实现误标为完成。

### 第一版：可靠基础闭环（当前应先做）

目标：不丢数据、可追溯、可审核、可恢复；先把已有写作板块和记忆板块的事实边界做实。

#### A. 来源与版本基础

1. 增加 `SourceEpisode`、`SourceDocument`、`SourceVersion`，至少关联项目、卷、章、正文版本、内容 hash、时间和来源范围。
2. 将每个抽取条目规范化为带来源的原子事实；`evidence` 必须包含 `sourceVersionId`、章节、范围、snippet、校验状态。
3. 记录正文保存版本；编辑器直接修改和流水线生成必须产生同一格式的正文版本记录。
4. 对旧 `MemoryData.version=1` 做显式迁移，未知字段不得静默丢弃；迁移前保留备份。

#### B. 抽取与证据

1. EditorPanel 与 PipelinePanel 统一调用一个记忆抽取服务入口，统一 provider purpose、超时、重试、取消、日志和返回协议。
2. AI 返回后做结构化 schema 校验、章节归属校验、snippet 在对应正文版本中的真实存在校验；失败条目进入待审核，不静默写入。
3. 抽取失败不阻塞正文保存；正文状态和记忆任务状态分离，支持重试、取消和断点续跑。
4. 为抽取、解析、证据过滤、合并、预览、确认、拒绝、锁定分别记录结构化日志。

#### C. 合并、审核与不覆盖

1. 合并器改为“追加事实、显式替代、冲突待审”，禁止用 `Object.assign` 直接覆盖未经比较的事实。
2. 引入 `confirmed/pending/stale/conflicted/rejected` 状态和 `supersedes/conflictsWith` 关系。
3. 统一预览模型：新增、更新、冲突、过期、删除建议分开显示；用户确认才改变正式事实。
4. 所有手工编辑、导入、角色卡导入、锁定、解锁、删除都进入统一 change record；锁定字段永远不能被自动抽取覆盖。
5. 默认导入永远是合并；覆盖导入必须二次确认并先备份，且支持撤销。

#### D. 持久化、并发和 UI

1. `saveProject` 增加写入队列/序列号，所有关键调用 await；关闭流程等待最终保存 Promise，而不是固定 500ms 猜测。
2. 项目切换时取消或隔离旧项目请求，禁止旧请求回写新项目 Store。
3. MemoryPanel 改为新模型统一 CRUD；legacy `items` 只作为兼容读写适配层，不再与新模型混成一套索引。
4. 每个实体、关系、事件、世界观、伏笔都支持来源查看、编辑、删除、锁定、变更历史和恢复。
5. 真实非空数据完成五视图验证，不能以空状态核销关系图、事件时间线和来源跳转。

#### E. 第一版硬验收门

- 新旧项目加载、保存、关闭、重启后实体/关系/事件/世界观/伏笔和历史完全一致。
- 正文确认、审核拒绝、字段锁定、冲突待审和确认写入逐项有真实行为证据。
- 合并导入不覆盖，覆盖导入可撤销，坏 JSON 不改变当前数据。
- 编辑器与流水线产生的记忆进入同一抽取/合并/审计链。
- 供应商失败、超时、非法 JSON、取消后正文不丢失，任务可恢复。

### 第二版：记忆线对齐与语义记忆

目标：解决“卷 2 修改后，哪些后续剧情受影响”以及主线/支线/人物线持续整理。

1. 增加 `Fact`、`PlotThread`、`Alignment`、`ImpactRecord`、`TimelineAssertion` 等模型。
2. Memory Skill 采用目录/manifest 形式；说明、schema、抽取规则、校验器、示例分离，应用负责调度和状态机。
3. Memory Agent 只负责固定职责调度：事实提取、证据定位、时间归属、剧情线归类、冲突检测、影响分析；每一步输入输出由代码控制，不能让模型自行跳步。
4. 建立卷纲→设定→卷纲要→章节→正文的跨层对齐表，保存目标、实现、偏差、来源和状态。
5. 建立正文版本 diff 到事实的反向索引：删除、改写、新增正文时标记 stale/conflicted，并列出受影响的卷、章、人物线、伏笔线和后续事件。
6. 时间线支持故事内时间、章节顺序、叙事顺序、有效起止和不确定性；图区分事实冲突与视角差异。
7. 检索升级为结构化过滤 + 关键词/BM25 + 向量 + 图邻居的混合检索；默认只注入 confirmed 且时间有效的事实，冲突事实必须带提示。
8. 关系图、思维导图、时间线、画像卡统一读取事实/线路/对齐服务，并支持从任何节点回到正文来源和版本差异。

#### 第二版硬验收门

- 人工修改卷 2/章 20 后，系统能列出受影响事实、剧情线、后续章节和需要重审的伏笔。
- 同一事实的多来源、冲突、锁定、替代和回滚可追溯。
- 主线、支线、人物线、伏笔线可以筛选、对齐、查看来源和定位偏差。
- 检索在长文本样本上不带入过期/冲突事实，且有命中证据。

### 第三版：跨板块生产与扩展能力

目标：写作板块 → 记忆中枢 → 动画/短剧素材包形成可追踪生产链。

1. 动画/短剧作为真实板块接入，不把导出函数冒充板块完成。
2. 从记忆和正文生成可编辑素材包：角色表、场景表、道具表、时间线、分镜、镜头、动作、对白、旁白、音效、音乐提示、画面提示词、视频提示词和字幕。
3. 素材包每项带来源事实、正文版本、记忆版本和导出版本；用户修改素材不会反向覆盖小说正文，需经过明确回写流程。
4. 提供剪映、Runway、HeyGen 等外部工具可消费的 JSON/CSV/Markdown/图片目录/字幕格式；外部工具是可选消费者，不作为神意核心运行依赖。
5. 增加本地向量索引、图数据库式关系索引或等价本地索引，支持大项目增量更新、分页和后台重建。
6. 通过统一 `AIService` 接入生成、验证、检测、嵌入、图片、视频、TTS；供应商用途由用户可读名称说明，支持多个供应商并行启用。
7. MCP 只暴露经过权限和项目隔离的工具，例如查询记忆、读取来源、生成素材包、提交审核；所有写入仍经应用层命令和审计。
8. 动态 Agent 支持任务队列、断点、重试、取消、并发上限和可视化进度，不允许后台无限重试造成请求风暴。

#### 第三版硬验收门

- 从已确认正文一键生成素材包，所有素材能回溯至记忆事实和正文来源。
- 素材包导出后可被至少一种外部工具按文档格式消费；导入后不破坏小说和记忆数据。
- 生成/验证/嵌入/媒体供应商可同时工作，失败供应商不会让其他任务使用错误默认模型。
- MCP/Agent 的每个工具调用都能看到参数、结果、错误、重试和项目范围。

## 5. 执行顺序建议

不要从可视化增强或动画出口开始。正确顺序是：

```text
第一版 A 来源版本
  -> 第一版 B 抽取证据
  -> 第一版 C 合并审核
  -> 第一版 D 持久化并发/UI
  -> 第一版硬验收
  -> 第二版 记忆线/影响传播
  -> 第二版检索和图谱升级
  -> 第二版硬验收
  -> 第三版动画/短剧素材板块
  -> MCP/Agent/向量索引
  -> 第三版硬验收
```

这不是把所有工作批量修改；每个阶段应拆成可独立回归的任务。每个任务必须绑定：影响文件、输入输出契约、错误路径、状态变化、持久化字段、真实行为验证和回滚方式。

## 6. 修复前必须采用的验证矩阵

每个实施任务都必须产生以下证据，不能只给“构建成功”：

| 验证层 | 必须证明的内容 | 证据形式 |
|---|---|---|
| 静态链路 | UI 事件确实连到服务、Store、持久化和下游 | 文件、函数、调用关系、字段读写 |
| 单元契约 | 解析、证据校验、合并、迁移、检索边界正确 | 测试原始输出和失败样本 |
| 组合链路 | 正文保存→抽取→审核→提交→视图更新→保存 | 自动化操作日志、状态前后对照 |
| 错误路径 | 超时、断网、非法 JSON、取消、重复提交不丢正文 | 错误日志、恢复后状态、重试次数 |
| 持久化 | 同项目关闭重开后数据和历史一致 | 文件快照 before/after、重启后读取结果 |
| 隔离 | 切换项目、并发请求不串写 | 两个项目的独立 ID、请求和文件对照 |
| 视觉交互 | 五视图真实数据显示、筛选、来源跳转、编辑、删除 | 真实鼠标/键盘操作、截图、DOM 状态和应用日志 |
| 大数据 | 长文本、多章、多事实、长历史不失控 | 同环境基准时间、内存、文件大小和结果正确性 |
| 下游 | 生成流水线、聊天、动画/短剧读取正确事实 | 捕获请求体、素材包内容和来源 ID |
