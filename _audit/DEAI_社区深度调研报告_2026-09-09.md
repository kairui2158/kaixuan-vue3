> 调研日期：2026-09-09  
> 调研对象：315 个候选仓库（12 组关键词），浅读后深读 8 个代表项目  
> 结论性质：调研报告，不执行改造  
> 项目经验依据：`_audit/神意开发经验总结_v3.md`

## 一、调研方法与过程记录

本次调研参照 `D:/codex/玄武规划SKILL/调研/2026-09-09_社区深度调研日志.md` 的方法执行，避免“高星项目充数”，按五轮推进：

1. **候选池扩展**：用 12 组关键词在 GitHub 检索，合并 315 个唯一仓库，保留原始 JSON 缓存，按主题相关度、维护状态、是否含真实实现三轴初筛。
2. **浅读筛除**：对候选池做 README 与目录结构浅读，筛掉纯榜单、纯营销页、无实现仓库。
3. **源文件取证**：浅克隆 8 个仓库到本地临时目录，逐行读取核心脚本与参考文档，只记录能给出 `file:line` 证据的结论。
4. **本项目对照**：回到本仓库，对照硬规则注入点、后处理调用点、完整性保护门，逐项标出社区有而我们没有的机制。
5. **汇总报告**：形成本报告，先判断现有方案是否安全，再给出分层目标架构与优先级排序。

## 二、深读项目与关键证据

### 1. qu-ai-wei（542 stars）

**定位**：完整改写工作流，不是替换表。

关键证据：
- `SKILL.md:9`：把 AI 高频症状当“编辑信号”，不当作作者身份鉴定；必要时重建句子、段落、全文信息架构，“不用局部换词假装完成改写”。
- `SKILL.md:15-66`：定义仲裁顺序，处理冲突时先事实、后语体；要求先建立全文“信息账本”，记录人物、事实、数字、时间、地点、动作、引语、归因、评价、排除项、限定、来源和术语。
- `SKILL.md:117`：改写后逐项回对信息账本和论证图。
- `references/pattern-catalog.md:47`：所有归因和全称判断必须能回指信息账本。

**对我们的启发**：它的核心不是“禁词”，而是把降AI当成一次有证据链的编辑任务。我们目前没有信息账本机制，也没有改写后的事实回对。

### 2. shuorenhua（1497 stars）

**定位**：最值得对标的结构安全工程。

关键证据：
- `automation/eval/hard_metrics.py:49-51`：字数留存率目标 >= 0.90，硬下限 0.85，超限才报警或判死。
- `automation/eval/hard_metrics.py:13`：protected spans 粗核“只报警不判死”，因为粗核是正则匹配，缺失留给 judge 复核。
- `automation/eval/hard_metrics.py:711-712`：报告格式强制输出 `protected spans 粗核：hit/total 保留`。
- `automation/eval/hard_metrics.py:769-777`：留存率 fail/warn 分层统计，protected spans 缺失单独列报警，不与主指标混算。

**对我们的启发**：我们已实现的 `passesBodyIntegrityCheck` 与它的留存率门禁同源，方向正确；但我们缺少 protected spans 机制，没有“必保片段预扫 + 改后回对”。

### 3. oh-story-claudecode（6691 stars）

**定位**：本次调研中参考价值最高的工程实践，脚本层“只检测、不自动改写”。

关键证据：
- `skills/story-deslop/scripts/check-ai-patterns.js:35-36`：所有 finding 分 `blocking` 与 `advisory` 两档；blocking 才用于生成/清理门禁，advisory 只提示可保留。
- `skills/story-deslop/scripts/check-ai-patterns.js:39`：“The script reports findings only. It never rewrites text.” 脚本只报告，绝不改写文本。
- `skills/story-deslop/scripts/check-ai-patterns.js:193`：blocking 规则要求真人语料命中约等于 0 才能上线（每 20 章不超过 1 处，且需人工确认）。
- `skills/story-deslop/scripts/check-ai-patterns.js:81`：密度规则用“次数 + 每千字”双门槛，`STOCK_REACTION_PER_KILO = 1.5`。
- `skills/story-deslop/scripts/check-degeneration.js`：同样只报告模型退化指纹（复读、截断、元信息泄漏、工程词泄漏），安全响应是“带反馈重生成 + 重试上限”。
- `skills/story-deslop/scripts/style-whitelist.js`：书级 `.deslop-whitelist`，字面量匹配，不跨书继承，避免把角色口头禅误杀。
- `demo/style-precedence-eval/RESULTS.md`：14 次真实执行，基线/候选对照、失败样本全部保留，形成可复验的评测链。

**对我们的启发**：这是本次调研里最明确的架构信号——成熟项目的“脚本层”不承担改写，改写交给模型层和用户确认。我们当前的后处理是“字符级直接替换”，属于较弱的一档。

### 4. Moonlit-Pages AIGC-Detector-Rewriter（445 stars）

**定位**：实测教训库，最反对“越改越顺”。

关键证据：
- `references/rewrite_methods.md:3-7`：总规则是“minimal edit, never regenerate, never shrink”；实测把重写强度提高、把段落重生成得更流畅，会让外部 AI 检测分数更差。
- `references/rewrite_methods.md:29`：禁止回译。回译是整段重生成的一种，会摧毁原有措辞并输出新的机器分布，正是导致“一章从 36% 改到 100%”的失败模式。
- `references/chinese_text_ai_risk.md:5`：高风险词表是“hint list, not ban list”；语义准确性和术语保护永远优先于替换。
- `references/chinese_text_ai_risk.md:54`：回读检查必须确认“未重排整段、未压缩”。

**对我们的启发**：我们的 `CLICHES_BODY_SAFE` 现在就是静态替换表。它已经比旧的 `process()` 安全得多，但仍缺少“最小编辑”原则下的语义级改写，也没有“术语/事实保护优先于替换”的排序。

### 5. OUBIGFA good-writing（767 stars）

**定位**：把“审阅”和“改写”拆成两种操作合同。

关键证据：
- `SKILL.md:39-49`：定义写作、审阅、修补、重写四种模式；审阅模式只诊断不动稿。
- `SKILL.md:49`：“没有缺陷清单直接改写，AI 痕迹会更显眼。”
- `references/ai-trace-index.md:14-26`：先清单后动手、最小改写、阈值是识别强度而不是删除配额、改动后必须做回滚检查。

**对我们的启发**：我们现在的“去AI”是单一动作，没有“诊断报告”和“最小修补”的分离。用户无法先看问题清单再决定改不改。

### 6. speak-human-tw（951 stars）

**定位**：价值排序与保护对象清单。

关键证据：
- `references/humanize.md:104-108`：判断顺位是事实正确 > 信息完整 > 去 AI 痕迹 > 人味；“人味永远排最后，一句有观点但改坏事实的句子，比一句无聊但正确的句子更糟”。
- `references/humanize.md:89`：不要表演不确定，不要替作者发明经历；作者没说过的转折，改写时不准造。
- `references/humanize.md:92`：“人味是作者的，不是你的。”
- `references/protected-list.md:64-65`：口语碎片、不完整句是“人味本体，是要保护的方向，一个字都不动”。

**对我们的启发**：这个项目最像小说场景。它明确反对为了像人而破坏事实，也反对把口语碎片当成要清理的杂质。我们当前规则没有对这类“反向保护”做显式声明。

## 四、核心结论

### 结论一：双层方向不是错路，但后处理的定位错了

“前置方法论 + 后置安全网”这个方向被社区验证，不是问题。问题在于我们的后处理目前承担了“改写”职责，而成熟项目的脚本层几乎只承担“检测、报告、门禁”职责，改写交给模型层和用户确认。

当前我们的架构是：

```text
前置方法论注入（已有）
    ↓
模型生成
    ↓
字符级替换（CLICHES_BODY_SAFE + CONNECTOR_REPLACE）
    ↓
完整性回滚门（已有）
```

社区成熟架构是：

```text
前置方法论注入（已有）
    ↓
保护片段预扫（缺：人名、设定、伏笔、白名单）
    ↓
模型生成
    ↓
检测报告 + blocking/advisory 分档（缺）
    ↓
模型级最小编辑改写 + 用户确认（缺）
    ↓
硬指标门禁（部分有：留存率/完整性已有，密度阈值未接入）
```

### 结论二：现在的方案是安全过渡态，不是终态

直接回答用户的问题：**硬规则的前后处理不是最优解，但也不是错误方案，而是社区验证过的正确过渡层。**

当前这套方案的价值判断：

- **安全性**：合格。`processBody()` 白名单 + `passesBodyIntegrityCheck()` 回滚门，能在现有规则出问题时保住原文结构，这正是此前正文被打碎问题后的正确止血。
- **效果上限**：有限。字符级替换能解决“显性套话”，不能解决句长方差、信息密度、节奏分布、视角一致性这些统计层问题。社区已有明确共识：“局部换词假装完成改写”不是有效方案。

### 结论三：最优解的四个关键机制

1. **脚本层降权为检测器**  
   把“自动替换”降级为“检测报告 + 建议”，报告包含 blocking 与 advisory 两档。脚本不再直接改写正文，只输出问题清单和位置。

2. **保护片段前置**  
   在生成和改写前，先扫出人名、地点、时间、等级体系、金手指设定、伏笔、书级白名单，形成 protected spans。改写后逐项回对，缺失即回滚或报警。

3. **改写交给模型层，但必须是最小编辑**  
   不是“重新生成一遍”，也不是字符级替换，而是模型在原句上做最小修补，遵循“事实正确 > 信息完整 > 去AI痕迹 > 人味”的顺位，禁止整段重生成和回译。

4. **硬指标门禁 + 评测基线**  
   保留并增强 `passesBodyIntegrityCheck()`，新增密度阈值（次数 + 每千字）、句长方差、连词密度等指标，并建立基线/候选对照评测，失败样本保留。

## 五、优先级建议

### P0：检测报告模式

把 `processBody()` 的自动替换路径改为可选，新增“检测报告优先”模式：先生成问题清单（blocking/advisory），用户确认后再进入改写。这一步不推翻现有安全层，只在旁边加一条更成熟的链路。

### P1：protected spans

生成前先预扫人名、设定、伏笔、白名单，改写后逐项回对，有缺失直接回滚或报警。对小说正文来说，这比再多替换表更能防止灾难性事故。

### P1：密度阈值脚本化

把 `DEAI_METHODOLOGY_PROMPT` 第 15 条的密度原则落到脚本层，实现“次数 + 每千字”双门槛，作为检测报告的一部分输出，而不是只停留在提示词。

### P2：评测基线

建立一组真实正文测试集，做基线/候选对照评测，每次改规则都要跑一遍，失败样本保留。这是防止“下一次又打碎正文”的制度性保障，也是社区项目共同的做法。

## 六、风险与边界

1. **不要为了检测分数牺牲事实**：speak-human-tw 的价值排序是最强约束，事实正确永远高于信息完整、去AI痕迹、人味。
2. **不要把人味机械化**：不要机械撒“其实”“就是”，不要替作者发明经历，不要表演不确定。人味来自作者原有的口语碎片和不完整句，不是改写时加进去的。
3. **不要回退到整段重生成**：Moonlit-Pages 的实测数据已经证明，把段落重写得更流畅会让 AI 检测分数更差，一章从 36% 改到 100%。
4. **保留现有安全层**：`passesBodyIntegrityCheck()` 和对话保护已经能防住最坏情况，任何后续改造都不能绕过这两层。

## 七、附带发现

`src/services/de-ai.js:164` 的 `CLICHES_BODY_SAFE` 中存在一条无效规则：`极大的 → 极大的`。这条规则不会造成正文损坏，但会虚增替换计数并污染观测数据，后续清理规则表时应删除。
