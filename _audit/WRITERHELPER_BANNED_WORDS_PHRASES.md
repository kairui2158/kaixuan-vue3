## 六、移植建议

### 可直接移植

1. 255 条禁用词可作为独立数组注入到 DeAi 系统的检测/替换层
2. 34 条禁用句式可作为独立的句式规则数组，补充当前完全缺失的句式级检测
3. description 分类字段可保留，用于 UI 中按分类显示和开关

### 需要适配

1. 当前 DeAiProcessor 的 CLICHES 使用正则替换 (pattern + replace)，WriterHelper 的禁用词是纯文本匹配
2. 需要决定：禁用词是直接删除还是替换为替代词还是标记检测
3. 禁用句式需要转换为正则模式匹配，因为 ... 表示的是中间可变内容
4. 153 条无分类的禁用词需要人工补充分类，或统一归为通用 AI 味分类

### 移植后的架构位置

```
DeAiProcessor (src/services/de-ai.js)
  |- CLICHES (60+ 条正则替换)         <- 保留，处理替换类规则
  |- BANNED_VOCAB (255 条纯文本禁用词)  <- 新增，处理删除类规则
  |- BANNED_PHRASE (34 条句式禁用)     <- 新增，处理句式检测类规则
  |- CONNECTOR_REPLACE (10+ 条)        <- 保留
  |- AI_FREQ_WORDS (27 个检测词)       <- 保留
  |- DI_EXCEPTIONS (200+ 排除词)       <- 保留
  |- SUMMARY_PATTERNS (总结句删除)     <- 保留，与 BANNED_PHRASE 部分重叠
  |- 20 条处理动作规则                  <- 保留
```

## 七、结论

WriterHelper 的禁用词和禁用句式是纯数据层的积累，不涉及架构改造。我们的 DeAi 系统架构比 WriterHelper 更深 (20 条处理动作 vs 纯词表)，但在词库量级上确实有差距 (60+ vs 255 条)。

移植这 255 条禁用词和 34 条禁用句式是数据层操作，可以在现有 DeAiProcessor 框架内直接扩展，不需要修改执行逻辑或架构。

但根据已有的 DEAI_SYSTEM_FULL_EXTRACTION.md 分析，正确的操作顺序应该是：先验证现有链路能跑通，再扩词库，再补句式，而不是直接移植。
