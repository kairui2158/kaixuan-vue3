# 组件存在必要性与生命周期收敛方案

> 日期：2026-10-05  
> 触发背景：预览状态机被删除后，确认“组件单看合法、组合后互相干扰”是系统性盲区。本方案把审计标准从“是否有 bug”升级为“是否仍有存在必要”，对每个可疑组件做保留、修复、迁移、下架、删除的明确裁决。  
> 结论级别：成熟，可执行。执行中不允许用预算、时间、轮次作为停止条件。

## 1. 判断框架

一个组件不能只因为它“能跑”就保留，也不能只因为它“出过 bug”就删除。本方案用五个问题裁决：

1. **用户入口**：是否仍有真实用户可见入口，或仅剩内部兼容？
2. **不可替代价值**：它的能力是否已被新链路完整替代？
3. **架构一致性**：它是否仍符合当前“统一 Agent + 统一工具面 + 单源权限”的路线？
4. **组合风险**：它和其它组件组合时是否产生伪状态、孤儿请求、旧语义回流？
5. **修复成本与删除收益**：修复它是在补产品能力，还是在给过时路线续命？

裁决类别：

| 类别 | 含义 | 执行纪律 |
|---|---|---|
| 保留修复 | 有真实价值，缺陷可修 | 修复后必须补组合级测试 |
| 收敛迁移 | 有价值但实现位置过时 | 先建新单源，再迁移消费方，最后删旧实现 |
| 先下架再修复 | 价值存在但当前实现会撒谎 | 生产工具面先移除，修复并通过验收后再恢复 |
| 隐藏观察 | 用户价值不确定 | 默认隐藏，保留实现一个观察期 |
| 删除 | 无不可替代价值或只剩历史兼容 | 引用闭包清零后删除，不留兼容壳 |

## 3. 详细裁决与理由

### 3.1 编辑器写入跟随：保留修复

**为什么保留**  
这是 API 直写“用户可感知”的核心能力：写入时定位光标、滚动到插入点、高亮当前写入区。它不是装饰组件，而是直写系统可信度的一部分。

**为什么不删**  
删除它会让 API 写入退回“用户不知道写到哪”的体验，违背当前产品目标。

**修复内容**

1. `editorViewport.ts` 增加程序滚动标记：`followWriteProgress()`、`revealTarget()` 设置 `scrollTop` 前标记 `programmaticScroll = true`。
2. `onUserScroll()` 只在非程序滚动时调用 `pauseFollowTemporarily()`。
3. 程序滚动仍必须触发 `scrollListeners`，保证搜索高亮重绘不受影响。
4. 用户真实滚动、键盘、指针操作继续暂停跟随。

**验收标准**

- 连续两次写入间隔小于 2.5 秒，两次都跟随滚动。
- 用户手动滚动后，跟随暂停 2.5 秒。
- 程序滚动后搜索高亮仍重绘。
- Electron 实测覆盖：写入跟随、用户接管、搜索高亮、停止跟随四条路径。

### 3.2 子 Agent 三工具：先下架再修复

**为什么不能直接保留**  
当前实现的单个组件都合法：`spawn` 入队、`wait` 有超时、`cancel` 改状态。但组合后它会撒谎：

- `wait` 超时把 record 标为 `failed/sub_agent_timeout`，真实 API 请求继续跑。
- `cancel` 把 record 标为 `canceled`，真实请求同样继续跑。
- 主循环结束后，队列里的任务可能继续消耗请求并写旧 trace。

这不是普通 bug，而是“工具向模型承诺了控制权，但执行层没有控制权”。在修复前继续暴露，等于把伪状态卖给模型。

**为什么不能直接删除**  
内置 Agent 的子任务能力是当前架构路线的一部分，删除会把 Agent 降级成单轮执行器。问题不是能力不该存在，而是生命周期没做完。

**执行方式**

1. **Phase 1 生产下架**：`agentOrchestrator` 不再把 `agent.spawn/wait/cancel` 加入工具面。UI 不展示，模型不可调用。
2. **Phase 2 生命周期补全**：
   - `runSubAgent` 返回 `{ result, cancel }` 或等价取消句柄。
   - `wait` 超时与 `cancel` 必须触发真实取消信号。
   - 主循环终态时强制处理队列：等待完成、取消或标记孤儿，不允许静默遗留。
   - trace 记录 `requested/canceled/observed` 三个状态，禁止只写管理器状态。
3. **Phase 3 恢复上架**：通过单测、Electron、真实 API 三层验证后再加入工具面。

**验收标准**

- `agent.cancel` 后，真实请求进入取消路径，trace 中有取消证据。
- `agent.wait` 超时后，不再有新物理请求与旧 run 事件。
- 主 Agent 终态后，子 Agent 队列为空或全部进入显式终态。
- 恢复上架前，工具面中不出现这三个工具名。

### 3.3 `useAiTools`：拆分处理，不整体续命

`useAiTools` 有两类完全不同的消费方，不能一刀切。

#### 3.3.1 生成流水线旧 AI 工具栏：隐藏后删除

**现状**  
`PipelinePanel.vue:52-59` 暴露 8 个按钮：写作规则、时间线、批量审阅、章节修订、翻译、风格转换、重新生成、按指令修改。它们走 `useAiTools.callAi()`，固定 prompt，只把文本显示在结果区，不进入统一 Agent、不进入编辑器写入链路、不使用统一权限面。

**判断**  
这 8 个按钮是旧架构遗留的“演示型工具”，与当前 API 对话 + 直写体系重复，而且继续维持一条独立 AI 调用路径。保留它们的价值低于统一架构收益。

**执行**

1. 本版本先隐藏按钮，不删实现，便于回滚。
2. 一个版本后若无用户反馈依赖，删除按钮、`toolAction()` 分支和 `useAiTools` 中对应函数。
3. 保留“AI起名”等非 `useAiTools` 功能，不误伤。

#### 3.3.2 大纲自动拆解：迁移后保留

**现状**  
`OutlineWorkspace.vue:3864/3881` 用 `useAiTools.callAi()` 做设定拆解和伏笔提取。这是有明确产品价值的一键功能，不应删除。

**执行**

1. 先修复 `useAiTools.callAi()` 的结果覆盖问题：只要任一轮成功，返回最后一个非空结果，不允许空尾轮覆盖成功结果。
2. 将这两个调用迁移到统一 AI 调用封装，复用 trace、预算、供应商、Agent 参数。
3. 迁移完成并验证后，删除 `useAiTools` 旧实现。

**验收标准**

- 技能链中间成功、尾部为空时，自动拆解仍返回有效结果。
- trace 记录每一步真实请求与响应。
- 迁移后大纲自动拆解行为与迁移前一致或更好。
- `useAiTools` 删除后，生产源码引用为 0。

### 3.4 去AI味：保留修复

**为什么保留**  
去AI味是完整产品功能，有设置页、技能选择、进度 UI、编辑器入口，不是残留组件。

**修复内容**

1. 三处 `createApiCallBudget(8)` 改为统一预算来源。
2. 长文本处理提供续命入口，至少支持用户点击继续。
3. trace 中记录预算状态与续命动作。

**验收标准**

- 三条 DeAi 处理链预算来源一致。
- 预算耗尽时用户可见原因，并可通过续命继续。
- 不改变去AI味的处理结果语义。

### 3.5 `timeoutHint`：接线，失败则删除

**现状**  
能力存在但无生产调用方，属于死观测能力。

**判断**  
长文档任务确实需要状态级超时提示，不能只靠全局默认值。因此首选接线，而不是删除。

**执行**

1. 主页与大纲 runtime 创建时传入 `timeoutHint`。
2. 长文档模式使用独立超时提示，不沿用普通对话默认值。
3. trace 与 watchdog 消费同一份 hint。
4. 若接线后无实际收益或造成误报，则删除字段，不允许继续保留死能力。

**验收标准**

- 长文档 run 的 trace 导出中能看到 hint。
- watchdog 使用 hint 而不是默认值。
- 普通对话行为不变。

### 3.6 `awaiting_confirmation`：源头归一

**现状**  
生产链仍产出旧状态名，再由 `stateTransitionGuard` 归一化成 `awaiting_user`。

**执行**

1. `workspaceSkillEngine` 直接产出 `awaiting_user`。
2. `ChatPanel`、`OutlineWorkspace` 消费新状态名。
3. 旧状态名只保留在历史 trace 导入兼容层。
4. 生产源码中 `awaiting_confirmation` 命中为 0。

**验收标准**

- 新 run 不再出现旧状态名。
- 旧 trace 导入仍能正常归一。
- 状态时间线可区分“等待用户”来源。

### 3.7 物理请求上限：保留并统一

**澄清**  
`maxPhysicalRequests` 不是模型 token 预算，而是 Agent 循环失控保护。它防止模型无限循环调用工具。因此不能按“不设 token 上限”的要求删除。

**问题**  
大纲传了，主页和子 Agent 没传，导致同一保护语义分裂。

**执行**

1. 新建统一 runtime 构建器，主页、大纲、子 Agent 共用。
2. `maxPhysicalRequests` 在构建器内单源计算并透传。
3. 达到上限时作为“继续检查点”，不是静默失败；UI 给出继续选项。

**验收标准**

- 主页、大纲、子 Agent 的 runtime 快照一致显示上限来源。
- 触发上限后，用户可明确选择继续或停止。
- 不再出现入口间默认值分叉。

## 4. 执行阶段

### Phase 0：基线锁定

1. 记录当前工具面、trace 字段、UI 入口清单。
2. 跑现有相关测试，形成 before 证据。
3. 确认无未提交无关改动混入。

### Phase 1：止血修复

1. 编辑器程序滚动标记。
2. `useAiTools.callAi()` 结果覆盖修复。
3. 子 Agent 三工具从生产工具面下架。
4. 主页 / 大纲 / 子 Agent runtime 参数统一。

### Phase 2：生命周期补全

1. 子 Agent 取消传播与队列收口。
2. `timeoutHint` 生产接线。
3. DeAi 预算续命。
4. `awaiting_confirmation` 源头归一。

### Phase 3：旧链路退役

1. 隐藏生成流水线旧 AI 工具栏。
2. 大纲自动拆解迁移到统一调用封装。
3. 删除 `useAiTools`。
4. 清理旧测试、旧脚本、旧规格引用。

### Phase 4：验证与收尾

1. 单测：组件行为 + 组合行为。
2. 集成：runtime 参数一致性、trace 对账。
3. Electron UI：真实点击路径覆盖写入跟随、旧工具栏隐藏、自动拆解、去AI味。
4. 真实 API：至少覆盖主页与大纲各一条长文档路径。
5. 回头看：生产引用、测试、脚本、规格、trace、构建产物七层对账。

## 5. 风险与反制

| 风险 | 影响 | 反制 |
|---|---|---|
| 下架子 Agent 工具后模型能力下降 | 中 | 先下架伪控制工具，主 Agent 单循环能力不变；生命周期补全后恢复 |
| 删除旧工具栏影响少数用户习惯 | 中 | 先隐藏一个版本，保留回滚窗口 |
| 自动拆解迁移引入行为差异 | 高 | 迁移前后同输入对比，结果不允许劣化 |
| runtime 统一改动范围扩大 | 高 | 只抽参数构建单源，不重写执行器 |
| 状态名清理破坏旧 trace | 高 | 兼容层保留旧名归一，只清生产输出 |

## 6. 成熟度结论

| 维度 | 结论 |
|---|---|
| 执行器 / 工具层 | 成熟：每个裁决都有明确工具面与生命周期动作 |
| 应用方案 / 交互闭环 | 成熟：用户可见行为、trace、回滚窗口均已覆盖 |
| 实现接线 | 成熟：改动点均定位到生产文件与调用链 |
| 验证标准 | 成熟：单测、集成、Electron、真实 API、七层回头看齐备 |

**禁止事项**

1. 禁止为了减少改动而保留伪状态组件。
2. 禁止用“以后再修”保留死能力。
3. 禁止删除有真实用户入口的功能而不提供替代或回滚窗口。
4. 禁止用 mock 冒充真实 UI 验证。
