# 大纲工作台双向写入能力社区深度调研报告（问题二）

日期：2026-09-10

调研目标：解决客户问题二——大纲工作台 API 对话框需要稳定的双向能力：既能读编辑器，也能写入编辑器；客户反馈“AI 不能写入编辑器，需要多轮问话才知道插入点，还要自己手动”。  
关联报告：`_audit/OUTLINE_COCREATION_COMMUNITY_RESEARCH_2026-09-10.md`（问题一：几十万字大纲的读取覆盖）。上一份报告只把写入作为 P2 提了一层，本报告是问题二的独立深度调研。  
证据缓存：`_audit/research-cache/outline-write-2026-09-10/`，与问题一缓存目录分离。  
范围声明：本报告只做调研、现状核查与判断，不包含执行方案，不修改业务代码。  
执行依据：`_audit/神意开发经验总结_v3.md`（先读再改、M1 影响圈、file:line 证据、验证纪律）。

## 结论摘要

1. **我们不是“没有写入能力”，而是“有提案式骨架，没有成熟编辑协议”。** 应用已经有写入协议、批次规划、部分接受、hash 校验和批次回滚，这些方向与社区成熟系统一致，应保留并强化。
2. **客户感知到的“不能写 / 不稳定 / 插入点难找”，是六个具体缺陷叠加的结果**，不是单一 bug：定位过弱、写入工具不做定位校验、SKILL chain 路径完全无工具、编辑器全文硬塞 prompt、失败无修正闭环、审批窗口缺 diff 导航与影响分析。
3. **社区共识非常一致：没有任何成熟系统让模型直写编辑器。** 成熟方案全部是“读取与定位 → 提案暂存 → diff 预览 → 用户审批 → 应用 → 校验与回滚”的闭环。我们已走到这条路的入口，但每一段都只有薄薄一层。
4. **最接近问题二完整答案的是 Roo-Code 与 SWE-agent 的组合。** Roo 的 middle-out 模糊定位、失败诊断与多块部分失败；SWE-agent 的唯一性硬校验、编辑后 lint 反馈与文件历史回退；Goose 的会话级确认状态机；OpenHands 的可视化编辑卡与自动刷新；Continue 的多匹配拒绝、缩进保持与反序替换。
5. **问题二不能在“写入层”单独解决。** 当前协议把编辑器全文塞进 prompt（`editorEditProtocol.ts:186`），外层又在 12,000 字处截断（`conversationContextService.ts:285`）。也就是说，问题一的读取基础设施是问题二写入的地基：模型看不全大纲，就永远给不准插入点。
6. **判断：问题二是产品级能力缺口，不是模型能力问题。** 换更聪明的模型只会降低失败率，不会补齐定位协议、审批体验、失败反馈和回滚体验。

## 调研方法

本次沿用前几轮的五轮调研法，并按用户要求避免“只扫几个高星项目就交差”：

1. **候选池**：以 coding agent 的编辑协议为主轴（它们对“受控写入”研究最深），再对照写作域 jarvis-write / NovelClaw 的讨论蒸馏与记忆写入。所有项目均真实存在于 GitHub，证据文件已下载到本地缓存。
2. **深读源码**：每个结论都对应本地缓存文件的行号，不引用 README 宣传语。
3. **对照本应用**：逐段核查 `editorEditProtocol.ts`、`editorEditService.ts`、`editorTools.ts`、`editorEditBatch.ts`、`editorBatchRecord.ts`、`OutlineWorkspace.vue`、`ChatPanel.vue`、`workspaceSkillEngine.ts`、`aiService.ts`。
4. **缺口归纳**：按社区成熟写入协议的七个必备环节逐项对照：定位、结构锚点、提案、审批、应用、校验、回滚。
5. **风险边界**：明确哪些能力必须保留（提案式写入、用户确认、hash 校验、批次回滚），哪些属于可选增强。

## 深读项目与证据

### 1. Roo-Code：目前最接近“成熟定位协议”的参照

核心文件：`roo-src-core-diff-strategies-multi-search-replace.ts`

- **匹配分级**：先精确匹配，失败后从中心向外的 middle-out 模糊搜索，再失败才进入 aggressive 剥离匹配（`:385-424`）。
- **相似度阈值**：默认 1.0 即精确匹配，可配置；这是“默认严格、按需放宽”的正确方向（`:76-87`）。
- **失败即诊断**：匹配失败时返回相似度得分、所需阈值、搜索范围、已尝试的匹配策略、原始搜索块与最佳候选块，并明确提示“先重新读取文件再重试”（`:449-456`）。
- **缩进保持**：匹配成功后按目标文件的相对缩进调整替换块，避免替换文本破坏排版结构（`:465-505`）。
- **多块部分失败**：一个 diff 里的多个 SEARCH/REPLACE 块可以部分成功、部分失败，失败块通过 `failParts` 返回（`:513-519`）；UI 显示 `成功数/总数`（`:534-537`）。

辅助证据：

- `roo-src-core-checkpoints-index.ts`：影子 git 检查点，每次任务动作保存快照，可按 hash 恢复（`:211-261`）。
- `roo-src-core-tools-EditTool.ts`：编辑前生成 sanitized diff 并计算 diff stats，写入走 diff 视图审批；用户拒绝时显式 revert（`:153-235`）。
- `roo-webview-ui-src-components-chat-BatchDiffApproval.tsx`：审批 UI 直接渲染后端生成的 unified diff 与增删统计（`:39-50`）。

对我们的启示：**写入失败不是错误，是可以交给模型自我修正的诊断信息。** 我们现在的 `target_not_found` 只有一句话，模型拿不到候选位置和上下文，只能靠用户重新解释。

### 2. SWE-agent：唯一性硬校验 + 编辑后校验 + 历史回退

核心文件：`sweagent-tools-edit_anthropic-bin-str_replace_editor`

- **唯一性硬校验**：`str_replace` 前统计出现次数；0 次直接失败，多次则列出所有命中行号并拒绝执行（`:516-534`）。
- **无变化拒绝**：`new_str == old_str` 时直接拒绝，避免制造空编辑（`:536-538`）。
- **编辑前/后 lint**：写入前取基线诊断，写入后再跑诊断；只保留与替换窗口相关、且是新引入的问题，避免旧问题污染反馈（`:540-574`）。
- **文件历史回退**：每次写入前把旧内容存入 file history，`undo_edit` 弹出上一版恢复（`:576-577`，`:634-643`）。
- **读取范围与结构边界**：`view` 支持 `view_range`，长文件强制先看结构；viewport 自动扩展到函数/类边界，避免模型只看到半截结构就动手（`:438-507`）。

对我们的启示：**“多次命中必须拒绝”应该成为大纲写入协议的铁律**；写作域还需要一个类似 lint 的“编辑后结构校验”：卷/章层级是否破坏、字数量级是否异常、相邻段落是否断裂。

### 3. Continue：多匹配拒绝、缩进保持与反序替换

核心文件：

- `continue-core-edit-searchAndReplace-performReplace.ts`
- `continue-core-edit-searchAndReplace-multiEditValidation.ts`

关键证据：

- **多匹配拒绝**：默认单替换时发现多个匹配直接失败，并明确给出两条出路——扩大上下文使其唯一，或显式 `replace_all`（`performReplace.ts:119-128`）。
- **缩进相对调整**：模糊匹配命中后，按匹配区域的缩入重新计算 `newString`，避免 LLM 给出的缩进破坏文件结构（`:37-70`）。
- **反序应用**：批量替换按位置倒序执行，保证前面的编辑不改变后面的偏移（`:102-116`）。
- **多编辑校验**：multiEdit 先整体校验每条 old/new/replace_all，再执行，禁止部分格式错误进入应用阶段（`multiEditValidation.ts:11-42`）。

对我们的启示：大纲虽然没有代码缩进，但有等价结构——标题层级、卷章缩进、空行节奏。我们的 `planEditorEditBatch` 已经在 working 内容上逐条规划（等价于顺序应用，偏移正确，`editorEditBatch.ts:49-67`），这一点不弱；缺的是多匹配拒绝与格式结构保持。

### 4. Goose：会话级确认状态机

核心文件：`goose-crates-goose-src-agents-tool_confirmation_coordinator.rs`

- 确认请求按 session 管理，HashMap 记录 `request_id -> Option<Answer>`，`None` 表示未答（`:17-31`）。
- 提交答案用互斥锁串行化，并发提交只有一个能生效（`:19-20`）。
- **首个答案不可变**：已回答的请求再次提交会报错，防止用户双击或多个 UI 重复提交造成状态翻转（`:73-83`）。
- **批量确认等待**：一次 turn 中的多个确认请求必须全部有答案才继续（`:87-104`）。
- **turn 结束清理**：活动回复流结束时清空 pending 确认，避免上一个 turn 的悬空确认污染下一轮（`:120-124`）。

对我们的启示：我们已有 pending batch 暂存和 show-diff 审批窗口，但没有明确的“会话级确认状态机”。切换标签页、生成新回复、连续发起第二次写入时，pending 批次的失效/覆盖/保留规则需要显式定义，否则会出现用户确认的是旧版本内容的暗坑。

### 5. OpenHands：编辑过程的可视化与状态同步

核心文件：

- `openhands-src-components-features-chat-tool-visualizers-file-editor-file-editor.tsx`
- `openhands-src-hooks-use-auto-refresh-files-on-edit.ts`

关键证据：

- **工具卡可视化**：`str_replace` / `insert` 在等待确认时渲染 action diff 卡；完成后渲染 before/after 全量 diff；错误单独渲染消息卡（`file-editor.tsx:2-7`，`:130-148`）。
- **空字符串也是合法 diff 边**：插入到空文件或清空内容时仍显示 diff，而不是跳过渲染（`:105-106`）。这在对写作用户展示“删除/替换”时尤其重要。
- **编辑后自动刷新**：文件列表、内容视图、diff 视图在收到编辑事件后自动同步，不需要用户手动刷新（`use-auto-refresh-files-on-edit.ts:53-58`，`:130-136`）。

对我们的启示：客户“看不懂插入点在哪”的另一半原因是视觉呈现。现在的 show-diff 窗口有审批骨架，但没有做到“每个编辑动作一张卡、卡片即 diff、点击卡跳到原文位置、接受后编辑器即时滚动同步”。

### 6. Aider / Cline / jarvis-write（复用问题一证据）

- **Aider**：SEARCH/REPLACE 失败后把相似行与失败原因回传给模型，让模型只重发失败块；这是“失败反馈闭环”的经典实现（`outline-co-creation-2026-09-10/aider-editblock_coder.py:82-124`）。
- **Cline**：编辑不可自动重试（`retryable: false`），防止状态化编辑重复应用；读取支持行范围分页，避免模型拿半截上下文动手。
- **jarvis-write**：写作域最接近客户诉求的形态——多轮讨论后独立蒸馏结构化提案，用户确认后版本化落库；影响分析只分析不执行。这正对应客户“聊完以后自动放到正确位置”的期望：不是聊完直接写，而是聊完产出提案。

## 本应用现状核查

### 已经做对的部分

1. **提案式写入，不直写编辑器**：`editor.propose_edits` 只返回 `pending_user_confirmation`，不触碰正文（`src/services/editorTools.ts:236-296`）。
2. **原子批次规划**：`planEditorEditBatch` 在 working 内容上逐条执行，后面的编辑基于前面的结果计算偏移（`src/services/editorEditBatch.ts:49-67`）。
3. **部分接受语义正确**：拒绝若干条后从原快照重放被接受命令，range 描述最终文档（`src/services/editorEditBatch.ts:80-102`）。
4. **版本与 hash 防护**：批次 target 校验 `contentVersion`（`editorEditBatch.ts:42-47`）；回滚要求当前内容 hash 与应用后 hash 一致（`editorBatchRecord.ts:110-115`）。
5. **批次台账**：记录 status、source/applied hash、accepted/rejected indexes、appliedAt、rolledBackAt（`editorBatchRecord.ts:12-29`）。
6. **写入预算**：原生工具循环限制写入提案数量，防止模型刷写（`aiService.ts:903-915`）。

这些能力说明我们不是从零开始。问题二的正确路线是“补协议”，不是推倒重做。

### 缺口一：定位协议太弱（高危）

`replace_match` / `delete` / `rewrite` 的定位逻辑是：

```ts
const index = content.indexOf(targetText)
if (!targetText || index < 0) return failed(command, target, 'target_not_found')
```

证据：`src/services/editorEditService.ts:92-96`。

后果：

- **首次命中即写入**。同一句话在大纲里出现多次时，AI 会改到第一处，用户以为是随机位置。
- **无唯一性校验**。SWE-agent 与 Continue 都把“多匹配”视为必须拒绝的错误。
- **无模糊回退**。Roo 有精确 → middle-out → aggressive 三级；我们精确失败就整体失败。
- **失败信息无法修正**。`target_not_found` 没有候选、没有上下文、没有建议，模型无法自我修正。

更矛盾的是：**读取工具 `editor.locate` 已经实现了精确匹配、多匹配拒绝和 Top-3 模糊候选**（`src/services/editorTools.ts:198-232`），但 `editor.propose_edits` 自己完全不调用这套校验（`:262-296`）。相当于我们有“验钞机”，但收钱的时候不用。

### 缺口二：无结构感知锚点（高危）

当前写入协议只有文本 `target`、`position`、选区，没有“卷/章/节标题”这类结构锚点。社区系统用函数/类边界做窗口扩展（SWE-agent）或 AST 定位；写作域的等价物就是标题层级、卷号、章节名、设定条目。

后果：用户说“把这段讨论结果放到第三卷第五章开头”，模型只能在全文里找字符串，而不是先定位“第三卷 → 第五章”，再在局部找插入点。长大纲里这会指数级放大定位失败率。

### 缺口三：chain 路径完全没有写入能力（高危）

- plain 路径（`askPlainAi`）会创建编辑工具，并注入工具策略（`src/components/common/OutlineWorkspace.vue:2053-2096`）。
- SKILL chain 路径调用 `callWorkspaceSkill`，其内部没有任何编辑工具注入；而且 chain 第 2 步起强制关闭 outline/settings/memory 上下文（`src/services/workspaceSkillEngine.ts:383-402`，`:420-485`）。

这直接解释客户现象：“加载 SKILL 后模型不知道自己能写编辑器”。同一工作台里，开不开 SKILL 会改变模型能力面，用户感知就是“有时能写、有时完全不知道插入点”。

这不能简单判定为“chain 不该有写入”。S0 诊断师确实不应写；S1 定稿师在用户明确要求修改时应该有提案能力。正确方向是把写入能力与意图/阶段绑定，而不是与“是否加载 SKILL”绑定。

### 缺口四：全文硬塞 prompt，与长文档缺口互相放大（高危）

`buildEditorEditPrompt` 的最后一段直接拼入 `target.content`（`src/services/editorEditProtocol.ts:177-187`）。外层 `buildContextBundle` 又把 outline 截到 12,000 字（`conversationContextService.ts:285`）。

后果：

- 短文档：重复注入（system prompt 一次、workspace context 一次、user message fallback 一次）。
- 长文档：模型看到的“当前编辑内容”和真实编辑器可能不一致，target 精确复制也会失败。
- 问题一没解决前，问题二的 `replace_match` 会长期表现不稳定。

### 缺口五：失败反馈与编辑后校验缺失（中高危）

- Roo/Aider 会把失败块、相似度、候选上下文回传给模型，支持“只重发失败部分”。
- SWE-agent 写入后跑 lint，把新引入的问题与替换窗口关联后反馈。
- 我们目前：JSON 解析失败整批拒绝，没有“部分失败重提”；应用成功后没有大纲结构完整性校验（层级破坏、段落断裂、字数异常、编号重复）。

### 缺口六：审批与回滚体验低于协议能力（中危）

协议里有批次记录、部分接受、hash 回滚，但 UI 只有 show-diff 窗口骨架，缺少：

- 每条编辑一张 diff 卡（Roo/OpenHands 形态）。
- 点击 diff 卡定位到编辑器原文位置。
- 批次应用后编辑器自动滚动/刷新到修改处。
- 影响分析（本次修改波及哪些卷/章/伏笔，jarvis-write 形态）。
- 会话级确认状态机（pending 批次在切换目标、重新生成、关闭面板时的失效规则，Goose 形态）。

### 缺口七：兼容模式写入可靠性未定义（中危）

供应商不支持原生工具时降级 JSON 协议（`aiService.ts:831-869`），这是必要的。但兼容模式下没有工具循环，意味着没有“先 locate 再 propose”的两步流程；模型必须一次性给出完全精确的 target。恰恰是这类供应商路径，最容易触发 `target_not_found`。

## 成熟写入协议对照表

| 环节 | 社区成熟做法 | 我们现状 | 差距 |
|---|---|---|---|
| 读取定位上下文 | 结构索引 + 范围读取（Cline/SWE-agent/PageIndex） | 12,000 字截断 + 全文塞 prompt | 大 |
| 目标定位 | 精确 → 模糊 → 候选诊断（Roo/Aider） | `indexOf` 首次命中 | 大 |
| 唯一性 | 多匹配必须拒绝并列出位置（SWE-agent/Continue） | 无校验 | 大 |
| 结构锚点 | 函数/类边界、AST（SWE-agent） | 无标题层级锚点 | 大 |
| 提案暂存 | 工具返回 pending，不落盘 | 已有，`propose_edits` | 小 |
| 批次规划 | 多块、偏移正确、部分失败 | 已有，且部分接受语义正确 | 小 |
| 用户审批 | diff 卡、每块可接受/拒绝、跳转原文 | show-diff 骨架，无卡级导航 | 中 |
| 确认状态机 | session 级、首答不可变、turn 结束清理（Goose） | 隐式 pending 变量 | 中 |
| 失败反馈 | 失败块 + 候选 + 只重发失败部分（Roo/Aider） | 单句 `target_not_found` | 大 |
| 编辑后校验 | lint / diagnostics（SWE-agent） | 无大纲结构校验 | 大 |
| 回滚 | 检查点 / 文件历史 / hash（Roo/SWE-agent） | 已有 hash 批次回滚 | 小 |
| SKILL/chain 集成 | 工具面一致，权限按阶段控制 | chain 完全无工具 | 大 |

## 架构判断

### 问题二的正确目标形态

成熟的大纲工作台双向写入应是九段闭环：

1. **结构定位**：先按卷/章/节标题定位，再在局部找文本。
2. **精确匹配**：target 必须逐字命中且唯一。
3. **模糊回退**：精确失败时给 Top-N 候选和上下文。
4. **提案暂存**：写入永远是提案，不触碰正文。
5. **影响说明**：本次修改涉及哪些卷/章/设定/伏笔。
6. **diff 审批**：每条编辑一张卡，可逐条接受/拒绝，可跳转原文。
7. **原子应用**：按接受项重放，版本与 hash 校验。
8. **编辑后校验**：结构完整性、层级、字数量级、断句检查。
9. **回滚与追溯**：应用后 hash 一致时可一键回滚，批次台账可查。

### 关键原则

- **不引入模型直写**。社区没有任何成熟系统这么做；我们现有的“提案 + 确认”安全边界是优势，不是负担。
- **写入能力必须覆盖 plain 与 SKILL 两条路径**。能力面按意图/阶段控制：诊断阶段只读，明确修改阶段可提案；不能让“是否加载 SKILL”决定模型能不能写。
- **问题一的读取协议是问题二的前置条件**。结构索引、范围读取、全文一致性不解决，写入定位永远建立在残缺视野上。
- **上下文不省成本**。按用户既定原则，不做以压缩为核心的“省钱”设计；按需读取是为了准确性，不是为了削减文字。
- **依赖策略**。优先零依赖等价实现；若引入依赖（例如成熟的 diff/模糊匹配库），按 v3 经验先评估风险并交用户确认。

## 优先级判断

### P0：写入可靠性地基

1. **统一定位引擎**：`replace_match/delete/rewrite` 走与 `editor.locate` 同一套精确 + 唯一性 + 模糊候选校验；`propose_edits` 在暂存前完成定位校验。
2. **chain 路径工具注入**：SKILL 模式与 plain 模式共享同一工具面，写入按意图/阶段授予权限。
3. **失败诊断闭环**：失败时返回候选位置、上下文、失败原因，支持模型只重提失败条目。
4. **长文档一致性**：写入 prompt 依赖问题一的结构索引/范围读取，不再依赖 12,000 字截断文本。

### P1：审批与可用性

1. diff 卡片化：每条编辑一张卡，逐条接受/拒绝，点击定位原文。
2. 应用后编辑器自动滚动到修改位置。
3. Goose 式会话确认状态：目标切换、重新生成、面板关闭时明确 pending 批次的失效规则。
4. 兼容模式降级提示：明示供应商不支持原生工具时定位可靠性下降，并引导用户扩选唯一片段。

### P2：写作域增强

1. 结构锚点写入：`volumeId/chapterId/sectionTitle` + 局部 target 双层定位。
2. 编辑后大纲校验：层级破坏、编号重复、字数异常、相邻段落断裂。
3. jarvis 式讨论蒸馏：多轮讨论收敛为结构化提案（位置、理由、影响范围），确认后进入写入链路。
4. 影响分析：只分析不执行，列出波及的后续卷章与设定。

## 风险边界

- **不得破坏 Folder 协议成熟化成果**：chain 工具注入必须与现有 folder skill 执行协议、意图路由、断点续跑兼容。
- **不得让写入变成隐形自动化**：所有社区基准都保留用户审批；我们已有的审批边界要保留。
- **不得只修 UI 不修协议**：diff 卡如果没有可靠定位引擎支撑，只是把错误展示得更漂亮。
- **不得只修协议不修上下文**：模型看不到完整结构与局部全文，协议再严谨也会失败。
- **回归验证必须真实**：按 v3 经验，须覆盖 mock 供应商 + 源 Electron 真实操作，验证点击 → store → diff → 应用 → 持久化 → 回滚全链路。

## 最终判断

客户说“API 不能写入编辑器”并不完全准确：应用有受控写入协议，且安全模型（提案、hash、回滚）是正确的。真实情况是：**写入协议处于半成熟状态，长文档读取缺口又放大了它的失败率；SKILL 路径完全没有写入工具，进一步让能力面不一致。**

对照社区，我们的成熟度判断：写入协议本体约 60%，审批与回滚骨架约 55%，定位协议约 25%，结构感知约 15%，失败反馈约 20%。整体双向写入能力约 40-45%。

最值得借鉴的组合是：**Roo 的定位与失败诊断、SWE-agent 的唯一性与编辑后校验、Goose 的确认状态机、OpenHands 的编辑卡与状态同步、jarvis-write 的讨论蒸馏与影响分析。** 路线不是推倒重做，而是把这些社区已验证的协议环节，逐项补进现有提案式底座。

本报告到此为止，不附带执行方案。待用户审核后再按优先级制定详细执行计划。
