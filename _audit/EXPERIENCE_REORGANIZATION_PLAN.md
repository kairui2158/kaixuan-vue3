# 经验文件系统性重组方案

> 生成时间：2026-08-31
> 目标：把经验文件从"日期流水账"升级为"按纪律区块索引的结构化知识库"，让每条经验在需要时能被快速命中，不再因为散落在长文尾部而被无视。

---

## 一、现状诊断

### 1.1 当前文件全景

| 文件 | 行数 | 结构 | 问题 |
|------|------|------|------|
| `_audit/神意开发经验总结.md` | 约 2083 行 | 4 卷 + 150+ 个日期快照章节 | 前两卷有体系，第四卷从 L216 开始变成按日期追加的流水账，规则散落在快照中间（规则 12 埋在 L901，规则 14 埋在 L904，生成前置条件铁律埋在 L1710），新经验追加时只会往尾部堆 |
| `_audit/神意开发经验总结_phaseC_add.md` | 约 40 行 | 错误类型 H/I/J 表格 | 与主文件格式一致但独立存在，不知道要去两个文件找经验 |

### 1.2 核心缺陷：五类内容混在一起

1. **通用铁律**（行为等价、验证作用域）——应永远置顶，但混在快照里。
2. **专项纪律**（设定层风格卡片必须始终可见）——只对特定组件有效，但写得像通用规则。
3. **脚本技巧**（CDP screenshot 超时设置）——技术备忘，不需要"纪律"级别。
4. **单次事件快照**（P7-9R2 验证顺序校正）——当时有用，事后价值衰减。
5. **根因模式**（A2 移除 v-show、ai-naming 整文件复制污染）——反复出现的系统性问题，需要提炼成可复用防御规则。

**为什么经验被无视**：当前结构没有"我正要做 X 类操作 → 先查 X 类纪律"的路由。新会话只能靠全文搜索关键词，而关键词永远猜不全。

---

## 二、重组目标

1. **零信息丢失**：原文件每一条经验都必须在新结构中有归属，原文件保留为归档不删除。
2. **按操作类型路由**：任务开始时根据"改码/写脚本/封装/验证"选择对应纪律区块，先读后做。
3. **根因模式独立成块**：把散落的"改 A 激活 B"类模式提炼成独立"错误类型 M"区块，配防御检查清单。
4. **活文档机制**：新经验按区块归位，不追加尾部；每个区块有编号、检查清单、最后更新日期。

---

## 三、新文件结构设计

### 3.1 文件布局

```
_audit/
├── 神意开发经验总结_v2.md          ← 新主文件（结构化）
├── 神意开发经验总结.md            ← 原文件重命名为归档保留（不删不改）
```

### 3.2 新主文件内部结构

#### 使用路由（文件最顶部）

| 我正要做… | 必读区块 |
|-----------|---------|
| 改任何源码 | §1 改码纪律 |
| 写验证脚本 | §2 脚本纪律 |
| 验证功能闭环 | §3 验证纪律 |
| 删除代码/组件 | §4 删除纪律 |
| UI 布局/样式 | §5 UI 纪律 |
| 封装/交付 | §6 交付纪律 |
| 数据持久化/存储 | §7 存储纪律 |
| AI 服务层 | §8 AI 服务纪律 |
| 不确定该查哪里 | §9 根因模式索引 |

#### §1 改码纪律（M 系列 + 通用改码规则）

**M 系列：改动污染防御（新增，最高优先级）**

来源：A2 移除 v-show、C4 批量修复、2026-08-30 ai-naming 整文件复制、2026-08-29 volume 脚本 Promise 假阳性等多轮同模式失败。

- **M1 影响圈声明**：改任何文件前，用 `rg` 列出该文件被谁引用、该函数读写了哪些 store 字段。产出两个清单：「我打算改的」和「这个改动可能碰到的」。超出需求范围的字段/组件/事件一律不碰。
- **M2 整文件操作禁令**：禁止跨分支/worktree 整文件复制；禁止"重写整个文件顺手清理"。必须用 apply_patch 逐行精准编辑，每行 diff 能回答"这行为什么在这个需求里"。
- **M3 diff 自审门槛**：提交前 `git diff` 逐行过，每一行必须能归入本次需求。回答不了的行 = 污染，剔除或单独说明。
- **M4 隐藏状态保护**：改"显示/隐藏"逻辑前，先确认它是有意状态控制（v-show 导航）还是死代码。不确定时不动，标记 TODO 留给专门任务处理。
- **M5 三面引用闭包**：删除类操作前，生产源码、测试脚本、历史资料三面搜索引用。引用未隔离前只关闭入口，不删实现。

**通用改码规则（从原规则 1/2/3 提炼）**

1. 行为等价：新架构必须复现旧架构的行为语义，不只是代码语义。
2. 一次一个闭环：改码→构建→杀进程→重启→验证，闭环完成才进下一个。
3. store 是唯一事实来源：用户重新打开还需要的状态必须放 store 或 storage。

---

#### §2 脚本纪律（D/I/J 系列精选）

1. 选择器必须先诊断：用 `rg` 搜源码确认 ID 存在且唯一，禁止凭假设写选择器。
2. 复杂脚本必须写 .cjs/.mjs 文件执行，禁止 PowerShell 内联嵌套引号/JSON。
3. 所有写操作必须 try...finally cleanup，异常退出不留脏状态。
4. evaluate 内 electronAPI 调用必须 async/await，返回值不能拼成 `[object Promise]`。
5. CDP screenshot 必须设 8-15s 超时并降级，失败不阻塞状态断言。
6. 脚本执行后必须 `process.exit(0/1)` 显式退出，禁止依赖事件循环自然结束。
7. v-show 元素验证用 `getComputedStyle().display !== 'none'`，不用 `offsetParent`。
8. 每次切换会话/载体前，先确认上一个 Electron/CDP 实例是否存活。

---

#### §3 验证纪律（C/F/规则 4/11 精选）

1. 构建成功 ≠ 功能完成：必须走真实 Electron（start-electron.bat）+ CDP 真实操作。
2. 验证必须递归：按钮存在 → 点击 → store 变化 → UI 响应 → 持久化。
3. 没有证据的"已完成" = 未完成：必须引用 file:line 或命令输出。
4. 验证作用域不扩大：服务层测试不能当 UI 证据，受控 mock 不能当真实 API 证据。
5. Vue 渲染等待：v-if 组件需异步渲染，CDP 检查前等 2.5s 或用 waitFor。
6. 启动态清理：验证前先处理可见的遗留弹窗/面板，禁止盲点隐藏按钮。
7. 夹具检查：重启持久化验证必须先确认测试项目存在，否则结果是"夹具缺失"不是"功能失败"。

---

#### §4 删除纪律（规则 5 + M5 扩展）

1. 死代码清理先做三面引用闭包：生产源码、测试脚本、历史资料。
2. 历史引用未隔离前只关闭入口（按钮/路由），不删实现。
3. Electron IPC handler、preload 暴露项先做引用闭包再删。
4. CSS 自动去重脚本禁止使用，每个删除必须手工确认。
5. 删除前确认用户要求的是"彻底删代码"还是"关闭入口"，默认后者。

---

#### §5 UI 纪律（规则 7 + 设定层/UI 快照提炼）

1. tokens.css 是唯一颜色/字号/间距变量来源，组件内禁止硬编码（组件级设计需除外）。
2. v-show 导航（流水线五层）是有意状态控制，禁止移除 v-show 改为 v-if 或全渲染。
3. 常驻 UI 卡片不能条件隐藏，空态显示"待 AI 分析"，不能整个消失。
4. 隐藏弹窗/未打开节点不能作为可见配色/布局证据，必须真实打开目标界面。
5. 死按钮扫描必须排除 v-show 隐藏区域。
6. 文字溢出验证必须逐弹窗、逐按钮、逐标签实测，不能只看一处通过就全量声明。
7. 弹窗递归验证三层：主页面 → 弹窗 → 弹窗内子弹窗。

---

#### §6 交付纪律（规则 9 + 客户交付快照提炼）

1. 版本号按改动等级升级：bugfix → patch，新功能 → minor，重大架构 → major。
2. 封装前工作区必须干净（`git status --short` 为空或只有明确归档文件）。
3. 封装命令 `npm run build`，产出 `dist/神意助手-Setup-{version}.exe`。
4. 安装包未签名状态必须在交付说明中如实标注。
5. 客户实操反馈项必须明确列出，不能预标通过。
6. DEV_LOG 必须写明：已验证项 / 未验证项 / 客户实操入口。

---

#### §7 存储纪律（规则 + 存储加固快照提炼）

1. 原子写盘四步：写 tmp → rename → 保留 bak → 验证可读。
2. 导入操作默认合并，覆盖必须用户主动选择高级操作。
3. 项目数据隔离：不同项目的 storage key 必须含项目 ID，禁止全局覆盖。
4. 旧配置兼容：读取时兼容老字段，保存后写新字段。
5. IPC 暴露三处同步：electron/ipc/*.js handler + preload.js + renderer 调用。

---

#### §8 AI 服务纪律（规则 + AI 层快照提炼）

1. 所有 AI 调用必须走 `aiService.callAi` 统一入口，禁止直接 fetch。
2. 取消必须中止真实请求并清理空占位消息，不能只隐藏按钮。
3. 流式/非流式超时分别配置，默认非流式 60s、流式更长。
4. 错误分类：network/timeout/http/json/auth/canceled，统一 error 对象结构。
5. 诊断日志单路径写入，detail 必含 providerId/purpose/model/durationMs/skillId/result。
6. 链式步骤失败时明确区分 failed/skipped/fallback/continued，不伪装成正常完成。

---

#### §9 根因模式索引（原第四卷快照按模式归位）

| 模式 | 散落位置 | 提炼规则 |
|------|---------|---------|
| 改 A 激活 B | A2、C4、ai-naming 08-30 | M 系列 |
| 脚本假设选择器 | D3、I1、H1-H3 | §2 规则 1 |
| Promise 未 await | J1、volume P4 | §2 规则 4 |

| 隐藏 DOM 当证据 | 规则 6 补充、P10 | §5 规则 4 |
| 载体冲突 | J2、08-31 _electron.launch | §2 规则 8 |
| 夹具缺失误判 | 08-31 settings-bind | §3 规则 7 |

## 四、迁移步骤（按序执行）

### P0 创建新文件骨架

1. 创建 `神意开发经验总结_v2.md`，写入使用路由 + 9 个区块框架。

4. 验证方式：`rg "已提炼到 v2" 神意开发经验总结.md | Measure-Object -Line` 与提炼条目数一致。

1. 把规则 1-11、规则 12/14、生成前置条件、防无限回滚等按主题归入 §1-§9。
2. 同一条规则出现在多个快照时，合并为一条并保留全部来源引用。
3. 验证方式：`rg "^### 规则" 神意开发经验总结_v2.md` 每条规则都有归属区块。

1. 逐个快照读取，判断是"已有模式的新实例"（只补来源引用）还是"新模式"（新增提炼规则）。

2. phaseC_add 原文件头部加标注"内容已合并到 v2，本文件仅作归档"。

1. 使用路由表每个链接指向 v2 中的实际锚点。

### P6 收尾

1. 原文件重命名为 `神意开发经验总结_归档.md`（或保留原名 + 头部标注"已归档"）。
2. 新文件命名为 `神意开发经验总结_v2.md`（或直接替换原名，用户决定）。
3. git commit + push，保持工作区干净。
4. 在根目录 `EXPERIENCE.md` 头部加指向新文件的链接。
5. 验证方式：`git status --short` 干净；`rg "v2" EXPERIENCE.md` 确认链接存在。

## 五、新经验写入规范（防止再退化为流水账）

### 5.1 写入决策树

```
新经验产生
├── 是通用铁律（跨模块/跨任务有效）？
│   └── 是 → 归入对应 §N 区块的"硬规则"列表
├── 是某个根因模式的新实例？
│   └── 是 → 在 §9 根因模式索引补来源引用，不新增条目
├── 是特定组件/功能的专项经验？
│   └── 是 → 归入对应 §N 区块的"专项经验"子节
└── 是一次性事件快照？
    └── 是 → DEV_LOG 记录，v2 中只补根因模式索引引用
```

### 5.2 条目格式（每个区块内统一）

```markdown
- **[编号] 规则标题**（来源：原 L{行号} {条目ID}；最后确认：{日期}）
  - 规则内容（一句话，可操作）
  - 检查方式（怎么确认自己没有违反）
```

### 5.3 定期维护

- 每次封装交付前，通读一遍使用路由表，确认每个区块的"最后更新"日期。
- 发现同一条规则重复出现 3 次以上时，升级为该区块的"硬规则"并加粗。

## 六、风险与边界

| 风险 | 应对 |
|------|------|
| 提炼时误删原始细节 | 归档文件不删不改，v2 条目保留来源行号引用，可随时回溯 |
| 区块分类有歧义（一条规则同时属于改码和验证） | 允许一条规则在多个区块出现，但正文只写一处，其他位置用交叉引用 |
| 迁移过程中原文件和新文件并存导致查找困惑 | P6 收尾时明确标注哪个是权威文件；EXPERIENCE.md 头部链接指向权威文件 |
| v2 文件膨胀回到流水账 | 遵守 5.3 定期维护 + 写入决策树，每条新经验必须归位不能追加尾部 |
