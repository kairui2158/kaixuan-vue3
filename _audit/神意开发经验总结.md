## 第一卷：错误全景与根因分析

### 错误类型 A：架构迁移类

| # | 错误操作 | 根因 | 改正措施 | 避免再犯 |
|---|---------|------|---------|---------|
| A1 | 直接把旧架构代码复制到 Vue3 组件中 | 认为"代码相同=功能相同"，没意识到两个系统本质不同（旧：事件+全局变量+手动刷新；新：状态+响应式+store+computed+生命周期） | 重写为新架构写法：业务状态放 store，组件用 computed 读取，联动用 emits/watch | 每次改代码前先读旧架构分析集的手册，确认"旧架构这一步做了什么"，然后想"新架构怎么做等价"，禁止直接复制 |
| A2 | 移除 v-show 导致流水线五层全渲染 | 看到 5 层面板"隐藏"以为是 bug，没理解 step-based 导航的设计意图 | 恢复 `v-show="pipelineStore.currentStep === N"` | 在改任何"隐藏/显示"逻辑前，先确认它是不是有意为之的状态控制 |
| A3 | CSS 从单文件到模块化迁移时变量名不统一 | 用多个 CSS 文件（global.css/tokens.css/modal.css）时，变量定义分散，选择器冲突，响应式断点丢失 | 统一 tokens.css 变量定义，建立视觉基准文档 | 所有 CSS 变量必须在 tokens.css 中定义，禁止组件内硬编码（组件级设计需要除外） |
| A4 | 自动去重脚本"保留最后定义"破坏了有意层叠覆盖 | 用脚本批量去重时没考虑 CSS 的层叠顺序，删掉了前面的有意覆盖 | 重建 CSS 结构，按"基类→组件→覆盖"层级管理 | 禁止用自动去重脚本处理 CSS，每个删除必须手工确认 |

### 错误类型 B：组件化拆分类

| # | 错误操作 | 根因 | 改正措施 | 避免再犯 |
|---|---------|------|---------|---------|
| B1 | 编辑器事件监听在 App.vue 分发但 EditorPanel 没监听 | 拆分到 32 个 .vue 文件时，事件分发链路被遗漏 | 补全 EditorPanel 的撤销/重做/保存事件监听 | 拆分时先画事件流图，确认每个事件的"发出→传递→接收→处理"完整闭环 |
| B2 | v-for 内 ref 收集成数组但 .focus() 失效 | Vue 3 的 v-for ref 数组行为与 Vue 2 不同，ref 数组是函数形式 | 改用 `(el) => { if (el) refs[i] = el }` 方式 | 迁移前先确认 Vue 3 的 breaking changes，特别是 ref 和 reactive 行为 |
| B3 | 组件本地状态替代持久化状态 | 正文生成结果用组件本地 `ref` 存，用户关掉面板再打开，数据丢失，按钮禁用 | 改为从 `projectStore.chapters[vol].body` 读取的 computed | 凡是用户关掉面板再打开还需要看到的数据，必须放 store 或 storage，禁止用组件本地 ref |

### 错误类型 C：修复与验证类

| # | 错误操作 | 根因 | 改正措施 | 避免再犯 |
|---|---------|------|---------|---------|
| C1 | 修 A 漏 B，修功能不修 UI，修 UI 不修数据 | 没有"闭环修复"意识，只修了表面症状 | 修复必须覆盖：store 状态 → UI 渲染 → DOM 验证 → 截图 | 每个修复划一个闭环边界，闭环内所有层必须一起修完 |
| C2 | 不构建就断言修复生效 | 改了 .vue 源文件但没跑 `npx vite build`，Electron 加载的是旧包 | 任何源文件修改后必须 `npx vite build` 再重启 | 每次修改后按顺序：改代码 → 构建 → 杀进程 → 重启 → 验证 |
| C3 | 不杀进程就重启 | 旧 Electron 进程残留，新进程加载旧数据 | 先 `taskkill /f /im electron.exe` 再启动 | 写入铁律：每次修改代码后必须杀进程再重启 |
| C4 | 批量修复而非精准修复 | 图省事一次改多个文件，每改一个引入一个新 bug | 一次只修一个功能闭环，修完验证再进入下一个 | 硬约束：一次只改一个文件，一个闭环，修完验证再继续 |
| C5 | 声称完成但没验证 | 代码编译通过就认为"修好了"，没有做行为验证 | 必须用 CDP 做真实用户模拟：点击 → 检查 store → 检查 UI | 没有 CDP 验证结果的"已完成"都是未完成 |
| C6 | 只检查表面不递归 | 只看了按钮是否存在，没点进去看效果 | 按钮点击后必须检查：store 变化 + UI 响应 + 菜单/弹窗展开 | 每次检查必须递归深入：点击按钮 → 检查弹窗 → 点击弹窗内按钮 → 检查 store |

### 错误类型 D：脚本与工具类

| # | 错误操作 | 根因 | 改正措施 | 避免再犯 |
|---|---------|------|---------|---------|
| D1 | 脚本修改应用真实状态（seeding 项目、锁定大纲） | 以为"测试完就清掉"没问题，但脚本异常退出后 cleanup 没跑 | 脚本设计为纯读检查：只检查元素存在性、可见性、store 状态，不点击不修改 | 检查脚本必须 100% 只读，所有操作必须可逆，异常退出时必须有 cleanup |
| D2 | 脚本残留持久化数据 | 脚本通过 `electronAPI.storageWrite` 写了数据，异常退出后 cleanup 没跑，重启后数据还在 | 写脚本时 identity 每个写操作，确保 cleanup 在 finally 中执行 | 凡涉及持久化写入的脚本，必须 try...finally 保证 cleanup |
| D3 | 选择器写错导致脚本误报 | `pl-s1-agent` 没加 `#` 前缀，变成了标签名选择器 | 所有 ID 选择器必须加 `#` 前缀，脚本增加选择器验证步骤 | 脚本写完后先跑一小段验证选择器正确性，再跑完整流程 |
| D4 | 截图 fullPage 超时 | Electron 内全页截图需要等待字体加载，30s 超时 | 截图改为：先 fullPage 15s 超时，失败则降级为视口截图 | 截图函数必须带超时和降级逻辑 |
| D5 | PowerShell 转义问题 | 在 PowerShell 中内联 JSON/正则/嵌套引号时，转义字符互相冲突 | 复杂脚本用 apply_patch 写文件，或用 .js/.ps1 文件 + node/cmd 执行 | 任何含嵌套引号/JSON/正则的命令，必须写文件执行，禁止内联 |
| D6 | 总是自己写脚本而不是用现成工具 | 每次需要检查就写一个新的 .cjs 脚本，重复造轮子 | 直接使用 Playwright 标准 API，复用已有验证脚本 | 先看 `_audit/` 有没有可复用的脚本，没有才新建 |

### 错误类型 E：链路与流程类

| # | 错误操作 | 根因 | 改正措施 | 避免再犯 |
|---|---------|------|---------|---------|
| E1 | 不对比旧架构链路就下手改 | 只看了新架构代码，没看旧架构的实现逻辑，改了之后功能不完整 | 每次改功能前必须读旧架构分析集的手册，理解"旧架构为什么这么干" | 硬约束：改任何功能前，必须读对应的旧架构行为手册 |
| E2 | 用开发版启动器替代源文件启动器 | 搞混了 vite 开发服务器和 start-electron.bat 的区别 | 始终用 `start-electron.bat` 启动 | 铁律：只能用 start-electron.bat 启动，禁止其他方式 |
| E3 | 不理解应用链路就断言"修好了" | 只看了一个页面，没看点击后跳转、数据联动、状态同步 | 验证必须覆盖：面板打开 → 按钮点击 → 数据变化 → 页面跳转 → 次级页面 → 返回 | 验证链路时必须模拟真实用户完整流程 |

## 第二卷：技术发现与决策记录

### P5. 编辑器上下文与 AI 对话深度核验（2026-08-22）

- **行为等价结论**：章节正文 `ch-body` 与章节概要 `ch-plot` 即使共享同一个 `chapterId`，也必须按 `chapterId + mode` 区分编辑器 tab。只按 `chapterId` 复用 tab 会导致用户点击概要后再点正文时仍显示概要，进而把右侧对话的上下文、Skill 和 Agent 一起带错。
- **已确认实现**：`src/stores/editor.ts` 的 `openTab` 以 `t.chapterId === tab.chapterId && t.mode === tab.mode` 查找已有 tab；真实 Electron/CDP 已核验正文/概要来回切换标题、模式和会话不混淆。
- **选区操作规则**：内联 AI 事件必须携带 `tabId`、`selectionStart`、`selectionEnd` 和 `selectedText`。AI 回包后，“替换”只改有效选区；没有有效选区时才弹出整章替换确认框。这里不能只看按钮反馈，必须核对 textarea、Pinia tab 内容和项目存储。
- **插入与保存边界**：聊天“插入/替换”先更新当前编辑器和 editor store，项目文件落盘仍由编辑器“保存”动作完成。验证必须拆成“编辑器/store 已更新”和“点击保存后 `wa_project_<id>` 已更新”两层，不能把前者当成持久化完成。
- **会话隔离规则**：聊天会话按 `projectId + tabId + chapterId` 归属；正文和概要即使 chapterId 相同，也必须拥有不同 tabId。切换上下文时要核对 activeSessionId、消息 DOM、`wa_chat_<projectId>` 三者一致。
- **重启验证规则**：关闭并杀 Electron 后用 `start-electron.bat` 重启，聊天消息可以从 `wa_chat_<projectId>` 恢复；`currentContext` 是运行时状态，重启后需要用户重新点击章节树建立当前编辑上下文，不能声称它会自动恢复。
- **验证纪律**：受控 API 只能用来证明应用的请求、流式解析、取消和替换链路，不能当成供应商稳定性证据。测试脚本必须是临时只读/可逆载体，结束时恢复项目和聊天快照并删除脚本。

### T1. IPC 序列化
- **问题**：Vue ref/reactive Proxy 不能直接传 Electron IPC，`ipcRenderer.sendSync` 用 structured clone 序列化，Proxy 触发 "An object could not be cloned"
- **修复**：所有 `storageWrite` 调用前必须 `JSON.parse(JSON.stringify())` 深拷贝
- **覆盖范围**：agent.ts、chapter.ts、deai.ts、project.ts、provider.ts、pipeline.ts、skill.ts、theme.ts

### T2. CDP 验证要点
- Playwright 的 `connectOverCDP` 在 `file://` 协议下 `waitForLoadState('networkidle')` 会无限挂起，必须用 `waitForTimeout` 代替
- CSS overlay 拦截 Playwright 的 `click()`，需要 `force:true` 或 `evaluate()` 方式触发
- `evaluate()` 方式触发点击比 `click({force:true})` 更可靠，因为能触发 Vue 事件处理
- 验证必须同时读 store 和真实 DOM 类名，不能只依赖一个

### T3. 构建与启动
- 构建命令：`npx vite build`（输出到 dist-renderer/）
- 启动命令：`start-electron.bat`（使用 `--remote-debugging-port=9227`）
- 每次启动前必须杀干净所有 Electron 进程
- 启动后等待 3-5 秒再连接 CDP

### T4. 存储路径
- 数据持久化到 `Documents/神意助手数据/`（由 electron/ipc/storage.js 定义）
- 键前缀：`wa_project_`、`wa_chat_`、`wa_agents`、`wa_skills`、`wa_pipeline_step_config` 等
- 卸载应用时文件不会丢失，在 `Documents/神意助手数据/` 中保留

## 第三卷：神意开发规则（铁律）

### 2026-08-26 遗留核销补充规则

1. “统一入口”必须按网络请求类型逐项列清：生成/验证/检测与模型获取、插件、MCP 不是同一语义，不能用一次 `rg` 命中就宣称全部收敛；每类都要有入口、路由、错误和验证证据。
2. 安装包存在不等于安装版可用。必须分别核验：进程启动、CDP 页面、原生文件对话框、文件写入/读取、重启恢复；缺一项只能写“烟测”或“未核销”。
3. 死代码清理先做生产入口、历史资料、测试脚本三面引用闭包；历史引用未隔离前不得删除旧模块，避免误删行为等价基准。
4. 构建成功、类型检查失败、自动化测试 runner 失败必须分开记录；不能用构建成功覆盖类型或测试缺口。
5. 旧架构文件的硬编码颜色扫描结果必须先按生产入口、历史资料、测试脚本三面分层；若无当前生产入口，只能标记为历史兼容基准，不能为“全仓库零颜色字符串”误删或批量改写。
6. “统一 AI 入口”必须区分生成调用、模型列表、插件市场和 MCP 工具协议；只有同一语义的网络调用才能合并，不得把外部 API 或工具协议强行塞进生成 purpose。
7. `start-electron.bat` 输出 `[OK] Application started` 不是进程存活证据；必须再检查实际进程和 CDP 端口，批处理若含 `pause`，启动与验证要分离执行。
8. 服务层自动化测试必须使用与项目模块解析一致的 runner；当前使用 Vite/Vitest。不得用 Node 原生 runner 直接执行无扩展名 bundler ESM，也不得混用 `node:test` suite 与 Vitest runner。

### 规则 1：行为等价原则（最高优先级）
```
1. 旧架构行为 = 旧架构这一步到底做了什么
2. 新架构实现 = 用 Vue3 的 store/computed/emits/lifecycle 实现等价行为
3. 禁止直接复制旧代码，两个系统本质不同
4. 唯一可信的旧行为基准在：C:\Users\凯瑞\Documents\New project 2\旧架构分析集
```

### 规则 2：新架构写法标准
```
1. 业务状态必须放 Pinia store，禁止用全局变量替代
2. 组件读取状态只能用 computed，禁止各自保存一份不同步的数据
3. 子组件不能直接改父组件状态，必须通过 emits 通知父组件
4. 联动靠 store 更新 + computed/watch 响应，禁止手动刷新式到处调用
5. 同一个业务数据的单一事实来源只能有一份，禁止双份来源
6. 表单用 v-model，面板打开关闭用生命周期和状态控制
```

### 规则 3：修复纪律
```
1. 一次只修一个功能闭环，禁止批量改一堆无关功能
2. 每个闭环修完输出完整验证结果，再进入下一个
3. 修复必须覆盖：store 状态 → UI 渲染 → DOM 验证 → 截图
4. 禁止自动去重/批量替换，每个修改必须手工确认
5. 先删后改：删除旧代码再写新代码，不留死代码
6. 遇到旧架构和新架构无法对齐的行为，先停下来报告，不要自己绕路
```

### 规则 4：验证纪律
```
1. 没有 CDP 验证结果的"已完成"都是未完成
2. 验证必须走真实用户操作：点击 → 检查 store → 检查 UI → 截图
3. 检查必须递归深入：按钮点击后检查弹窗，弹窗内按钮再检查
4. 验证必须同时读 store 和真实 DOM，不能只依赖一个
5. 每次修改后按顺序：改代码 → 构建 → 杀进程 → 重启 → 验证
6. 截图函数必须带超时和降级逻辑
```

### 规则 5：脚本纪律
```
1. 检查脚本必须 100% 只读，不点击不修改不 seeding
2. 所有脚本必须 try...finally 保证 cleanup
3. 凡涉及持久化写入的脚本，cleanup 在 finally 中执行
4. 所有 ID 选择器必须加 # 前缀
5. 复杂脚本（含嵌套引号/JSON/正则）必须写文件执行，禁止内联
6. 脚本跑完后必须清理残留，不留脏状态
```

### 规则 6：工程纪律
```
1. 只用 start-electron.bat 启动，禁止其他方式
2. 每次启动前必须 `taskkill /f /im electron.exe` 杀干净进程
3. 源文件修改后必须 `npx vite build` 再重启
4. 改任何功能前，必须读对应的旧架构行为手册
5. 先读代码再改，用 apply_patch 编辑，验证后再声称完成
6. 一个工具调用失败 2 次后换方案，不重试同一格式
```

### 规则 7：UI 统一纪律
```
1. 所有 CSS 变量必须在 tokens.css 中定义，禁止组件内硬编码
2. 弹窗统一先定基类（modal.css），再逐个组件替换
3. 按钮统一使用 global.css 定义的 .btn-primary/.btn-secondary/.btn-danger
4. 字号统一按 tokens.css 的 --font-size-xs/sm/md/lg 四级
5. 组件级字号硬编码保留为设计需要，不加全局覆盖
6. 同一 UI 只有一种写法，发现重复立即清理
```

### 规则 8：链路完整性
```
1. 每次改功能前先画链路图：输入→处理→输出→联动→存储
2. 验证时必须模拟真实用户完整流程，不能只看一个页面
3. 字数链必须自动传导：大纲字数→卷数→每卷字数→章数
4. 关闭应用时的状态必须持久化，重启后恢复
5. 所有按钮必须有可见入口，禁止无入口的功能
```

### 规则 9：GitHub 版本管理铁律
```
1. 每次代码变动必须提交并上传 GitHub，禁止只改本地不推送
2. 神意仓库为 GitHub 私有仓库（shenyi），不对外公开
3. 提交前必须检查 git status，确认本次提交只包含本次变更内容
4. 提交信息必须写明改动内容（格式：类型: 组件 - 改动描述）
5. 推送失败时先排查远程/认证，不重复 push 同一错误命令
6. 每次上传后输出推送结果，证明远程仓库已同步
```

### 规则 10：经验回写铁律
```
1. 每次开发前必须读取 _audit/神意开发经验总结.md，确认已遵守全部规则
2. 每次开发完成后必须更新 _audit/神意开发经验总结.md，记录新错误/新经验
3. 每次开发完成后必须更新 _audit/DEV_LOG_*.md 开发日志，按日期追加
4. 经验总结和开发日志必须与代码变更一起提交 GitHub
5. 禁止出现“改了代码但没更新文档”的未闭环状态
```

### 规则 11：验证作用域铁律
```
1. 相同 class 可能出现在多个组件，测量/选择必须限定组件作用域（如 #ow-chat-messages）
2. 全页面 querySelectorAll 统计同一 class 的结果不能作为组件验证证据
3. 字号修复必须走真实输入→发送→渲染链路，不得用临时 DOM 注入冒充
```

### 卷纲与章节经验复用 P1（2026-08-26）

1. 卷纲和章节列表必须是独立的滚动容器，至少同时约束 `min-width: 0`、`min-height: 0`、`overflow-x: hidden` 和 `overflow-y: auto`；不能让多对象卡片把步骤面板无限撑高。
2. 列表、详情编辑区、生成反馈区和底部操作区必须有清晰的承载边界。底部操作区使用不收缩的布局项并保持可见，不能被列表内容挤出视口。
3. 卡片内的 input/textarea 必须有 `box-sizing: border-box`、`min-width: 0` 和 `max-width: 100%`，否则长文本或组合控件可能造成横向截断。
4. P1 只建立布局契约，不得借布局修改生成函数、store 字段、持久化协议或按钮语义；对象选择和唯一详情编辑区分别在 P2/P3 实施。

### 卷纲与章节经验复用 P2-P3（2026-08-26）

1. 多对象工作区采用“列表选择 + 唯一当前对象编辑区”后，列表只负责导航，保存/锁定/删除/API 反馈继续放在当前对象详情区，避免一屏展开多个完整卡片。
2. 过滤后的章节视图不能直接把显示索引用作原始数组索引；生成正文和删除必须先按稳定 `chapter.id` 映射回 `projectStore.chapters[volumeId]`，否则手工章节与生成章节混排时会错操作。
3. 章节对象不存在时必须保持空状态，不为了验证而向客户项目写入测试数据；没有真实对象的切换、删除和正文落点只能记录为验证边界。
4. P2/P3 的工作区结构不能改变原有生成、锁定、持久化和正文事件语义；经验复用是结构和验证方法复用，不是复制设定层代码。


### 全应用 UI 升级 V2-P3 经验（2026-08-23）

1. 弹窗配色统一必须覆盖自定义 overlay、嵌套 content、项目/差异弹窗和设置诊断面板，不能只改公共 modal 基类。
2. 颜色 fallback 的治理应以语义 token 替换为边界，保留尺寸、z-index 关系、滚动和事件行为；不能借配色任务顺手重排布局。
3. 递归验证必须先真实打开可见弹窗，再读取 computed background、border、z-index、clientWidth/scrollWidth；关闭必须使用当前弹窗作用域内的真实关闭按钮，并核对可见 overlay 为 0。
4. 空闲态没有打开的工作弹窗时，不能把隐藏 DOM 当作 API 日志、统计或流水线子弹窗的运行时配色证据；源码收敛和可见工作态验证要分开记账。

### V1/V2-R1-S1 设置界面溢出复盘（2026-08-23）

- 错误操作：看到设置页整体 `scrollWidth/clientWidth` 相等，就把设置页文字溢出判断为没有问题。
- 根因：页面级尺寸不能证明内部按钮内容、卡片操作区和长文本没有被挤压；此前没有逐元素读取 `clientHeight/scrollHeight`、边界坐标和换行策略。
- 改正措施：设置页增加 `box-sizing:border-box`、`min-width:0`、操作区 `flex-wrap`、长文本 `overflow-wrap:anywhere` 和横向溢出裁定；复验必须逐个点击七个子页并扫描可见子元素边界。
- 避免再犯：以后“文字溢出”验收不得只看页面级 `scrollWidth`；必须同时检查文字节点、按钮、卡片、输入框和提示文本的实际矩形边界，并核对 `scrollHeight` 是否因 padding/line-height 异常增加。

### V2 配色盘点经验（2026-08-23）

- 配色 token 存在不等于页面配色统一；必须同时记录源码 token、组件 fallback 和可见 Electron/CDP computed color。
- 隐藏弹窗或未打开的流水线节点不能作为可见配色证据；验证前必须真实打开目标界面，并限定当前可见节点作用域。
- 配色治理不得批量替换所有十六进制颜色。先建立页面背景、面板、输入、文字、边框、状态、AI 气泡、用户气泡和遮罩的语义映射，再按页面闭环逐点替换。
- V1 结构已冻结时，V2 只能改变颜色表现，不能顺手修改布局、字号、按钮位置或业务链路；发现结构问题必须另立修复编号。

### P7-9R2 入口阻断经验（2026-08-23）

- 受控 JSON 响应满足 `choices[0].message.content`、五数组、真实 `chapterId` 和非空证据，并不等于用户闭环成立；必须先证明真实入口按钮可用。
- 本轮 Electron 页面中“提取记忆”按钮虽然可见，但 DOM 为 `disabled`，导致请求、预览、审核、写入和四视图验证全部不能开始。不能用 `force` 点击禁用按钮，也不能直接改 store 绕过前置状态。
- 后续修复顺序必须是：正文真实保存 → 变更标记更新 → 提取按钮 computed enabled → 真实点击 → AI 响应解析 → 预览审核 → 项目持久化 → 四视图读取。前置状态未成立时，不得继续后面的表层按钮测试。
- 服务层契约核对和 Electron UI 行为核对要分开记账；类型检查被既有债务阻断时，不能将其改写为本轮业务通过，也不能借机批量修复无关类型错误。

### P4 收尾校正：重生成与 CDP 证据边界（2026-08-22）

1. 重生成不能依赖组件直接 splice 后立即调用发送函数；应由 chat store 原子替换用户消息和旧 assistant，再在响应式 tick 后显式传递用户文本。即使代码路径已修正，仍必须取得第二轮消息、assistant 收束和本地存储差异三层证据。
2. `start-electron.bat` 被调用不等于源文件运行时通过；必须同时拿到 Electron 绝对路径、CDP 页面列表和真实 DOM 操作结果。CDP 端口不可用时，阶段只能记为环境阻塞。
3. 真实供应商 HTTP 失败/超时/取消不能用 MCP 本地错误替代；必须分别记录请求失败、重试请求、最终状态，取消还要验证空占位清理和可再次输入。

### P6 全功能回归收尾规则（2026-08-22）

1. P6 必须把“代码入口、DOM 可见、Pinia 状态、Electron 持久化、重启恢复、供应商真实响应、原生文件落盘”分成独立证据层；任何一层缺失都不能扩大成整条闭环通过。
2. 断点对象可读取只证明存储入口存在；只有“失败→保存断点→重启/重试→从正确步骤继续→成功后清除断点”才算断点续跑通过。
3. 生成状态文字或按钮禁用不等于取消生成；取消必须有用户可见入口，并证明真实请求中止、空占位清理、状态收束和再次生成可用。
4. 原生导入/导出必须拿到窗口、用户确认、目标文件存在且可读、数据状态前后对比四层证据；页面按钮和 `dialogOpenFile` 代码不能替代。
5. 记忆的“同源”不等于“同步已发生”：正文确认/审核/写入、四视图内容变化、保存和重启恢复必须逐项核销；动画/短剧没有真实读取接入时明确写“未接入”。
6. 目标模式收尾必须生成正式报告，保留“已通过、部分通过、未核销、未接入、环境阻塞”状态，并只提出下一阶段，不自动跳回前置阶段。

### P4-R 实际核销经验（2026-08-22）

1. 重生成的正确判据不是消息总数增加，而是同一会话中原 user/assistant 对被替换、重新产生真实请求、assistant 收束完成并写回存储；因此本次 `5 → 5` 也可以是有效通过，但必须核对内容、时间戳和请求数。
2. 受控 HTTP `503 → 200 SSE` 可以证明应用的重试闭环，但只能证明应用行为，不代表供应商网络稳定性；请求次数、最终消息、Pinia 状态和持久化必须同时记录。
3. 取消验证至少覆盖真实请求发送中和普通重试等待中。每种时机都必须证明没有后续请求、状态为 `canceled`、空 assistant 清理、输入恢复；只看到取消按钮或 AbortController 不算通过。
4. 自动化验证产生的业务测试消息必须在收尾阶段通过同一 store 和存储入口清理，并记录清理前后数量，避免把测试数据留给客户。

### P7-1 流水线取消生成核销经验（2026-08-22）

| 项目 | 结果 | 证据边界 |
|---|---|---|
| 用户入口 | 已通过 | 源文件启动器启动后，设定层生成中显示 `#btn-pl-cancel-generation`；非生成状态隐藏 |
| 请求中止 | 已通过（受控 HTTP） | CDP 仅在本次页面会话替换 `window.fetch` 为延迟响应；点击取消后受控请求收到 `AbortSignal`，`aborted=true` |
| 状态收束 | 已通过 | Pinia `pipeline.isGenerating` 从 `true` 变为 `false`，`generationStatus` 为 `canceled`，进度未被后续完成/失败逻辑覆盖 |
| 空结果保护 | 已通过 | 取消前后 `project.settings` 深比较不变，空数组没有覆盖项目设置 |

| 取消后恢复入口 | 已通过 | 取消按钮消失，生成按钮恢复可用；未用真实供应商再次消耗请求 |

本轮根因与修正：`aiService` 原本支持 `AbortSignal`，但流水线没有把信号传给统一 AI 服务，也没有用户可见取消入口；流水线 store 新增唯一 `AbortController`，各生成路径统一读取同一信号，章节重试/补充循环在取消状态下停止。`provider.callApi` 同步转发 signal。

严格边界：本轮受控延迟请求证明的是应用取消机制，不证明供应商网络稳定；没有把取消期间的真实供应商重试、心跳等待和断网恢复写成 PASS。chain 失败后从正确 Skill 继续、原生文件读写、记忆四视图和主编辑器正文 API 仍需后续单独核销。

新增规则：

1. 取消功能的完成判据必须同时包括真实请求中止、状态收束、空结果不落盘、取消后入口恢复；按钮出现不算完成。
2. 受控 `fetch` 只能证明应用层 AbortSignal 传递，必须在报告中标注“受控验证”，不能代替供应商故障验证。
3. 取消动作不能清除断点；断点是否能从失败处续跑必须由独立闭环验证，不能由“断点对象还在”推导。
### P7-2 chain 断点续跑核销经验（2026-08-22）

| 风险/错误 | 根因 | 改正措施 | 避免再犯 |
|---|---|---|---|
| 重启后虽然本地有断点，chain 仍可能从第一个 Skill 开始 | 断点只在 Pinia store 初始化时读取；项目/流水线打开时序可能使内存值落后于 Electron 持久化值 | 在每次 chain 执行入口重新调用 `refreshBreakpoint()`，以当前项目的持久化断点决定起始 Skill，并恢复 `prevResponse` | “断点对象可读取”不等于“断点续跑成立”；必须验证失败、强制退出、重启、请求次数和成功后清除 |
| 把取消生成当作断点续跑验证 | 取消路径会主动停止生成，不能证明失败后从中间 Skill 恢复 | 使用受控 HTTP 503 让前序 Skill 成功、后续 Skill 失败，再杀 Electron，重启后让后续请求成功 | 取消、供应商失败、进程重启恢复必须分成三个独立闭环 |
| 只看最终生成结果，无法证明没有重复调用 | 最终文本可能相同，且 UI 日志不会可靠显示所有请求边界 | 通过请求计数、请求体是否包含 `prevResponse`、首个请求是否再次出现、Pinia/storage 断点前后值共同核对 | chain 恢复验收至少需要“恢复起点 + 请求次数 + 上一步输出传递 + 断点清除”四类证据 |

新增规则：

1. chain 每个 Skill 成功后必须持久化 `step/projectId/lastSuccessChainIndex/lastOutput`；失败不得清除最后一个成功断点，全部成功后才清除。
2. 恢复前必须按当前项目过滤断点；不同项目的断点不得串用。
3. P7-2 的最小行为证据固定为：双 Skill chain 配置 → 第一步成功 → 第二步受控失败 → 断点落盘 → 强制杀 Electron → 源文件启动器重启 → 只执行第二步 → 成功后断点为空。
4. 本轮只证明应用层对受控 HTTP 失败的恢复逻辑，不证明供应商网络稳定性，也不替代章节层、多卷章节补充生成的专项验证。
## P7-3 章节断点续跑经验（2026-08-22）

- 章节断点必须同时绑定 `projectId + volumeId + total`；不匹配时只能忽略断点，不能清空已有章节。
- 生成结果保存时必须保留同卷未标记 `pipelineGenerated` 的手动章节，防止续跑或补充生成覆盖用户内容。
- 验证章节直接 API 断点时，必须先清空各层 Skill 配置；设定层遗留 chain Skill 会把受控请求拦截在前置层，不能把该结果误判为章节验证。
- Electron 原生 `confirm()` 自动化每次只能注册一个一次性 dialog handler；弹窗变化后重新读取可见 DOM，禁止盲点隐藏按钮。
- 代码实现、构建成功不等于行为闭环通过；没有“失败保存 → 杀进程 → start-electron.bat → 重启 → 正确章节继续 → 清除断点”的证据，P7-3 只能标记部分完成/未核销。

### P7-3 续验收补充经验（2026-08-22）

1. 验证章节层不能只清空 Skill 下拉框；必须逐层检查 store 和 DOM，删除所有已选 Skill chip，并确认隐藏配置没有恢复。
2. 先打印统一 AIService 的实际请求 URL，再按真实供应商域名拦截；抽象路径通配不能单独作为 Electron 网络证据。
3. 生成结束不能只等待 UI 文案；必须同时核对按钮状态、Pinia 生成状态、项目存储和请求计数。
4. 全屏面板遮罩会拦截主页面项目按钮；清理测试数据必须先点击真实关闭按钮，再通过项目管理 UI 删除，不能直写业务存储。
5. 受控 API 命中只能证明统一入口可达；被前置层截获时不能推导章节断点成立，必须按前置请求、目标请求、持久化、重启、恢复分层记账。

### P7-4 真实 API 错误恢复核验经验（2026-08-22）

1. `file://` 页面不能直接动态导入 `/src/services/*.ts` 做运行时验证；这会解析成错误的 `file:///D:/src/...` 路径，导致请求计数为 0。
2. CDP 页面连接、Pinia 存在和按钮 DOM 只能证明运行基线，不能证明 AIService 已执行；错误场景必须有真实请求计数、错误分类和最终状态。
3. P7-4 当前仅核销构建、源文件启动器、CDP 基线和进程清理；网络错误、超时、HTTP 重试、取消及诊断日志保持未核销。
4. 验证载体失败后必须删除临时文件并杀 Electron；不得留下脚本，也不得把载体错误写成业务错误或通过结论。

### P7-4 第二轮服务层核验经验（2026-08-22）

1. `file://` 页面无法导入 `src` TypeScript 时，可用 Vite 对当前真实服务及其依赖做一次性 bundle，再由 Node 执行；必须记录这是“服务层受控 HTTP”证据，不能扩大成真实 Electron UI 或供应商稳定性证据。
2. 网络/超时/HTTP/取消必须分别核对 `calls`、AbortSignal、`AiServiceError.kind`、providerId/purpose/model 和最终日志；只看到异常文字不算闭环。
3. `retry=false` 的网络/超时测试只能证明错误分类与失败收束，不能证明自动重试耗尽；`503 → 200` 且请求次数为 2 才能证明一次 HTTP 重试成功。
4. 取消分支当前在 `params.signal.aborted` 后直接抛出 `canceled`，不会调用末尾 `logRequest`；因此取消诊断日志仍是独立未核销边界，不能把取消错误对象当成日志证据。
5. 临时验证目录、bundle、脚本和输出必须在本轮文档写入后删除，并清理 Electron；保留开发日志与经验文件的核心更新。
6. 自动重试耗尽的请求次数必须按实现真实记录；当前服务层为主重试 `9` 次请求加 `3` 次心跳探测，共 `12` 次，不能只写“发生了重试”。

### 记忆整合异常路径新规则（2026-08-23）

1. `kind=json` 是应用层终态错误，不得进入网络重试或 heartbeat 恢复循环。
2. JSON 修复请求失败后必须在有限次数内结束，UI 必须回到 `loading=false` 并显示中文错误。
3. 网络/超时错误可以按供应商策略重试，但必须保留取消入口，取消后正文和项目状态不变。
4. 异常回归必须同时核对请求次数、loading、错误 DOM、记忆条目和正文内容，不能只读代码。

本轮根因：`AiServiceError(kind=json)` 原先被 `callAi` 的通用网络错误分支和 heartbeat 接管，造成非法 JSON 长时间不收束。修复为 JSON 错误立即结束重试并跳过 heartbeat，网络错误恢复行为不变。

### 大纲工作台导入后编辑闭环经验（2026-08-23）

1. 错误操作：看到 `textarea` 没有 `readonly` 就直接判定“导入后可编辑”，没有验证全局 `keydown` 监听是否通过 `preventDefault()` 吃掉编辑快捷键。
2. 根因：`useShortcuts` 在 `window` 级别处理 `Ctrl+S/Z/Y/F`，没有区分当前焦点是否位于编辑器；浏览器原生撤销、重做和编辑快捷键因此失效，用户会感觉导入后的编辑框“不能操作”。
3. 改正措施：文本输入控件（`INPUT`/`TEXTAREA`）在聊天输入框和查找框之外直接交还原生键盘行为；保留聊天发送和查找专用快捷键，不改变大纲 `v-model`、store 或导入解析链路。
4. 验证要求：必须真实执行“打开工作台→导入→输入→删除→复制→粘贴→撤销→重做”，同时读取 `disabled`、`readOnly`、焦点、`pointer-events` 和内容长度；只查源码或只测试普通字符不够。
5. 边界：本轮源文件 Electron 真实验证使用 `.txt` 导入并通过；`.docx` 解析与安装包客户环境仍需用真实客户样本另行验收，不能把 TXT 证据扩大解释为所有格式均已通过。
6. 清理规则：CDP 探针、临时导入文件和中间测试文件在验证后删除，只保留本开发日志和本条经验记录。

### 2026-08-26 原生文件续验与启动载体经验

1. `start-electron.bat` 输出“Application started”只是批处理输出，不代表源文件 Electron 进程已经存活；必须用端口、进程路径和 CDP 页面三项新鲜证据确认。
2. 封装版进程名可能是产品名而不是 `electron.exe`。执行杀进程前必须读取实际 PID/Path；只杀 `electron.exe` 会留下单实例锁，导致源文件启动器静默退出并制造假性 `9227` 连接失败。
3. 源文件 Electron 的 `dialogWriteFile` + `dialogReadFileAsync` 真实往返可以核销 IPC 文件桥接，但不能扩大解释为客户通过原生文件选择器完成了完整导入导出；二者必须分开记录。
4. 没有 `wa_lastProjectId` 和 `wa_project_*` 的真实项目数据时，不得为了验证重启恢复而脚本注入假项目；只能记录恢复边界未核销，等待真实客户样本或可恢复测试快照。
5. 构建、类型检查、测试 runner、CDP 行为和安装包客户路径是五个独立验证门；任意一个失败都必须保留具体错误和状态，不能用构建成功覆盖其他门。

### 2026-08-26 遗留核销续验经验

1. Windows `start`、工作目录和嵌套引号会制造“安装版启动失败”的假象；诊断时应使用一次性 detached Node 启动载体，并分别检查 PID、CDP 端口和页面 URL。临时载体执行后必须删除。
2. `dialogReadFileAsync` 的返回契约是 `{ path, content }`，验证必须比较 `read.content`，不能把整个返回对象与字符串比较后误报 IPC 失败。

5. Node 原生测试 runner 不兼容 Vite bundler 的无扩展名 ESM import 时，不为 runner 修改生产导入规范；应采用 Vite 兼容 runner 或隔离测试载体，并保留失败原始输出。
