# 内嵌降AI“方法指导者”方案 V3

日期：2026-11-01  
状态：待用户审核；审核通过前不改生产代码  
前置：`_audit/PROPOSAL_2026-11-01_DEAI_DIAGNOSE_ROUTE_RETURN_V1.md`、`_audit/PROPOSAL_2026-11-01_DEAI_MENTOR_GUIDANCE_V2.md`  
范围：生成流水线正文层内嵌降AI、folder SKILL `meta.deai` 契约、流水线 UI、trace、测试守护  
明确排除：应用手动“去AI味”功能、`DeAiSettings.vue`、`EditorPanel.vue` 去AI味按钮、`useDeAi.ts`、`deai.ts` store  
核心定位：**只做方法指导者。生成前教方法，生成后给位置化教学反馈；不改稿、不裁判、不评分、不阻断叙事**

## 0. 用户五条裁决对齐

1. **两套降AI严格区分**：V3 把“流水线内嵌降AI”和“应用手动去AI味”列为两套独立系统。现有纠缠点是流水线后处理读取 `deAiStore.hardRuleMode` 与 `hardRules`，导致用户为手动功能选择 `legacy-auto` 时反向改写流水线正文。V3 将拆开该共享状态，手动去AI味功能保留原状。
2. **补齐旧内嵌降AI退场**：V3 补齐旧三段提示词、`legacy-auto`、`deep-fix` 与流水线读取手动 store 的完整退场清单，按 G0.10 执行七层清零与五证验收。
3. **角色唯一化**：职位只有一个，即“方法指导者”。V2 的“确定性门禁”降级为指导者工具箱中的只读确定性提示；脚本类 AI 味信号只能 advisory，不再承担阻断职责。平台合同失败仍由流水线既有合同验收处理，叙事 verdict 仍归 folder SKILL。
4. **效率保护**：指导包设定硬预算（每步不超过 6 条、不超过 1200 字符）；本地构造零额外 API 请求；执行影子期 before/after 耗时对比；超过阈值自动降条数，不牺牲合同正确性。
5. **应用体现**：流水线进度条徽章、步骤日志、运行记录详情展示指导包摘要与教学反馈；不新增阻塞等待状态，不把内嵌配置混进手动去AI味设置页。

## 1. 背景与根因

### 1.1 两套系统现状

当前应用实际存在两套名为“降AI”的系统，但边界不清：

- **流水线内嵌降AI**：三段链步提示词 `DEAI_METHODOLOGY_PROMPT / DEAI_CREATIVE_PROMPT / DEAI_POLISH_PROMPT` 定义于 `src/services/de-ai.js:1222-1267`，通过 `resolveDeaiPromptForChainStep` 按 `skillIndex` 分发；流水线在 `src/components/pipeline/PipelinePanel.vue:2776-2837` 与 `:3713-3775` 注入；后处理在 `:6090-6294` 按模式执行清洗或修复。
- **应用手动去AI味**：`src/components/editor/EditorPanel.vue:35` 的去AI味按钮、`src/components/settings/DeAiSettings.vue` 设置页、`src/composables/useDeAi.ts` 与 `src/stores/deai.ts` 的独立工作流。

### 1.2 共享状态根因

流水线后处理在 `src/components/pipeline/PipelinePanel.vue:6093` 读取 `deAiStore.hardRuleMode`；在 `:6103-6105` 于 `legacy-auto` 时调用 `DeAiProcessor.processBody` 改写 `finalBody`；`:6220` 的 `deep-fix` 分支同样读取该 store。因此用户在设置页为手动功能选择的模式会影响流水线生成结果，形成两套系统实际共享执行状态。V3 的隔离改造不是文案问题，而是状态源级改造。

### 1.3 质量风险

旧内嵌降AI混杂三种职责：生成前注入约束、生成后改写正文、终步门禁裁决。V2 曾尝试以“指导者 + 门禁”修正，但用户裁决要求只保留一个职位，门禁语义继续保留会造成第二裁判权，违背 G2.9 单一裁判原则。

## 2. 目标与非目标

### 2.1 目标

1. 流水线内嵌降AI成为唯一职位的方法指导者。
2. 两套降AI系统状态完全隔离，互不读取。
3. 旧内嵌降AI语义按七层清零退场。
4. 生成效率不劣化；新增耗时可观测、可回退。
5. 应用 UI 有明确、非阻塞、可对账的体现。

### 2.2 面包修

1. 不改手动去AI味功能、入口、设置与 store。
2. 不做自动改稿、语义裁判、评分器。
3. 不输出“AI味总分”；阈值与词库校准保持 provisional。
4. 不新增“等待作者裁定”状态。
5. 不替 folder SKILL 生成模板。

## 3. 两套系统职责与状态边界

### 3.1 职责矩阵

- **流水线内嵌降AI**：随生成链运行；提供生成前方法指导与生成后教学反馈；配置源为流水线正文层 contract 与 folder SKILL `meta.deai`；trace 属于 pipeline run；UI 在流水线进度与运行记录中体现。
- **手动去AI味**：由用户在编辑器手动触发；提供检测报告、深度修复、硬规则模式；配置源为 `deai.ts` store；trace 属于 DeAi 任务链；UI 在 `DeAiSettings.vue` 与 `EditorPanel.vue` 体现。

### 3.2 隔离硬规则

1. 流水线执行禁止读取 `deai.ts` store 的 `hardRuleMode`、`hardRules`、`mode` 等任何用户手动配置。
2. 手动去AI味禁止读取流水线指导包、教学反馈与 run trace 内嵌降AI字段。
3. 两侧只允许通过共享的只读核心检测器做底层检测，且不得互相传递执行配置。
4. 若新增共享工具必须先登记影响圈并新增隔离负向测试，防止未来再引入跨链读配置。

### 3.3 状态存储

内嵌降AI不新增用户设置项。运行状态仅存 pipeline run trace：指导包版本、条数、字符数、步骤、省略项、ownership、教学反馈、耗时与 zero-diff 标记。手动去AI味的持久化配置保持 `deai.ts` 原状。

### 3.4 共享工具边界

`DeAiProcessor.detectBody` 等只读检测器可以被两层复用，但配置必须显式入参，不得从 store 拉取；流水线侧调用只传流水线自己的 immutable options。若未来某共享工具需要行为开关，必须拆分为两个显式入口，避免共享默认值造成语义漂移。

### 3.5 演进边界

如果以后手动去AI味希望复用指导者方法，只能复用“方法论文本资产”，不得复用流水线执行器、配置或 trace 模型。反向同理。

## 4. 角色定义：只做方法指导者

### 4.1 生成前

生成前指导包按步骤角色分发，每条含方法名、原则、判断方式、边界与示例，禁止只给禁令。S1 教事件密度、因果骨架、场景作用、三测试；S2 教表达、叙事用笔、风格优先、禁止机械执行指标；S3 教最小修复、语义保真、表达微调、信息无损合并。每步最多 6 条。

指导包头部必须声明：

1. 风格卡片是唯一风格 owner，指导包只是默认方法，不覆盖风格选择。
2. 指导是创作方法，不是事后修改清单。
3. 叙事缺口按 SKILL 契约上报，不擅自补设因果。

### 4.2 生成后

教学反馈提供位置、阅读效果、修复方向与 owner 路由；不携带候选全文，不改稿，不输出总分。语义类 findings 默认 advisory，仅供报告与用户观察；重试仍由 SKILL verdict 或平台合同失败触发。确定性脚本信号可列出位置和证据，但不作为链路阻断条件，其用途是让教学反馈更具体、可核对。

### 4.3 不做什么

1. 不修改正文，不改写请求。
2. 不判定叙事是否成立；叙事 verdict 归 folder SKILL。
3. 不输出降AI总分或整体 AI 率结论。
4. 不触发语义重试。
5. 不新增阻断型门禁语义。
6. 不把手动去AI味当作内嵌降AI的后备执行器。

## 5. 应用体现设计

### 5.1 生成前可见

流水线正文层徽章更新为“内嵌降AI：方法指导”。鼠标悬停提示显示当前步骤、指导条数、字符预算与 ownership。进度日志由“17条前置约束 + 硬规则后处理”改为实际指导包摘要，例如“降AI方法指导已注入：S2 6 条，overlap 省略 2 条，风格卡片优先”。

### 5.2 生成后可见

正文层运行详情增加可折叠“方法指导反馈”面板：

- 指导包摘要：步骤、条数、字符数、省略项、ownership。
- 教学反馈：位置摘录、阅读效果、修复方向、owner 路由。
- 效率指标：指导包构造耗时、端到端耗时、重试次数、合同失败率。
- 状态标签：`informational-only`，不提示用户必须处理。

### 5.3 UI 隔离

手动去AI味设置页不出现“流水线内嵌降AI”配置。流水线 UI 不显示手动模式的 `legacy-auto/deep-fix` 字样。运行记录导出的 standard 与 deep 均保留指导包与反馈摘要，便于客户复查。

### 5.4 用户旅程

用户无需配置任何新开关。生成时自动看到方法指导摘要；生成后在运行记录中可展开反馈；反馈不会阻塞下一步。若 SKILL 声明教学所有权，徽章显示“SKILL 自有方法，应用仅观测”，此时应用不注入重复内容。

## 6. 旧内嵌降AI退场计划

### 6.1 退场对象

1. 生成前注入：`DEAI_METHODOLOGY_PROMPT`、`DEAI_CREATIVE_PROMPT` 与 `DEAI_POLISH_PROMPT` 的生产注入路径，以及 `resolveDeaiPromptForChainStep` 在流水线中的调用。
2. 生成后改写：`legacy-auto` 分支、`deep-fix` 分支以及其它调用 `DeAiProcessor.processBody` 改写 `finalBody` 的流水线代码。

4. 旧 trace 语义：`deaiPromptVariant` 的旧枚举、旧 processor 值 `hard-rules-legacy-auto` 与 `deai-deep-fix` 在执行层的新增写入。

### 6.2 保留对象

1. `DeAiSettings.vue` 的手动模式配置。
2. `EditorPanel.vue` 的去AI味按钮与报告入口。
3. `useDeAi.ts` 的检测报告、深度修复、硬规则流程。
4. `deai.ts` store 的持久化结构。
5. story-deslop 方法论资产，用作指导包内容来源。

### 6.3 分阶段退役

- **Phase A：影子建立与隔离**：新增指导包服务、指导 trace 与零行为 diff；同时切断流水线对手动 store 的读取，为流水线后处理引入固定默认或 contract 驱动行为。
- **Phase B：教学反馈接管**：指导包成为生产注入内容；教学反馈进入运行详情；`conflictPolicy` 默认迁移 `skill-wins`；契约升级 V2。
- **Phase C：七层清零**：旧提示词、旧后处理模式、旧 trace 执行层写入、旧测试断言、旧规格文档、旧运行状态与旧构建产物全部清理。

### 6.4 G0.10 七层清零清单

1. 源码：旧三段提示词、`legacy-auto/deep-fix` 流水线分支、跨 store 读取、`resolveDeaiPromptForChainStep` 流水线消费点。
2. 测试：同批迁移 `de-ai.spec.ts`、`skillDeaiContract.spec.ts`、`deaiChainVariantIntegration.spec.ts`、`deai-voice-profile-injection.spec.ts`、`deai-injection-policy.spec.ts`、`runTrace.spec.ts`，新增负向断言旧形态不得回潮。
3. 脚本：封装验证脚本加入旧语义 `rg` 清零检查与隔离负向断言。
4. 规格：更新 folder SKILL 指导手册、经验文件与开发日志。
5. 日志/trace：执行层停止新增旧 processor 与旧 variant；历史 trace 导出时保留兼容读，但不再写入。
6. 运行状态：旧持久化配置迁移并落盘；旧磁盘包健康检查阻断；覆盖导入保留新语义。

### 6.5 五证验收

## 7. 效率设计

### 7.1 成本结构

新增成本主要为提示词长度与教学反馈本地构造。指导包本地构造为同步字符串操作，无额外 API 调用；反馈复用既有检测与验收结果，不重复扫全文时无需新增 O(n) 检测。若复用 `detectBody`，其单次线性复杂度可接受，但必须记录耗时，避免重复检测。

### 7.2 硬预算

1. 每步最多 6 条。
2. 每步总字符不超过 1200。
3. 每步指导包构造耗时目标不超过 5ms；超过时记录 warning。
4. 反馈位置摘录每个不超过 120 字符，最多 5 条。
5. trace 只保存结构化摘要，不重复保存全量提示词。

### 7.3 影子对比

Phase A 期间每次运行记录：

- 指导包字符数与条数。
- 指导包构造耗时。
- 端到端 durationMs。
- 首次 API 调用耗时。
- 重试次数与合同失败率。
- 与旧路径输出零 diff 标记。

达标条件：不少于 20 章、至少 2 个题材、至少 2 个模型；同时输出旧路径与新路径的对比。若中位端到端耗时增加超过 10%，或首 token 增加超过 10%，或合同失败率上升，则先降条数（6→4→3）、精简字符，再复测；不得通过放宽合同验收补偿效率。

### 7.4 回退策略

1. 保留 feature flag 仅用于实现迁移与回退，不暴露给用户设置页。
2. 回退不恢复 `legacy-auto/deep-fix` 旧语义，只退回“无应用教学注入”或“SKILL 自有方法”。
3. 若效率超标由提示词变长导致，先降条数与字符预算；若仍超标，Phase B 延期。

## 8. `meta.deai` 契约 V2

说明：字段名仍为现有 `meta.deai`，本节标题为文档层级描述。

新增合法字段：

1. `contractVersion: 2`。
2. `guidanceOwnership: skill | app | split`。
3. 既有 `generation`、`finalStepDetection`、`conflictPolicy` 保留，但 `suffix-only` 从 Phase B 起与 `on` 不再等价：当存在 overlap 且需要按 SKILL 声明省略时，`suffix-only` 允许保留受影响的指导条目，作为与 `on` 的语义差异。
4. 未知字段仅在导入/体检预检阶段报错并阻断导入，不再只依赖运行时 trace。

推导规则：

1. `conflictPolicy=skill-wins` 且未声明 ownership 时视为 `skill`。
2. `conflictPolicy=app-wins` 且未声明 ownership 时视为 `app`。
3. 报告型或缺失默认为 `app`，但只做教学，不修改正文。
4. `guidanceOwnership=skill` 时，应用不注入应用指导包，只记录 SKILL 自有方法与观测数据。

### 契约

1. `finalStepDetection` 已有 off 断链路；本方案不扩大其职责，只用于教学反馈生成开关，且不参与终态判定。
2. `generation=off` 时生产注入与教学反馈均关闭。
3. agent 路径真实传入 `meta.deai`，集成测试不得传 null 冒充真实链路。

## 9. 20 轮推演

1. **两套系统会不会继续纠缠？** 会，如果不拆状态源。流水线当前读取手动 store 是实锤。方案已将隔离列为 Phase A 硬门禁，并新增负向断言。
2. **只做指导者是否退回改稿?** 不会。指导包只进 prompt；反馈不改稿；处理器调用从流水线退场。
3. **效率会不会变差？** 会，如果无预算。因此每步 6 条、1200 字符、5ms 本地构造、20 章影子对比、10% 劣化降条数回退。
4. **手动功能是否受影响？** 不受。手动功能保留原状，只共享只读检测器，配置显式入参。
5. **SKILL 迭代是否被锁死？** 否。`guidanceOwnership=skill` 后应用退让，只观测。
6. **overlap 会不会漏？** 有风险。按元数据声明的 overlap 清单省略，并 trace 记录省略项，漏项可对账。
7. **教学反馈会不会诱导复述？** 会，如果带旧稿。设计明确不带全文，位置摘录不超过 120 字符。
8. **语义 advisory 是否会变裁判？** 有风险。设计明确 advisory 不改终态、不触发重试，且新增负向测试。
9. **旧语义会不会残留？** 会。测试守护面已查明，必须同批迁移，并有七层清零与五证验收。
10. **trace 会不会膨胀？** 有风险。只存摘要和结构化字段，不重复保存提示词全文。
11. **UI 是否会误导用户？** 有风险。徽章与日志文案必须与实际注入条数一致，反馈标签为 informational-only。
12. **多流水线并发是否受影响？** 指导包为 run 级 immutable 对象，无共享状态，不引入阻塞。
13. **是否影响终步检测？** 不影响。教学反馈不改终态，`finalStepDetection` 只控制反馈生成。
14. **是否会新增等待状态？** 否。无用户裁定状态，非阻塞可折叠。
15. **手动与自动 trace 是否混淆？** 有风险。两者 trace 类型分开，导出保留独立 section。
16. **检测器复用是否会传语义？** 有风险。共享工具必须显式入参，禁止读取 store 默认值，新增隔离测试。
17. **效率数据是否可信？** 必须用同一模型、同题材、同章节数配对比较，排除供应商波动；至少 2 个模型交叉验证。
18. **回退是否会带回旧语义？** 有风险。回退只退到“无应用教学”或“SKILL 自有”，不恢复旧改稿。
19. **文档承诺是否超前实现？** 有风险。手册只写已实现行为，实施后同步更新。
20. **零 diff 是否可信？** 影子期须断言输出逐字节一致；不一致立即停止。
21. **反向质询：V3 最大漏项是什么？** 若只删旧提示词而不切断跨 store 读取，两套系统仍纠缠。因此 Phase A 把隔离放在教学接管之前。

### G0.7 正反推修订

- 正推：用户可见“方法指导”徽章与日志；trace 有结构化指导记录；反馈面板可展开；无新增配置负担；手动去AI味不变。
- 反推：若用户在手动模式选择 legacy-auto，流水线仍不受影响，通过隔离负向断言证明。

## 14. 决策点

1. **隔离优先级**：建议 Phase A 先切断流水线对手动 store 的读取，再接管教学。

3. **旧语义退役节奏**：建议 Phase C 七层清零，不做长期兼容。
4. **UI 体现**：建议徽章 + 步骤日志 + 可折叠反馈面板；不新增用户配置与阻塞状态。
5. **`guidanceOwnership`**：建议纳入契约 V2，允许 SKILL 接管教学。
6. **效率阈值**：建议中位耗时或首 token 劣化超过 10% 时先降条数复测；不得放宽合同验收。
