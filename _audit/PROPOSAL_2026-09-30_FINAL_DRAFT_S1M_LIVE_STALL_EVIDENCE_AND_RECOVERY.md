## 1. 结论先行

本轮 S1M（100 万字档）终稿实测在第 17/20 段进入供应商级低速流式输出，不是应用空转，也不是工具循环：

1. Electron 进程全程响应，窗口可见，任务状态为 `generating`，聊天状态为 `streaming`。
2. 终稿通道本轮无工具调用（`tools: []`），API 调用数停在 18，对应 1 次分段规划 + 17 次分段生成，没有重试风暴。
3. 前 16 段共生成 818,912 字，耗时约 7 小时 57 分；第 17 段单独运行超过 91 分钟仍未完成。
4. 用户可见窗口仍在十位数级别跳动，说明流未断，只是吞吐极低。
5. 当前产品与验证脚本都缺少“段内吞吐/停滞”观测，导致用户只能看到慢，不知道还活着、还要多久、能不能换路。

## 3. 观测缺陷（本轮同时暴露）

1. 心跳只记录任务状态快照，`completedChars` 只在分段完成时更新，段内流式进度没有进入心跳，导致“86 分钟无更新”的假象。
2. UI 有字符计数，但没有吞吐率、滚动平均、预计剩余时间，用户无法判断“活着但慢”还是“死了”。
3. 没有段内停滞检测：只要流不断，哪怕 10 字/分钟也会一直等。
4. 没有分段级恢复：一旦中断，已完成的 16 段不能作为可恢复产物继续第 17 段。

## 4. 解决策略

原则：不恢复预算、不设输出上限、不因为“跑得久”自动失败；但必须让用户看得见真相，并能在供应商劣化时换路。

### 4.1 吞吐观测（必做）

在终稿任务里记录并展示：

1. 当前段已输出字符、启动时间、已耗时。
2. 实时吞吐：最近 10 秒、60 秒滚动 `chars/s`。
3. 预计剩余：按当前段目标字符与滚动吞吐估算，标注“估算值”。
4. 状态三分类：`streaming_active`（有新字符）、`streaming_slow`（低于阈值但仍在动）、`stalled`（可配置时间内无任何新字符）。

trace 中以秒级聚合记录吞吐，不逐字符落盘，避免 37MB streamText 问题复发。

### 4.2 段内停滞检测（必做）

以“最后一次收到 chunk 的时间”为唯一停滞依据，不用总耗时：

1. 默认 10 分钟无任何新字符 → 标记 `stalled`，UI 给出三个动作：继续等待、重试当前段、取消。
2. 不自动中断请求；判定只改变 UI 与 trace，不改变生成语义。
3. 重试当前段前保留已生成部分，优先从当前段部分文本继续，而不是整段重跑。

### 4.3 分段检查点与恢复（必做）

把终稿任务从“内存任务”升级为“可恢复任务”：

1. 每段完成后持久化 `completedText`、`activeSegmentIndex`、任务元数据与 hash。
2. 应用重启或任务中断后，可从第 N 段继续，不重做前 N-1 段。
3. 当前段的部分输出也定期落盘，恢复时优先走“接缝续写”，失败再整段重试。
4. 恢复必须校验源文 hash；源文变了则提示重新开始，不允许拼接错源。

### 4.4 自适应分段（强烈建议）

100 万字按 20 段约 5 万字/段，单段失败或劣化的代价过大：

1. 默认目标段长降到 1 万至 2 万字，段数增加但单段风险变小，进度更细。
2. 保留结构边界优先：优先按标题/章节切分，其次按目标长度切。
3. 若供应商吞吐持续低于阈值，允许任务在下一段自动缩小段长；已开始段不切。
4. 接缝合并沿用现有 overlap 去重逻辑，增加段间衔接校验。

### 4.5 供应商劣化换路（建议）

1. UI 显示当前供应商与模型，检测到 `streaming_slow` 或 `stalled` 时允许用户切换供应商/模型后继续当前任务。
2. 换路只影响未完成段；已完成段与源文 hash 不变。
3. 记录换路事件、前后吞吐对比，供后续选择供应商参考。

### 4.6 验证策略调整

1. S100/S200 继续作为常规回归档。
2. S1M 改为独立长跑 soak 验证，不阻塞日常封装；必须启用分段检查点，允许跨进程恢复。
3. 验证心跳改为读取 `onProgress` 的段内累计字符，修复本轮“心跳无更新”的观测盲区。
4. 验收结论必须区分：`completed`、`active_streaming`、`stalled`、`failed`。长时间低速不等于失败。

## 5. 不做的事

1. 不加 token 预算、输出上限、续生成次数上限。
2. 不因为总耗时自动取消任务。
3. 不把工具调用引回终稿通道。
4. 不用 mock 或缩短源文冒充 S1M 真实验证。

## 6. 实施顺序

1. Phase A：吞吐观测 + 心跳修复（低风险，先让真相可见）。
2. Phase B：停滞检测 + 用户动作（继续/重试/取消）。
3. Phase C：分段检查点与跨进程恢复。
4. Phase D：自适应分段与换路续跑。
5. Phase E：S100/S200 回归 + S1M 带 checkpoint 长跑复测。
