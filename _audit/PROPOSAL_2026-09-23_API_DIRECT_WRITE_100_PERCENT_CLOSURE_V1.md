# 2026-09-23 API 直写系统 100% 闭环方案 V1

## 0. 结论先行

本方案目标不是继续打补丁，而是把 API 直写系统从“核心链路成熟”推进到“定义清晰的 100% 完成度”。

100% 的定义必须先钉死，否则永远无法验收：

1. 已声明支持的工具面、权限、协议、状态机、日志、UI，全部有自动化回归覆盖。
2. 5K / 100K / 1M 三档真实文档，全部在可见 Electron 窗口完成真实用户级操作验证。
3. 1M 档必须按“1M 上下文模型”的真实能力设计：文档地图 + 分段读取 + 分批写入，不允许把 1M 文档塞进单次请求或单次 `replace_document`。
4. 五类供应商协议中，声明支持直写的每一条路径都有真实或协议级双验证；未验证路径必须在 UI 与配置层显式标记，不允许默认可用。
5. 所有失败分支、恢复分支、取消分支、日志分支都有测试与 trace 证据。
6. 最终验收前不升版本、不封装；验收后全量回归 + 生产接线 + asar 启动 + 安装包实测。

不设 token 预算；不设人为执行轮次上限；任何一轮真实用户测试失败，按“失败即停 + 完整重跑”处理。

## 1. 当前基线

### 1.1 已达标

- 直写主链路已通过 7602 字 live 六步实测：改句、增句、删句、移动、整理、重排全部真实写入。
- `direct-tool-intensive` 12 轮单源策略已恢复，生产入口无 `maxToolIterations: 6` 残留。
- 伪工具调用收敛门已实现：一次强纠正，仍失败则本地兜底并明示“本轮未写入”。
- EditTask 状态机已有 checkpoint、documentVersion、contentHash 双校验。
- run trace 三层记录 `actualToolSurface`，DiagLogger 与 run trace 双侧对账。
- 3.60.0 基线：856 条 services 测试通过、type-check 通过、build:vue 通过。

### 1.2 阻止 100% 的缺口

| 缺口 | 现状证据 | 100% 要求 |
|---|---|---|
| 上下文容量模型缺失 | 供应商配置只有 `maxTokens` 输出上限，没有输入上下文窗口字段；`src/services/providerAdapter.ts:81` 只解析输出 | 增加 `contextWindowTokens`，所有请求前做上下文预算 |
| 长文档策略过薄 | `src/services/longDocumentPolicy.ts:14` 只有 1 万阈值与关键词判定 | 升级为任务规划器：文档规模、操作类型、输出预算、供应商能力共同决策 |
| 1M 文档不可单批替换 | `replace_document` 要求完整全文，且单命令 60000 字符上限 | 1M 场景必须走文档地图 + 分段读取 + 分批 EditTask |
| 文档地图工具缺失 | 现有读取依赖搜索与局部读取，缺少结构化总览 | 新增文档地图工具，返回节结构、范围、字符与 token 估算 |

| 供应商矩阵未全实测 | `src/services/providerTools.ts:73` Gemini streaming 仍为 `unverified` | Gemini 流式真实验证；Anthropic / Azure / DeepSeek / OpenAI-compatible 分别验证 |
| 意图语料统计不足 | holdout 28 条，train/dev/test 各不足 10 条 | 语料扩容并重新校准，不允许靠放宽写权限阈值解决 |
| 文档版本口径滞后 | SKILL 协议文档仍是 3.53.x 口径 | 同步到最终版本，工具、权限、边界、trace 全量更新 |
| 外部 SKILL 协议不合规缺防线 | 现状只能事后靠 trace 判别，不能在运行时阻断 | 增加运行时协议防线：schema 校验、未知工具拒绝、参数越界拒绝、trace 标记 |

## 2. 总体架构

### 2.1 分层执行模型

```text
用户输入
  ↓
意图路由（会话状态 + 权限判定）
  ↓
长文档任务规划器
  ├─ 小范围局部修改 → direct tool loop + editor.write
  ├─ 结构移动 / 局部重排 → 定向读取 + 受限编辑命令
  └─ 大范围整理 / 1M 级任务 → EditTask 分批执行
  ↓
上下文预算器
  ├─ provider.contextWindowTokens
  ├─ system + tools + history + editor context + output reserve
  └─ 超预算即降级或分片，禁止静默截断
  ↓
工具执行层
  ├─ 文档地图 / 搜索 / 分段读取
  ├─ editor.write 受限编辑
  └─ EditTask 批次 + checkpoint
  ↓
观测层
  ├─ run trace 三层记录
  ├─ DiagLogger 双侧同步
  └─ UI 实时状态与失败明示
```

### 2.2 1M 场景的硬设计

1M 上下文模型的能力是“能看见 1M”，不是“能一次输出 1M”。因此：

- 读取侧：使用文档地图定位，再按 range 分段读取，每段附带 cursor。
- 修改侧：优先使用 `replace_match`、`replace_selection`、`move`、`insert`、`delete` 等受限命令。
- 整理侧：按章节或批次生成局部修改，不允许要求模型输出完整 1M 全文。
- 安全侧：每批都走完整性校验与 checkpoint；任何批次失败暂停任务，不自动继续。

## 3. Phase 1：上下文容量模型

### 改动

1. 供应商配置新增 `contextWindowTokens`：
   - 默认 0 表示未知，未知时按保守值处理并在 UI 显示。
   - 支持导入导出配置、配置校验、设置页编辑。
2. 新增 token 估算器：
   - 中文按保守比例估算；英文按词与字符混合估算。
   - 与真实 usage 对账后修正本次会话估算偏差。
3. 新增上下文预算器：
   - 输入：system、tools、历史、编辑器上下文、保留输出。
   - 输出：`fits / needs_segmentation / exceeds_provider`。
   - 超出供应商窗口时必须分片、降级读取范围，或明确失败，禁止静默截断。
4. run trace 新增字段：
   - `providerContextWindowTokens`
   - `estimatedInputTokens`
   - `contextBudgetDecision`
   - `usageReconciliation`

### 验收

- 单测覆盖：0、未知、128K、1M、超窗、null、非法值。
- 请求发出前必须能看到预算决策；trace 与 DiagLogger 双侧一致。
- 真实 API 的 usage 与估算误差记录在案，不要求完美，但必须可见。

### 真实用户证据

在可见 Electron 中分别用 5K、100K、1M 文稿触发一次只读分析请求，用户可见：

- UI 显示上下文窗口与预算决策。
- 1M 文档不会被一次性塞入请求。
- trace 里有完整预算链路。

## 4. Phase 2：文档地图与分段读取

### 新增工具

1. `editor.document_map`
   - 返回文档总字符、估算 token、节列表、每节范围、每节摘要长度。
   - 支持大纲结构与普通长文两种模式。
2. `editor.read_range`
   - 输入：`cursor` 或 `sectionId`、`maxChars`。
   - 输出：内容、`nextCursor`、`hasMore`、`range`。
   - 单次返回上限默认 12000 字符，可被上下文预算器下调。
3. 搜索工具增强：
   - 返回匹配位置、所在节、局部上下文、总匹配数。
   - 对超多匹配结果分页，禁止一次性塞满上下文。

### 协议更新

- SKILL 协议文档同步新增工具说明。
- system prompt 明确：长文档必须先地图后读取，禁止连续无计划读取。
- 连续只读不写入的既有策略保留，并增加“读取计划”提示。

### 验收

- 单测覆盖：空文档、无结构文档、嵌套标题、重复标题、超大节、分页边界、cursor 回绕、非法 cursor。
- 1M 合成文档上，文档地图生成时间与内存占用有基准记录。
- 分段读取在 1M 文档上不允许产生失控的 trace 体积。

### 真实用户证据

用户在可见 Electron 中要求“分析整篇结构”，可见：

- 模型先调用文档地图。
- 再按需分段读取。
- UI 实时显示读取进度，而不是长时间无响应。

## 5. Phase 3：EditTask 自动升级与分批执行

### 改动

1. 长文档规划器接管大范围操作：
   - 整篇整理、全篇重排、多章节调整、超过输出安全阈值的任务自动进入 EditTask。
   - 小范围句段操作保留 direct tool loop。
2. EditTask 计划阶段新增结构：
   - 目标章节范围。
   - 批次列表。
   - 每批预期修改类型。
   - 风险标记与完整性校验策略。
3. 执行阶段：
   - 每批完成后写入 checkpoint。
   - 批间允许暂停、恢复、取消。
   - 失败批次进入 `waiting_user`，不自动重试超过一次。
4. UI：
   - 显示总批次、当前批次、已完成修改、失败原因。
   - 恢复与取消按钮状态与 EditTask 状态机严格一致。

### 验收

- 状态机全覆盖测试：正常、暂停、恢复、取消、批次失败、checkpoint 不匹配、终态恢复拒绝。
- 1M 文档整理不允许出现单条 `replace_document`。
- 每批写入都有 `documentVersion + contentHash`。
- 内容守卫两向验证：合法重排通过，人为删节仍阻断。

### 真实用户证据

用户在可见 Electron 中对 100K 与 1M 文档分别发起“统一编号并整理格式”：

- UI 进入 EditTask 进度态。
- 每批完成后编辑器可见变化。
- 中途取消一次，再恢复一次，最终内容完整。
- trace 记录所有批次、checkpoint、恢复、取消事件。

## 6. Phase 4：供应商矩阵与协议成熟化

### 范围

| 供应商 | 验证方式 | 必测项 |
|---|---|---|
| openai-compatible | 真实 live | 工具调用、流式、非流式、收敛、直写 |
| deepseek | 真实 live | 工具调用、长文档、收敛 |
| azure-openai | 真实 live；无密钥时协议级 + 配置阻断 | 工具调用、错误映射 |
| anthropic | 真实 live；无密钥时协议级 + 配置阻断 | tool_use / tool_result、流式 |
| gemini | 真实 live；无密钥时协议级 + 配置阻断 | function call、流式工具调用 |

### 规则

1. Gemini streaming 必须从 `unverified` 变为 `implemented`，或在能力矩阵中显式降级为“非流式工具调用”。
2. 每类供应商至少完成一次 5K 文档六步直写。
3. 供应商不支持工具时必须走 JSON 协议降级，UI 明示协议形态。
4. 供应商上下文窗口未知时，不允许按无限上下文处理。
5. 每条协议路径的错误分支都要有测试：401、408、429、500、流中断、伪工具调用、空正文。

### 真实用户证据

用户在可见 Electron 中切换供应商配置，逐个完成至少一轮“读取 + 修改 + 写入 + trace 导出”。没有真实密钥的供应商，UI 必须显示“未实测协议”，不允许伪装成已验证。

## 7. Phase 5：意图路由与语料成熟化

在进入语料成熟化前，先补一条运行时协议防线，解决“外部 SKILL 或模型输出不遵守协议”这个无法靠文档解决的问题：

### 外部 SKILL 协议防线

1. 未知工具名：直接返回结构化错误，不猜测映射，不静默忽略。
2. 参数 schema 校验：必填缺失、类型错误、越界值、未知字段全部拒绝，并返回可修正错误。
3. 权限校验前置：即使 SKILL 声称需要写工具，也要经过当前意图与会话状态授权；未授权时返回明确错误。
4. 上下文范围校验：读取范围超限、cursor 非法、一次性请求全文时返回结构化错误并提示正确工具。
5. 协议形态标记：每个工具调用在 trace 中记录 `native_tool_call` / `json_protocol` / `rejected_invalid_protocol`。
6. 不合规行为可观测：unknown_tool、schema_invalid、permission_denied、range_invalid 均写入 run trace 与 DiagLogger。
7. 不做的事：不试图在运行时改写模型意图，不静默修复不合规调用。防线目标是“错误可发现、可解释、可阻断”。

验收：构造 20 类以上不合规调用样本，全部被结构化拒绝并双侧留证；不允许任何不合规调用直接落入编辑器执行层。

### 改动

1. 语料规模目标：
   - train / dev / test 每组不少于 100 条。
   - holdout 不少于 200 条。
   - adversarial 不少于 100 条。
2. 语料来源：
   - 社区真实项目语料。
   - 应用真实运行记录。
   - 构造的错别字、近义词、口语、省略、多意图混合样本。
3. 校准要求：
   - 写入类 falseAccept 必须为 0。
   - edit falseRejection 不允许靠放宽写权限阈值解决。
   - discuss / analyze 不允许被权限闸门拦截。
4. 会话状态：
   - EditTask 活动状态优先于单句静态分类。
   - 跨轮任务连续性必须进入路由上下文。

### 验收

- 输出校准报告：每组规模、准确率、误拒、误放行、边界样本。
- holdout 与 adversarial 分开报告，不允许合并充数。
- 任何阈值调整都必须留下前后对比与样本归因。

### 真实用户证据

用户在可见 Electron 中连续执行：讨论、提问、局部修改、大范围整理、任务恢复、任务取消。每类输入都必须进入正确执行形态，trace 记录路由决策与会话状态。

## 8. Phase 6：观测与日志闭环

### 必须记录

1. 意图路由：决策、置信、会话状态、降级原因。
2. 上下文预算：窗口、估算、分片决策、usage 对账。
3. 工具循环：轮次、工具名、参数摘要、结果摘要、孤儿调用检测。
4. 直写批次：命令、目标、结果、documentVersion、contentHash。
5. EditTask：计划、批次、checkpoint、暂停、恢复、取消、失败。
6. 收敛：伪工具调用、强纠正、本地兜底、未写入明示。
7. 供应商：协议形态、流式状态、错误映射、上下文窗口。

### 双侧一致

- run trace 有而 DiagLogger 无，视为缺陷。
- DiagLogger 有而 run trace 无，视为缺陷。
- UI 显示成功但 trace 无写入成功，视为最高级缺陷。

### 验收

- 每类事件至少一条真实 trace 样本。
- 日志体积策略：摘要记录全量，正文按上限截断并标记，不允许静默丢失。
- 导出 JSON 包含完整事件链与文档快照引用。

## 9. Phase 7：真实用户级全量实测矩阵

### 9.1 文稿

| 档位 | 字符规模 | 用途 |
|---|---:|---|
| S | 5K | 快速回归与协议行为 |
| M | 100K | 长文档主线 |
| L | 1M | 1M 上下文能力验收 |

1M 文稿使用确定性生成器构造，包含：

- 500 个左右稳定章节锚点。
- 每章固定编号、固定句式、固定可定位句。
- 少量重复短语用于搜索压力测试。
- 不使用客户真实项目内容。

### 9.2 每档操作

1. 修改指定句。
2. 新增指定句。
3. 删除指定句。
4. 移动指定章节。
5. 统一编号与格式整理。
6. 多章节连续调整。
7. 中途取消后恢复。
8. 导出 run trace 并复盘。

### 9.3 1M 档硬断言

- 不出现整篇 `replace_document`。
- 每次请求的估算输入不超过供应商窗口。
- 文档地图与分段读取可见。
- EditTask 批次全部有 checkpoint。
- 最终文档内容无丢失、无重复章节。
- UI 全程有可理解状态，无长时间空等。
- trace 可完整解释每一次 API 调用与写入。

### 9.4 失败即停

出现以下任一情况立即停止：

- UI 声称成功但编辑器未变。
- 工具失败但 UI 显示成功。
- 1M 文档被单次全文注入。
- 任何批次绕过完整性校验。
- run trace 与 DiagLogger 单侧缺失。
- 意图路由把明确写入请求拦成只读。

失败后必须：

1. 保留现场 trace 与文档快照。
2. 补失败分支测试。

## 11. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 1M 模型输出上限低于整篇文档 | 高 | 强制分批 EditTask，禁止整篇替换 |
| 供应商真实 1M 模型不可用 | 高 | 能力矩阵显式标记；有模型才验收 1M 档，不用小窗口模型冒充 |
| 1M live 耗时长 | 中 | 用户可见分批进度；每批独立 trace；失败可恢复 |
| token 估算不准 | 中 | 与真实 usage 对账并动态修正；预算保守 |
| 语料扩容引入噪声 | 中 | train/dev/test 分离；adversarial 单独报告 |
| 修改面过大导致回归 | 中 | 每 Phase 独立验收；关键门禁测试先行 |
