# 生成流水线下一层提效 Phase 6 方案

## 状态

待审核。本轮只产出方案，不改生产代码。

定位：Phase 5 解决了"计时口径正确、观测不冒充、活跃流不误杀"；Phase 6 解决的是 Phase 5B 账本暴露出的下一层问题：请求编排结构本身把一个可并行的任务串行化了，重试粒度过粗，记忆抽取占住关键路径。按 G1.15，这不是"哪一层慢"的症状层问题，而是编排器、契约、调度、观测四个机制层互相叠加的结果。

## 原始目标

用户原话核心：根据经验文件，对生成流水线"下一层"优化策略做详细方案；尽最大可能推断；评估对应用的实际提升；覆盖影响到最底层。

方案必须回答四个问题：

1. 慢在哪里：用 Phase 5B 真实账本定位，不允许凭感觉。
2. 为什么慢：拆到机制层，不允许停在"模型生成慢"。
3. 怎么改：给出可执行的分层改造，覆盖 trace、调度器、编排器、契约、供应商适配、UI 进度。
4. 改了值不值：每个优化点标注预期收益口径，推断就是推断，不冒充实测。

## 细胞层根因定位

按 G1.15 四层递进拆解，Phase 6 要处理的是机制层，不是症状层：

1. **串行化不是模型慢，是编排结构把任务切成了串行链。** 卷纲层 36.18 分钟流式输出、本地只有 31ms，说明应用没有制造额外等待，但它把 3 卷拆成 12 次首尾相接的请求，每卷必须等前一卷完全返回才启动。
2. **请求策略被 SKILL 形态隐式决定。** `single-volume` 是为契约质量引入的，但它同时把并发空间锁死了。这是"质量修复"和"速度结构"在同一处代码叠加的典型组合层问题。
3. **重试粒度过粗。** 正文层 2 次 retry 是整章级别的重试；如果失败原因是单个小节或单个字段，重试代价被放大到全章。
4. **记忆抽取占用关键路径。** 15.75s 本身不大，但它发生在用户想确认正文的时刻，属于"可异步却同步"的结构问题。
5. **观测还缺吞吐维度。** 现有账本能告诉我们总耗时和流式耗时，但不能输出 `charsPerSecond` 曲线、慢流分类和请求依赖图，导致"慢"无法进一步归因到供应商、网络还是输出模式。

## Phase 6A 观测升级

### 目标

在改任何执行行为之前，先把观测补到能回答"这个请求为什么这么久"的程度。这是 G1.19 的硬前提。

### 设计

扩展 step 级 timing ledger，新增：

- `charsPerSecond`：全程与滑动窗口双口径。
- `firstTokenToLastTokenMs`：首 token 到流结束的纯输出窗口。
- `slowStreamClassification`：`provider_slow` / `network_slow` / `output_mode_slow` / `unknown`，先落 `unknown`，分类规则在 Phase 6B 采样后校准，不允许拍脑袋。
- `requestDependencyGraph`：每个请求记录 `waitFor` 前置请求 id，能画出"哪些等待是依赖必需，哪些是人为串行"。
- `parallelSlotId`：并发改造后用于区分槽位。
- trace schema 升版，旧 trace 不回填，新字段全部可选。

### 关键约束

- 不允许用 prompt 长度除以耗时冒充吞吐，吞吐必须来自真实流式增量。
- 慢流分类在 Phase 6B 之前只允许输出 `unknown`，防止把猜测写成观测。
- 依赖图必须能证明"卷 2 的请求在卷 1 完成前 0ms 发出"，也就是人为串行的铁证。

## Phase 6B 跨模型与跨供应商采样矩阵

### 目标

Phase 5B 只有 deepseek-v4-pro 单供应商样本。按 G1.19 和 G2.11，不允许用单一供应商的吞吐直接推导并发策略是否安全。

### 采样设计

| 维度 | 取值 | 目的 |
|---|---|---|
| 供应商 | 至少 2 家，含当前默认供应商 | 区分供应商级限流与应用级结构 |
| 模型 | 每家至少 2 个模型档位 | 判断慢流是否模型档位特性 |
| 并发探针 | 1 / 2 / 3 并发各一次 | 直接测供应商是否真正并行返回 |
| 输出规模 | 与 Phase 5B 同级 | 保证可比性 |

### 判定规则

- 并发 2 时墙钟接近单请求耗时：供应商支持真并行，Phase 6C 放行并发 2。
- 并发 2 时墙钟接近串行两倍：供应商串行化处理，Phase 6C 保持并发 1，只做契约瘦身与异步化。
- 出现 429 或软错误：记录降级策略，写进调度器的退避规则。

这一步的产出决定 Phase 6C 的并发上限，是整个方案的分支点。

## Phase 6C 调度器与卷槽规划

### 目标

把"人为串行"改成"依赖驱动的受控并行"，同时不牺牲卷纲的连贯性契约。

### 新增组件

**`src/services/pipelineScheduler.ts`**

- 输入：任务依赖 DAG，每个节点声明 `waitFor`。
- 输出：就绪队列与并发槽分配。
- `concurrencyLimit` 默认 1，也就是行为上等价现状；并发值由 Phase 6B 采样结果写入，不允许写死。
- 取消语义：用户取消时必须同时 abort 所有 in-flight 请求，不允许留下半开请求。

**`src/services/volumeSlotPlanner.ts`**

解决并行化后最危险的质量问题：卷名与卷位冲突。

- S1 阶段先串行生成全部卷的骨架与槽位（第 1 卷到第 N 卷的名称、定位、边界）。
- S2-S4 按槽位并行展开，每卷拿到的上下文包含全量槽位图，知道自己前后是谁。
- 槽位预分配后，并行的各卷没有"我该排第几"的歧义，也就没有虚构邻卷的空间。

### 执行形态

- C1：S1 串行，产出槽位图。这一步不许并行，因为它是全局结构决策。
- C2：卷间 S2-S4 并行，并发上限来自 Phase 6B。
- C3：运行时遇到 429 / 软错误，自动降并发并退避重试，不把失败直接抛给用户。

### 为什么这样切

卷与卷之间真正的全局依赖只有"整体结构与槽位"，这个依赖在 S1 一次性收口；每卷内部的展开是局部决策，天然可并行。这样并行不会让第 3 卷不知道第 1 卷在讲什么，因为槽位图已经把全局骨架固定了。

## Phase 6D 输出契约瘦身与 fragment 级修复

### 目标

减少每次请求的无效输出量，并把重试代价从整章降到片段。

### 契约瘦身

- 每个输出字段设定长度上限与"禁止复述输入"规则，超限在 trace 记 `contractViolation`，不静默截断。
- 卷纲层上下文当前 136,499 字符输入、73,910 字符输出，其中存在复述式摘要。瘦身目标是让输出只包含增量决策，不重复上游已给定的事实。
- 复用 Phase 4 的 `repeatedPromptBlocks` 观测，每层建立"最少必要上下文"清单。

### fragment 级修复

- 校验失败时先定位失败 fragment：字段级、小节级、还是整章级。
- 字段级失败只重发该字段的修复请求，携带失败原因与原片段。
- 小节级失败重发该小节。
- 只有结构性失败才允许整章重试。
- 正文层当前 2 retry 若来自局部字段问题，按此改造后预计显著降低重试耗时；具体数字必须实测，不预填。

## Phase 6E 记忆抽取异步化与层间等待消除

### 目标

把不在关键路径上的工作移出关键路径。

### 设计

- 记忆抽取改为后台任务：正文确认动作不等待抽取完成，抽取结果落库后通过事件更新 UI。
- 失败不影响正文确认，只提示"记忆抽取失败，可重试"。
- 层间 gap 观测继续保留；若采样发现用户确认之外还有隐藏等待，登记为新事项，不混入本方案收益。

## Phase 6F 验证方案

### 单元与回放

- 调度器：DAG 就绪、并发上限、取消、429 降级、槽位冲突五类路径全覆盖。
- 槽位规划器：卷名重复、槽位空洞、S1 部分失败三类边界。
- fragment 修复：字段级、小节级、整章级三级路由断言。
- 观测：吞吐字段必须来自流式增量，负数与重叠计时直接判失败。

### Electron 真实 UI

- 可见窗口真实操作，SKILL 通过真实下拉选择。
- 卷纲层并行 run：用户必须能在 UI 看到"第 1 卷 / 第 2 卷 / 第 3 卷"各自的实时进度，而不是一个全局假进度条。
- 取消操作：多卷 in-flight 时点取消，确认所有请求真正终止、无残留写入。

### 真实 API before/after

- 同项目、同供应商、同模型、同 SKILL 配置。
- before 使用 Phase 5B 账本。
- after 至少一次完整端到端 run。
- 对比字段：端到端墙钟、卷纲层墙钟、物理请求数、重试数、首 token、吞吐曲线、上下文字符数、契约通过率。

### 停止条件

以下全部满足才允许收口：

1. 6B 采样矩阵完成，并发策略有数据依据。
2. 调度器取消、降级、槽位冲突路径有测试证据。
3. Electron 真实 UI 看得到每卷独立进度与真实取消行为。
4. 真实 API after run 完成且四类耗时可归因。
5. 端到端墙钟相对 Phase 5B 基线下降不低于 25%；达不到则如实报告差距与原因，不允许用请求数下降冒充墙钟下降。
6. 产物契约通过率不低于 Phase 5B。
7. 无观测冒充：吞吐、依赖图、并发槽位全部来自真实事件。

## 预期收益（推断口径）

以下全部是推断或目标，不是实测，实测数字以 Phase 6F before/after 为准：

| 优化项 | 当前基线 | 预期方向 | 依据 |
|---|---|---|---|
| 卷纲层并行化 | 36.66m / 12 串行请求 | 20-25m 区间 | 前提是 Phase 6B 证明供应商支持并发 2；若不支持则此项收益归零，只保留瘦身收益 |
| 正文层 fragment 修复 | 10.94m / 2 retry | 重试耗时明显下降 | 前提是失败原因确为局部；若均为结构性失败则收益归零 |
| 记忆抽取异步化 | 15.75s 占关键路径 | 用户确认等待减少约 15s | 小但确定，因为它是纯位置问题 |
| 契约瘦身 | 卷纲层 136K 输入 / 74K 输出 | 首 token 与输出窗口缩小 | 收益幅度依赖复述占比，需采样量化 |

最诚实的总口径：如果供应商不支持并发，Phase 6 的确定性收益只有异步化加瘦身，总耗时改善有限；如果支持并发 2，端到端有望从约 53m 进入 40m 以内。两个分支都不预先承诺，以 6B 数据定生死。

## 作者反证表

按 G1.17，对本方案最可能错的假设逐一给出证伪方式：

| 假设 | 最可能错在哪 | 证伪方式 |
|---|---|---|
| 供应商支持并发 2 | 供应商在服务端串行化或限流 | 6B 并发探针：并发 2 墙钟若接近串行两倍，此假设死亡 |
| 卷间并行不伤质量 | 各卷并行展开时丢失全局连贯 | 槽位图契约校验 + 人工抽读 3 卷衔接处；连续性评分低于串行基线则回退 |
| 瘦身不伤产物质量 | 压掉的复述其实是模型的推理支架 | 契约通过率与人工抽读对比；通过率下降则恢复字段 |
| fragment 修复成功率足够高 | 失败原因多为结构性，局部修复救不了 | 统计三级路由分布；若字段级占比低，收益假设死亡 |
| 吞吐分类可靠 | 慢流成因复杂，分类规则过拟合 | 6B 跨供应商采样校准前保持 unknown，禁止先写结论 |

## 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 并行导致卷名或槽位冲突 | 产物结构损坏 | volumeSlotPlanner 预分配 + 冲突测试为发布门禁 |
| 429 或供应商限流 | 并发收益归零甚至变慢 | C3 自动降并发退避，默认并发 1 |
| 取消残留写入 | 项目状态不一致 | 取消语义单测 + Electron 多卷 in-flight 取消实测 |
| fragment 修复引入新 bug | 产物拼接错误 | 三级路由测试 + 拼接后契约整体验证 |
| UI 假进度 | 用户信任损失 | 每卷独立进度必须绑定真实请求事件 |

回滚策略：`pipelineScheduler` 的 `concurrencyLimit=1` 即行为回滚开关；契约瘦身与 fragment 修复各自独立开关，任何一项不达标可单独关闭，不影响其他项。
