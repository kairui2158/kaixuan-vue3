# 客户可交付版本闭环方案 V1（待审核）

> 状态：2026-10-26，基于 V4 交付后未闭环项对账形成，未获批准前不修改生产代码。
> 基准：当前 HEAD `8c5a3038`，版本 `3.108.1`，工作区干净；经验文件 `_audit/神意开发经验总结_v9.md` v9.6.0。

## 1. 目标

把 V4 交付后的全部遗留项收敛为一个可交付客户的版本：live 供应商真实并行验收通过、真实机器性能采样达标、历史验证脚本语义对齐、不适用项正式闭账、版本升级并封装核验、台账与索引收口。最终交付物是一个新版本安装包及其完整证据链，而不是“测试全绿”的口头结论。

## 2. 遗留项闭环矩阵

| # | 遗留项 | 当前判定 | 处置 | 验收标准 |
|---:|---|---|---|---|
| R1 | live 供应商真实并行未验证 | 仍适用（`untested`） | Phase B 用应用内置供应商 key 执行 live 全场景 | 跨层 3 run 并行、同供应商并发不超上限、取消互不污染、排队归属正确、证据无 key 泄漏 |
| R2 | 真实机器性能采样仅 mock | 部分适用 | Phase C 在 live 模式采样 UI 响应与耗时账本 | freeze=0、slowClick=0、点击反馈达标；供应商等待与本地开销分离记账 |
| R3 | 13 个历史 Electron 脚本未复跑 | 适配度降低 | Phase D 分类处置：被新验证器取代则登记 superseded，独有语义则复跑，失效则修验证器 | 每个脚本有明确结论：PASS / superseded / verifier defect / untested 边界 |
| R4 | 无新封装，复用 3.108.1 | 仍适用 | Phase F 升版 3.109.0 并 NSIS 封装 | asar、真实启动、electronAPI、安装路径、SHA256 全核验，旧产物清理 |
| R5 | 流水线未接 per-run `toolRunBudget` | 不适用（架构演进） | Phase E 正式闭账并加负向回归，防止未来误把工具循环接回流水线 | 新增断言：流水线 `routeSkill` 调用不携带 `tools/toolPolicy`；聊天/大纲工具路径不受影响 |

## 3. 执行阶段

### Phase A：基线冻结

1. 记录 HEAD、版本号、`git status` 干净状态。
2. 新鲜执行全量 `npm run test:services`、`npm run type-check`、`npm run build:vue`，作为本轮唯一基线；历史 PASS 不复用。
3. 建 `_audit/TASK_LEDGERS/TASK_LEDGER_2026-10-26_RELEASE_CLOSURE.md` 七节骨架（G0.12）。

### Phase B：live 供应商真实并行验收

1. 使用应用内已配置的默认供应商与模型，不重新输入 key；key 只从应用配置读取，禁止写入日志或证据。
2. 执行 `SHENYI_PARALLELISM_LIVE=1 node scripts/verify-pipeline-parallelism-electron.mjs`。
3. 必测面：跨层三 run 同时运行、同层排队与唤醒、进度条取消只作用于展示 run、provider queue 事件归属正确 run、断点恢复与失败终态后再入。
4. live 失败时先分类：产品缺陷 / 供应商额度或限流 / 验证器口径漂移。产品缺陷按 G1.14 修复后重跑完整门禁；供应商边界如实登记，不得放宽断言造 PASS。

### Phase C：live 性能采样

1. 复用验证器内建性能观测：longTask、freeze、slowClick、点击反馈耗时。
2. 按 G1.19 把耗时拆为物理请求等待、流式输出、本地构建/校验/后处理三段，禁止用总耗时直接判应用卡顿。
3. 预算沿用现行门禁：freeze=0、slowClick=0、点击反馈达标；live 下供应商慢不等于应用慢，必须分离后判定。

### Phase D：历史脚本分类复跑

1. 枚举 13 个 Electron 脚本，逐个标注当前守护的语义与对应生产入口。
2. 分类执行：已被 `verify-pipeline-parallelism-electron.mjs` 或更新验证器覆盖的登记 `superseded`；仍有独有断言的在当前版本复跑；验证器锚点过时的先修验证器再跑。
3. 产出脚本对账表，任何脚本不得以“没跑”或“跑不过就删”收尾。

### Phase E：不适用项闭账

1. 新增负向测试：流水线路径 `routeSkill` 不得携带 `tools/toolPolicy`，防止未来把工具循环重新引入无工具直写链。
2. 在台账写明 R5 不适配依据：`PipelinePanel.vue:2532` 无工具面、`realSkillExecutor.ts:973-975` 仅显式传参才挂工具、`agentOrchestrator.ts:421-433` 已有预算兜底。
3. 不改聊天/大纲的工具路径，不把该闭账扩大成新架构改动。

### Phase F：版本升级与封装

1. 版本 `3.108.1` → `3.109.0`。
2. `npm run build` 生成 NSIS 安装包。
3. 核验链：asar 内容、打包应用真实启动、electronAPI 可用、安装路径可选、SHA256 记录。
4. 按 G1.12 清理旧产物，删除后复核只剩当前版本一套。

### Phase G：台账、日志与仓库收口

1. 补齐 TASK_LEDGER 七节证据与 DEV_LOG，登记 master index。
2. 若 live/脚本复跑产生新教训，回写经验文件并升版本号；若无新教训，明确登记“无新增规则，不更新正文”。
3. 提交 git，确认工作区干净。

## 4. 审核决策点

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| D1 | live 验证供应商 | 使用应用内置默认供应商，不新增输入 | 你已明确应用里有可用 key；验证器已支持从真实配置读取且不回显 key |
| D2 | 13 个脚本处置 | 分类复跑而非全量盲跑 | 避免把已被新验证器取代的旧脚本结果当成新证据，也避免漏掉独有语义 |
| D3 | 版本号 | 3.109.0 | 本轮含 live 验收与负向门禁新增，按仓库惯例升 minor |

## 5. 作者反证（G1.17）

| 假设 | 最可能错在哪 | 证伪方式 |
|---|---|---|
| live 供应商能承载并行验证 | 额度、限流或模型不可用会导致失败被误判为产品缺陷 | 先做单请求探针；失败时按错误码分类，供应商边界不推给应用 |
| 历史脚本失败等于回归 | 验证器锚点可能落后于当前架构 | 先审脚本断言语义，再判产品；修验证器与修产品分开提交证据 |
| live 慢是应用问题 | 供应商排队与流式输出会抬高总耗时 | 按 G1.19 分段记账，本地开销与供应商等待分离后再判 |

## 6. 风险与回滚

1. live 发现产品缺陷：缺陷修复走独立小提交，重跑完整门禁后再进入 Phase F；禁止带着已知缺陷封装。
2. 封装失败：只回退版本号变更，不回退验证证据。
3. 历史脚本大面积失效：优先判定是否为架构演进导致的旧语义守护，必要时将脚本迁移到当前语义而非删除。

## 7. 非目标

1. 不重设计并行架构，不改 V4 已交付的 run 归属、排队门、运行中心。
2. 不改 SKILL 层内容，不改供应商协议。
3. 不把 `toolRunBudget` 接回流水线；该方向已被判定违背无工具直写链设计。

## 8. 成熟度结论（G0.6）

| 层 | 结论 |
|---|---|
| 方案闭环性 | 成熟：5 个遗留项全部有处置路径与验收标准 |
| 验证标准 | 成熟：live、性能、脚本、封装、负向断言均定义；执行结果不预支 |
| 实施风险 | 可控：live 与旧脚本的不确定性已由分类与回滚策略覆盖 |

整体结论：方案可执行、可验收、可回滚。批准后从 Phase A 开始，任何阶段未过门不得进入下一阶段，也不得封装。
