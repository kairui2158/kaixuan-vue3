### 社区共识提炼

1. **Shiki 是语法高亮的绝对主流**：4/4 项目采纳，无争议。
2. **DOMPurify 是 XSS 防线的事实标准**：直接 innerHTML 渲染的项目（CherryStudio、Open WebUI）全部使用；用 react-markdown 的项目靠 rehype 管线达成同等安全。没有任何头部项目用手写正则做安全过滤。
3. **marked 引擎本身不落后**：LobeChat（17.x）和 Open WebUI（9.x）都在用 marked，我们不迁移引擎是有依据的。
4. **没有头部项目自动修复"非法表格"**：它们靠模型输出约束 + GFM 严格解析，渲染侧只做优雅降级。我们的"伪表格归一化"是超出社区的差异化补强，但必须先修根因（模型输出格式）。
5. **中文场景是专门问题**：Vercel 为 streamdown 单独发布 CJK 插件，说明 CJK 断行/标点排版在 AI 对话渲染中是一等公民问题。
6. **流式渲染三条路线**：Vercel 走 remark 增量 + 记忆化（React 专属，不可用）；smd 走 3kB 增量 DOM 解析器（可用但 WIP、表格仅基础版）；最务实的是 rAF/时间窗节流 + 完成后单次全量解析。

## 三、技术选型对比与推荐

### 3.1 渲染引擎：**保留 marked，不迁移**

| 选项 | 采纳者 | 评估 |
|---|---|---|
| 保留 marked | LobeChat、Open WebUI（同引擎） | 内置 GFM 表格；我们已有使用经验；迁移收益为零、破坏面为正 |
| 迁移 markdown-it | CherryStudio | 插件生态更丰富，但我们的需求（表格+高亮+净化）marked 全部可覆盖 |
| remark / react-markdown | LobeChat 部分、streamdown | React 生态绑定，Vue 下引入成本高 |

**推荐**：保留 marked。唯一动作是把两处散落的 `marked.parse` 收编进统一服务并集中配置。

### 3.2 安全过滤：**引入 DOMPurify，替换手写正则**

社区依据：CherryStudio、Open WebUI 均为 dompurify + innerHTML 渲染路线；LobeChat 靠 rehype 管线。我们三处入口中一处裸奔、一处正则半吊子、一处先转义，标准不一。

**推荐**：`ChatMessage.vue` 与 `OutlineWorkspace.vue` 的过滤统一替换为 DOMPurify（默认配置已防 XSS，配合 `ALLOWED_TAGS` 收紧）；`SkillSettings.vue` 的迷你渲染器直接改调统一服务（其输入是我们自己的模板预览，风险低，但统一后维护成本最低）。

### 3.3 语法高亮：**Shiki，按需语言 + 懒加载**

社区依据：4/4 项目用 Shiki。

体积顾虑的处理：Shiki 全量打包约数 MB，但 Electron 场景本地加载无网络成本；采用按需语言打包（json / js / ts / bash / markdown 五种起步），首块代码出现时再动态 import，预计安装包增量 < 2MB，运行时零网络依赖。

备选：highlight.js（Open WebUI 同款，体积更小但观感档次低一档）。若审核时对体积敏感，可降级到此方案，接口设计保持一致。

### 3.4 流式渲染：**rAF/时间窗节流 + 完成后单次全量解析**（不引入新库）

| 方案 | 评估 | 结论 |
|---|---|---|
| streamdown | React 专属，Vue 不可用 | 排除，但其"记忆化 + 未闭合块修复"思路纳入设计参考 |
| streaming-markdown (smd) | 3kB 增量 DOM，理想但 WIP；表格仅基础版（无对齐/多行单元格），与最终 marked 渲染会有样式跳变 | 观望，不引入 |
| rAF/时间窗节流 | 每 100-150ms 或每帧最多重解析一次；流中保持轻量配置，完成后全量最终解析一次 | **推荐**：零新依赖，风险最小，覆盖 95% 卡顿场景 |

### 3.5 表格根治：**双层修复**（根因优先 + 渲染侧兜底）

第一层（根因，收益最大）：在生成流水线/对话的 system prompt 与 SKILL 输出约定中加入表格输出规范——必须使用 GFM 标准表格（半角 `|`、表头后必须有 `|---|` 分隔行），从源头消灭非法表格。落地位置：`aiService.ts` 的 system prompt 注入点（若架构上不便，则在各对话发起处的 system prompt 统一追加一段"表格输出规范"文本）。

第二层（渲染兜底，处理 CJK 特有失败模式）：中文模型高频产出三类"伪表格"：
1. 全角管道 `｜` 代替半角 `|`；
2. 分隔行省略或写成单个短横线（不符合 GFM 分隔行要求）；
3. 行内多余全角空格导致列错位。

归一化函数（在统一服务内、marked 解析前执行）：检测到"连续 2 行以上含 3+ 个管道符的行"时，触发表格重建——全角转半角、补齐分隔行、按列数补齐单元格。无法安全重建时保持原文（宁可显示为文本，不制造错误表格）。

### 3.6 状态徽章：**CSS 类注入方案**（不引入结构化 JSON 协议）

调研发现：头部项目没有"状态词转徽章"的正则替换先例；CherryStudio 等的做法是自定义组件按内容类型渲染（如对思考块、代码块做组件级拦截）。完整结构化 JSON 协议（让模型输出 JSON 再渲染组件）改造面大，涉及 SKILL 层协议变更，超出本次"显示增强"边界。

**推荐折中**：在统一服务的 HTML 后处理阶段，对表格单元格文本做受控替换：仅匹配封闭状态词典（健康/正常 → 绿，警告/偏低/偏高 → 黄，缺失/异常/衰退 → 红），替换为带类的徽章 span。词典封闭可枚举、误伤面可控，且纯 CSS 展示、不改任何数据。

## 五、升级对比与用户体验预期

| 维度 | 现状 | 完成后 |
|---|---|---|
| AI 输出表格 | 非法语法退化成密集文字墙，无表格线 | 真表格：表头强调、斑马纹、状态词彩色徽章，一眼可扫 |
| 代码块 | 灰底等宽字，无高亮无复制 | Shiki 高亮 + 语言标签 + 一键复制 |
| 流式输出 | 每 chunk 全文重解析，长文卡顿 | 平滑节流输出，低端机不冻结 |
| 长报告阅读 | 密集堆叠，层级靠猜 | 段落呼吸感、标题层级、舒适列宽 |
| 安全 | 一处裸奔 + 一处弱正则 | DOMPurify 统一防线 |
| 文本选择与复制 | 全局禁选，对话内容无法选中复制 | 内容区可选中、Ctrl+C 可用、可选右键菜单 |
| 可维护性 | 3 套渲染实现各自漂移 | 单一服务，改一处全应用生效 |

用户体验核心变化：客户打开"主编体检报告"这类结构化输出的第一眼，从"看不懂的文字墙"变成"专业体检单"——这是截图里暴露的最直观差距。

## 六、风险清单（汇总）

1. 归一化误伤：触发条件严格化（连续多行 + 列数一致），无法安全重建时保持原文。
2. 状态徽章误伤：封闭词典（约 15 个词），不匹配不替换。
3. Shiki 体积：按需语言 + 懒加载，增量控制 < 2MB；不可接受时降级 hljs（接口一致）。
4. 三入口收编回归：SkillSettings 预览行为变化需人工过一遍；收编后 rg 确认无散落 parse。
5. system prompt 注入点：若 aiService 不便统一注入，退而在各对话发起处追加规范文本（效果等价，维护点稍散）。
6. 流式节流时序：完成事件与最后一次节流刷新的竞态——完成时强制同步全量渲染一次即可闭环。

## 七、优先级建议

**P0（选择复制，最小修复先落地）→ P1（底座）→ P2（表格，观感差异最大）→ P5（节奏）→ P3（代码块）→ P4（流式）→ P6（回归交付）**

理由：P0 是基础交互缺陷、改动最小且客户可直接感知，先行落地；P1 是其他所有项的载体；P2 直接解决客户截图里的第一观感问题；P5 是低成本高感知；P3/P4 是体验加分项；P6 收口。

## 八、执行保障机制（防遗留、防无效化）

### 8.1 上轮失效根因（诚实复盘）

1. **范围缺失，不是执行走样**：上轮全应用 UI 计划做的是"壳"（气泡形状、字体、配色、布局），Markdown 渲染质量（表格渲染、状态徽章、语法高亮、流式性能、渲染底座统一）当时根本不在计划范围内——客户截图暴露后才补进台账"未排期"。所以不是"做了没做好"，是"当时就没排进去"。
2. **多面漂移**：三套渲染实现并存且无统一底座，改一处不等于改处处，遗漏在结构上必然发生。
3. **完成定义失守**：以"代码存在"代替"真实可用"，缺少真实操作证据，问题只能在客户屏幕上暴露。

### 8.2 本次五道防线

| # | 机制 | 具体做法 |
|---|---|---|
| 1 | 盘点表即合同 | 二.5 的 8 面清单是执行范围基线；执行中新发现展示面，先补盘点表再动工；每阶段验证按"展示面 × 能力"矩阵逐格勾选，不允许只验一个面 |
| 2 | 完成定义 = 证据 | 每阶段走：构建 → 杀进程 → 源文件启动 → 真实操作（固定标准测试输入）→ 截图/剪贴板取证 → 勾选。标准输入固定：XSS 三例、伪表格三类、状态词词典、5000 字长文，结果前后可比 |
| 3 | 机器断言写进完成条件 | `rg "marked\.parse" src` 仅剩 markdownService 一处；`user-select` 断言（body=none 保留 + 内容面 text 清单）逐面核对；断言不过 = 阶段未完成，禁止勾选收尾 |
| 4 | 防无效化 | 每阶段独立 commit；封装前重跑全部断言 + 8 面 × 4 能力（表格/徽章/复制/流式）巡航核销表；经验文件登记"展示面接线台账"——后续任何新面板/新对话必须接 markdownService，断言脚本随仓库保留可随时复跑 |
| 5 | 目标模式纪律 | 一阶段一目标，验证失败不收尾、不剔出队列；连续未过按根因定位 → 最小修复 → 再验证循环，换路径不换目标 |

### 8.3 诚实边界

"100%"靠流程逼近而非口头保证：机器断言把渲染入口收敛变成可自动核查的事实，逐面核销表把范围变成逐格证据，证据链把"声称完成"与"已证明可用"绑死。任何无证据的完成声明，一律按未完成处理。
