## 最高优先级门禁速查（先读再动手）

1. M1 影响圈声明：先列“打算改的”和“可能碰到的”，未列入影响圈的不碰。
2. M6 门禁复读：动手前复读最新 DEV_LOG 与本文件相关章节，修复后回写日志与经验。
3. M8 日志覆盖同步：任何新链路、降级、旁路、执行形态变更，runTrace 与 DiagLogger 必须同步覆盖并双侧对账。
4. M9 权限执行门：写入工具必须在服务层统一授权；入口传参不能替代权限门。
5. M10 测试契约门：测试守护设计意图，禁止为绿灯固化错误契约或只测成功路径。
6. §8 规则 42：流水线每层进度反馈绑定独立 step 与独立日志数组，禁止跨层泄漏。
7. §8 规则 94：UI 有配置入口不等于链路已接入，必须追到真实 API 调用点。
8. M12 正反推研磨门禁：非平凡修复必须先做目标倒推、爆炸半径矩阵、正推风险、反推有效性和优先级证据化修订；同款逻辑分叉必须抽共享收口。
9. M16 同款折叠统一门禁：同一状态语义在多入口折叠/归并时必须用共享映射函数收口；回头审计发现同款分叉时视为 P0。
10. M17 回头看门禁：每次任务收尾前必须执行回头看，对账目标、diff、生产入口全量盘点、同款逻辑/脚本/验证器、日志与测试证据；未执行不得声称完成。
11. M18 方案成熟度门禁：任何方案/修复计划在用户确认或执行前必须给出成熟度结论，未给出视为方案未完成；仅“半成熟”或“局部成熟”时必须明示断点。方案不成熟时不得进入写码阶段。
12. M19 工具面单源门禁：同一请求内工具面必须单源计算；真实 API 请求与 runTrace 共用同一份工具面数据，trace 必须记录 actualToolSurface 而不是入口声明值。
13. M28 构建产物新鲜度门禁：E2E/验证读取 `dist-renderer` 前必须校验 bundle 新于全部 `src` 源文件；新旧并存清零必须覆盖构建产物层，禁止只扫源码。
14. M80 终稿停滞恢复门禁：Pinia 内任务对象跨中断/重试传递前必须先做纯数据快照，禁止对 reactive proxy 使用 `structuredClone()`；慢流容忍请求已有输出后不得再触发物理重连，避免重试首 chunk 重置停滞观测；活动 API 记录必须按 call-id 匹配关闭。验证终稿分段回放时，mock 必须精确分段块优先，禁止让上一段衔接尾巴污染下一段匹配；任务文本与编辑器文本的分隔符口径不同是刻意设计，验证器必须与生产 normalize 同源。（09-30 终稿停滞恢复闭环）
14. M29 封装产物与工作区分层清理门禁：封装核验通过后必须清理旧安装产物，但禁止把未提交源码当成旧留存删除；git 脏状态必须先分类再动。
15. M30 模型输入窗口门禁：上下文压缩只认模型输入窗口，未知窗口必须跳过并留痕，禁止把输出 maxTokens 冒充输入窗口，多 workspace 必须分桶路由。
16. M31 非破坏性折叠身份门禁：二次压缩折叠必须按 retained 消息稳定身份反推折叠集合，禁止用过滤后下标切原始数组；marker 保留必须有独立回归测试。
17. M32 写队列临界区门禁：会话追加/折叠/清空类写操作必须在项目级写队列临界区内读取最新 state 后修改并落盘；禁止队列外先读快照、队列内再合并旧快照。必须补并发追加回归测试。
18. M33 真实输出预算接线门禁：上下文压缩的 reservedOutputTokens 必须来自本轮真实请求的最终 maxTokens（含重试/降级后的有效值），经 apiMeta/meta 显式传递；无法取得时才回落 workspace 路由预算。成功轮、失败轮、folder 轮、text 轮、direct 轮必须有独立接线与回归测试，禁止把 Provider 全局值冒充所有路径的请求预算。
19. M34 trace 请求同源门禁：runTrace 的 requestMessages 必须与真实 API 请求来自同一构建函数；direct、continuation、skill、pipeline 四条路径都禁止用空数组、子集或旧消息源冒充真实请求。技能路径允许 onApiCallStart 占位、onApiCallFinish 回填，但回填必须成功/失败双分支闭环。长流式 run 必须有 debounce 快照落盘与 API call 完成即落盘，崩溃前现场不得只存在于内存；观测落盘失败仍必须 fail-open。
20. M35 计划类变量单一事实源门禁：卷数、已生成卷数、每卷字数、剩余预算必须由统一计划服务计算；single、continue、auto、模板上下文与 prompt 构建全部消费同一结果，写回前必须钳制到计划预算。禁止入口各自读取设置或临时计数，冲突与钳制必须进入 runTrace。（09-19 卷纲计划分叉）
21. M36 路由后工具面单源门禁：工作台入口不得在调用技能引擎前自行用 `forcedIntent || 'auto'` 构建工具面；真实工具面必须由引擎按最终路由结果统一授权并回写 trace。fallback 推荐意图必须消费单一导出函数，禁止入口各自复制类型收窄逻辑。（09-19 意图路由 V5 收尾）
22. M37 协议解析输出形状门禁：兼容协议、降级协议或任何适配层输出给工具执行器的对象，必须与该工具的 `inputSchema` 逐字段一致；内部存储字段（如 `type` / `version`）禁止混入工具入参，可选字段缺省时必须从对象中物理删除而不是置为 `undefined`。新增或收紧 schema 校验时，必须先全仓盘点既有解析器的输出形状并跑真实兼容路径回归。
23. M38 供应商验证分层门禁：供应商能力、协议、live 结果禁止混在同一句“通过”里声明。能力矩阵、协议仿真、mock E2E、真实供应商四层必须独立报告：能力与仿真可本地断言；live 未执行只能写 `untested`；供应商网关差异（如函数名带点被拒）必须登记为事实，不得伪装成应用缺陷或跳过记录。API key 只能经环境变量临时传入，禁止写进仓库、日志、脚本或证据文件。
24. M39 工具循环策略单源门禁：工具循环上限必须由 `toolLoopPolicy` 按场景单源声明，调用方传入的 `maxIterations` 只能向下钳制，禁止入口私自放宽；新增调用场景必须先声明 `scenario`。物理请求、逻辑 API call 与 runTrace 的 usage、usageUnavailable、工具轮终态字段必须同源透传，禁止服务层补齐但记录层丢字段。
25. M40 Electron 级直写实测门禁：API 直写、权限门、工具循环类改动必须用真实 Electron UI 验证，测试契约覆盖写入、修改、删除、跨轮权限翻转、停滞重试与 trace 导出。mock 必须区分“场景全局计数”和“单轮阶段计数”，场景切换与每轮发送都要重置计数；工具成功后的 iteration 请求必须返回正文，禁止回放同一工具调用制造假失败。mock 强行调用未授权工具时，必须断言服务层拒绝且编辑器未变更。（09-20 Electron 直写高强度实测）
26. M41 验证器口径与运行环境对账门禁：验证脚本不得把“离线无上下文基线”与“真实会话上下文结果”混成同一对账口径；每条结果必须分类为 pass、expected-failure、context-sensitive 或 stress-observation，再分别对账并完整落盘。验证脚本修改必须先核对分类器的输入赋值顺序。依赖 Node 原生模块的生产能力禁止在 renderer 动态加载，必须放 Electron 主进程并通过 IPC 暴露；renderer 保留的动态导入仅限 Node 测试环境。（09-20 意图路由 V6 Phase 1）
27. M42 任务收尾清理门禁：每次任务完成声明前必须执行分层清理，删除本轮产生的临时探针、解包残留、可再生成调研载荷、旧安装产物与 blockmap；删除前核对绝对路径仍在预期工作区内，删除后复核不存在并写入 DEV_LOG。禁止把未提交源码、测试、方案、DEV_LOG、经验文件或当前验证证据当成“旧留存”删除；`git status` 脏状态必须先分类再动。（09-20 工作区收尾清理铁律）
28. M43 Electron preload 封装门禁：任何修改 `electron/preload.js` 或主进程 IPC 桥接的任务，在 type-check / test / build 之前必须先执行 `node --check electron/preload.js`；打包后必须启动真实打包产物并确认 `window.electronAPI` 存在，再声明封装完成。preload 是单文件全应用 API 入口，语法级小错误会让窗口可见但所有 API 不可用，且测试可能全部通过。（09-20 3.55.0 首包 preload 事故）
29. M44 Electron 验证脚本门禁：所有 `_electron.launch` 验证脚本必须显式设置启动/单步超时、阶段日志和 finally 强杀进程；启动打包 exe 时不得再传 `app.asar` 参数。验证脚本挂起不算“运行中”，必须能在超时内暴露卡点。（09-20 embedding 验证挂起事故）
30. M46 兜底产品语义门禁：不得为了让验证或测试变绿而改变产品语义。`no_match` 与 `ambiguous` 是两类输入，兜底策略必须分别断言：`no_match` 失败后可安全降级 readonly-discuss，`ambiguous` 失败后必须保持 await-user 并弹 fallback 气泡；两类输入不得共用同一个气泡/继续请求断言。（09-21 意图路由 V6 Phase 5）
31. M47 验证基线新鲜度门禁：Electron/线上验证对账前必须确认离线 baseline 由当前源码生成，且分类器必须覆盖“离线通过但线上分叉”的 live-divergence 形态；旧 baseline 或缺失分叉分类会把观测差异误报成基线缺失。（09-21 意图路由 V6 Phase 5）
32. M48 状态桥同进程门禁：E2E 通过全局状态桥注入 Vue 状态时，必须在同一次浏览器 evaluation 内完成“读取桥、写入 ref、等待渲染”，禁止把含 getter 的桥对象返回 Node 再传回页面；跨进程序列化会丢 getter，形成“看似已注入、实际改了空对象”的假验证。必须用目标弹窗的精确选择器逐个等待，禁止用一个宽选择器等待“任意一个弹窗出现”。（09-21 技能弹窗响应式压力验证）
33. M49 旧入口副本三面清零门禁：为兼容工具链保留的根目录入口副本，必须和生产入口同步语法校验；一旦生产入口迁移，封装校验脚本、构建配置与运行时引用三面都要指向新入口，再删除旧副本。禁止让“无运行时消费者”成为保留损坏旧文件的依据，因为验证器仍可能把它当事实扫描。（09-22 preload 副本残留）
34. M50 验证产物清理脚本化门禁：任务收尾清理不得依赖手工命令一次性删除。必须提供带路径守卫的清理脚本，显式列出可删除目标、校验绝对路径位于 `_data`/`dist` 等预期层、删除后复核不存在，并把清理结果写入 DEV_LOG。（09-22 验证产物清理）
35. M51 路由阈值校准门禁：意图路由阈值、margin 与 OOS 判定必须由校准脚本在同一语料集上输出完整指标（accuracy、writeFalseTriggers、falseRejections、missedRejections、discussBlocked），并记录 baseline；排序必须以写入误触发为硬约束，然后按准确率和误拒/漏拒择优。生产常量、校准产物、trace thresholdSource 三者必须同源一致；发现排序方向或指标口径与社区成熟实现相反时，视为 P0 校准缺陷。（09-22 意图语义路由 Phase 2）
36. M52 路由语料切分与证据口径门禁：意图路由校准语料必须做确定性 train/dev/test 切分，阈值只允许在 dev 集选择，test 集只做未参与调参的最终报告；禁止把当前 falseRejections 数量写成硬上限或筛选策略，禁止为降误拒放宽写入类安全阈值。`thresholdSource` 的样本/示例计数必须与真实数据结构逐项核对后写入，禁止凭记忆或阶段估算生成版本标签。margin-gate 异步裁决必须复用既有 LLM fallback 链路，并覆盖成功、请求失败、非法 JSON、低置信度与超时路径。（09-22 意图路由 V6 Phase 6）
37. M53 校准脚本完整重跑门禁：校准、评估、验证脚本新增数据源接线或改动输入组装逻辑后，必须完整重跑该脚本本体，禁止只用局部测试、导入检查或历史产物冒充接入闭环；声明顺序类缺陷（如 TDZ）必须纳入回头看的“脚本自身执行验证”。回头看不只审生产源码，也要审脚本自身的真实执行证据。（09-22 意图语料自成长 V2）
38. M54 验证脚本 mock 序列对齐门禁：验证脚本的 mock 触发条件必须与真实请求序列对齐，按场景显式声明触发语义；禁止用全局请求计数做分支开关。mock 回放同一工具/写调用被服务层守卫（如 `duplicate_write_blocked`）拦截时，必须先判定是产品守卫生效还是测试脚本制造假失败；守卫行为不得为测试绿灯被削弱。（09-22 意图对抗语料工厂）
39. M55 收敛目标窄化门禁：多轮收敛任务必须在方案中写明“收敛的是可执行证据链，不是泛化完美路由”。停止条件是既定 Silver 安全硬约束清零、连续有效轮满足、完整回归与文档账本通过；不得把 Bronze 误配或真实用户 confirmed 语料缺口伪装成未收敛缺陷。（09-22 意图对抗工厂收敛 V2）
40. M56 收敛轮证据账本门禁：工厂报告的 `inputHash` 只对输入集求值，路由行为修复后同输入集 hash 不变；收敛轮身份必须由“轮次报告 + corpus 输入 hash + Silver 指标 + 扩库动作 + 证据路径”组合登记。禁止仅凭 inputHash 去重，也禁止把同 hash 的行为修复轮虚报成多个有效轮。（09-22 意图对抗工厂收敛 V2）
41. M57 自动扩库留痕门禁：工厂扩库种子必须物理隔离在 factory-only 数据源，永不进入 train/dev/test；每批扩库都要记录来源批次、意图覆盖、暴露的问题与修复方式。种子标签若与产品语义冲突（如“补一段”为编辑器插入语义），必须修种子标签并补正反样本，禁止为绿灯改路由语义。（09-22 意图对抗工厂收敛 V2）
42. M58 编辑任务工具面状态归一门禁：权限面必须与任务状态机归一联动，禁止用“是否传入 task 对象”推断写权限；任务终态后必须移除 task 控件并恢复普通工具面。活动任务期间的控制语义必须三方一致：任务状态机、system prompt 工具面声明、runTrace `actualToolSurface`；任何一方继续消费旧假设即视为未闭环。（09-23 EditTask Phase 5）
43. M59 终态收敛与控制语义门禁：任务进入终态时必须三方同步收敛——`activeTask` 清空、UI 任务条消失、runTrace 保留终态事件；事件同步层禁止用 `getActiveTask() || getCurrentTask()` 之类的终态兜底把终态任务重新挂回活动 UI。`task.resume` 类控制工具必须在 handler 层校验状态，终态任务必须返回明确错误而不是 `ok: true`。测试契约必须同时覆盖成功、取消、失败三类终态，Electron 断言方向必须与单测一致，禁止验证器迁就旧缺陷。（09-23 EditTask 20 轮回头看）
44. M60 交互态与伪元素溢出扫描门禁：默认态 `scrollWidth` 扫描不能覆盖 hover/focus 伪元素（tooltip 等）；伪元素还可能污染 `scrollWidth`，默认态扫描必须用 Range 等方式区分真实文本宽度与伪元素贡献。交互态溢出验证必须读取真实 used geometry（`getComputedStyle(host, '::after')`），禁止脚本自拼“期望矩形”冒充测量结果；Chrome 在 mouseenter 同步段可能返回 `auto`，必须有估宽兜底。左右空间必须独立计算，且要覆盖“两侧都放不下自然宽度”的场景：此时选择空间更大的一侧并收窄，而不是放弃处理或压成最小宽度。封装级核验还要守住验证器自身：`finally` 无条件 `exit(0)` 会吞真实异常，Playwright `boundingBox()` 只有 `x/y/width/height`，绝对像素下限会误伤合法短标签；验证器失败必须先区分产品缺陷与测量脚本缺陷。（09-23 侧栏 tooltip 溢出修复 + 3.59.0 封装）

## §1 改码纪律

### M 系列：改动污染防御（最高优先级）

1. **M1 影响圈声明**：改任何文件前，用 `rg` 列出该文件被谁引用、该函数读写了哪些 store 字段。产出两个清单：「我打算改的」和「这个改动可能碰到的」。超出需求范围的字段/组件/事件一律不碰。
2. **M2 整文件操作禁令**：禁止跨分支/worktree 整文件复制；禁止“重写整个文件顺手清理”。必须用 apply_patch 逐行精准编辑，每行 diff 能回答“这行为什么在这个需求里”。
3. **M3 diff 自审门槛**：提交前 `git diff` 逐行过，每一行必须能归入本次需求。回答不了的行就是污染，剔除或单独说明。
4. **M4 隐藏状态保护**：改“显示/隐藏”逻辑前，先确认它是有意状态控制（v-show 导航）还是死代码。不确定时不动，标记 TODO。
5. **M5 三面引用闭包**：删除类操作前，生产源码、测试脚本、历史资料三面搜索引用。引用未隔离前只关闭入口，不删实现。
6. **M6 门禁复读**：每次修复动手前必须复读最新 `DEV_LOG` 与本文件相关章节，以最新开发经验锚定改动范围；修复后必须重新验证该修复项并回写 DEV_LOG/经验规则。禁止跳过门禁直接改码。
7. **M7 全局层审计**：Overlay 迁移或 z-index 体系变更时，必须同步审计全局确认框、Toast、诊断面板、内联菜单等非队列层；验证矩阵必须覆盖“全局确认层高于所有 Modal 队列成员”的反向层级，并对每个确认入口做真实点击回归。只验证宿主 Modal 打开/关闭不能证明其内部 confirm 可见可点。（09-13 重置对话回归）
8. **M8 日志覆盖同步门禁**：任何功能、修复、降级、旁路或执行形态变更，必须同步对账 runTrace 与 DiagLogger 覆盖：新链路的工具调用、权限决策、降级原因、直写呈现、终态与失败现场都要进入日志；验证时必须对账事件类别与数量，并检查 renderer 与主进程双侧一致。工具未被暴露时的 `tool_not_found` 拒绝同样是失败现场，必须写诊断日志；只把错误回传给模型不算覆盖。缺覆盖不算闭环。（09-14 直写补验扩展为全局门禁；09-19 Phase 1 补 tool_not_found 分支）
9. **M9 权限执行门禁**：写入类工具必须在服务层统一执行门校验，禁止只依赖入口“自觉不传工具”。`discuss/analyze` 只读，不得暴露任何写入工具；`edit/generate` 才可暴露并执行 `editor.write`；pipeline 禁止交互式写入工具。`editor.propose_edits`、`pending_user_confirmation` 确认预览链路全应用禁止回流。单测与 E2E 必须断言权限门本身，不得用 mock 行为或“请求发出即通过”冒充安全验证。（09-16 API 直写成熟化修订）
10. **M10 测试契约门禁**：测试是设计意图的守护者，不是现状代码的复读机。发现产品行为与既定方案冲突时，先修产品并同步测试契约；禁止为让测试变绿固化错误行为，也禁止 E2E 场景只覆盖成功路径而不覆盖拒绝路径。（09-14 直写 E2E 审查）
11. **M11 意图语义单源门禁**：权限相关的显式意图规则必须由 `classifyChainIntent()` 和 `routeChainIntent()` 共享；新增“直写/直接写入”等祈使词时，两条分类入口、单测和真实 UI E2E 必须同步覆盖。禁止只修 UI 路径导致服务路由语义分叉。权限问句不得短路终判：命中“有没有写入权限”后必须二次判定句内是否含祈使写入或试探性写入指令，纯问句才保持 discuss。（09-17 权限问句复合写入修订）
12. **M12 多轮正推/反推研磨门禁**：非平凡修复进入执行前必须完成五步研磨，禁止把“最小改动”当成免检理由：
    1. **目标倒推**：从用户最终可感知行为倒推最小改动点，再正推该改动会引入什么新风险；不得从代码现象直接跳到点修。
    2. **爆炸半径矩阵**：逐项列出“会砸到谁”——组件、store、协议、测试、日志、安装包；未列入矩阵的联动面不得被动。
    3. **正推验证**：证明“这样改后目标行为能生效”，并逐条标出新 BUG 风险和对应防线。
    4. **反推验证**：反向质询“最小改动能生效吗？”“只修一处够吗？”“现有链路会不会绕过它？”任一问不出来源或反例，方案不能定稿。
    5. **优先级证据化修订**：用反推证据决定升降级；证明不阻塞本轮目标的项降级保留后续项，不能用猜测扩大改动。

    同款逻辑、同款校验或同款解析规则已分叉 2 处以上时，必须优先抽共享函数收口；禁止只修本次触发的入口，让其他入口留到下次复现。（09-15 Outline Trace 多轮递归修复方法论）

    **09-16 修订（防假研磨）**：正推/反推不得停留在“逻辑看起来成立”，必须锚定到至少一条真实用户路径或真实代码入口。以下情形均视为假研磨，方案不得放行：
    - 只验证执行器本身，不验证入口到 API 的真实工具面传递。
    - 用 mock 强制返回目标工具调用，冒充“入口真的把工具递给模型”。
    - 只覆盖成功路径，不覆盖“纯文本确认 → 短批准 → 提案/写入 → UI 呈现”这类真实交互链。
    - 只比较设计参数是否写对，不检查 trace 里实际请求、实际工具面、实际终态。
    - 正反推结论与测试证据断档，无法证明“目标用户行为已经生效”。

13. **M13 调用路径门禁**：新增或迁移任何 AI 外呼、后台任务、基础设施探测、chain 交接和终态归并，必须先声明 Trace 归属；run/API/turn 状态只能由统一归并函数判定。禁止新入口先上线、日志补查靠用户复现。（09-15 调用路径审计 V2）
14. **M14 Trace 降级与 schema 门禁**：Trace 是观测层，落盘失败、目录锁定或磁盘满必须记录 `autosave-failed` 并 fail-open，禁止把观测故障冒泡成生成失败；Trace 导出结构变更必须同步升级 `schemaVersion`、更新导出按钮版本和旧数据兼容测试。并发/迟到收尾冲突必须在统一归并函数写入 `status-conflict-ignored`，被忽略的收尾也是必要证据。（09-15 Trace 加固 V2）
15. **M15 状态审计门禁**：模块生命周期/资源状态变化必须经过状态守卫、统一收口函数或带原因的 `stateHistory`；新状态必须在映射表注册，禁止状态语义随调用方漂移。活跃态必须有看门狗、终态必须闭合、看门狗/完整性检查只观测不抢改业务终态。Trace 新增状态证据必须同步 schemaVersion 与兼容测试。（09-15 状态审计 V2）

### 通用改码规则

1. **行为等价**：新架构必须复现旧架构的行为语义，不只是代码语义。旧代码禁止直接复制。旧行为唯一基准：`C:\Users\凯瑞\Documents\New project 2\旧架构分析集`。
2. **新架构写法标准**：业务状态放 Pinia store，组件用 computed 读取，子组件通过 emits 通知父组件，联动靠 store 更新 + computed/watch。同一业务数据只有一份事实来源。
3. **一次一个闭环**：改码 → 构建 → 杀进程 → 重启 → 验证，闭环完成才进下一个。禁止批量改无关功能。
4. **先读代码再改**：用 apply_patch 编辑，验证后再声称完成。工具调用失败 2 次换方案。
5. **store 是唯一事实来源**：用户重新打开还需要的状态必须放 store 或 storage，禁止组件本地 ref 存业务数据。
6. **saveConfig 不得重新赋值 config.value**：持久化函数只负责写盘，禁止重新赋值整个响应式 config。调用方已原地修改 `config.value`，再重新赋值会触发消费组件 `watch({ deep: true })`，watch 再回调持久化，形成死循环并占满主线程，表现为全应用鼠标键盘无响应。根因是持久化函数同时承担状态赋值和写盘两个职责。（09-03 coCreation 冻结）
7. **compose 不得丢失 folder 技能对象**：`combineComposeTemplate()` 只拼 template 字符串会让 folder 技能退回 text 路径，pre/post 脚本与 schema 失效。找到带 `skill` 的模板后必须展开保留原对象，仅合并 template、validationRules、outputSchema、retryPolicy 等组合字段。（09-07 compose folder 修复）
8. **utilityProcess 通信用 `process.parentPort`**：worker 内不要假设 `ipcRenderer` 或父级全局回调存在；用 `process.parentPort.on('message')` 接收、`postMessage` 回包。第三方 SKILL 脚本必须持续隔离，blocked 尝试后同一 worker 仍可继续服务。（09-08 深扫 P0）
9. **窗口状态防抖且退出立即落盘**：`resize/move` 走 500ms debounce，`close/before-quit` 清 pending timer 后同步保存；否则拖动窗口高频写盘，退出丢失最后位置。（09-08 深扫 P1）
10. **storage 导入与写入同级原子化**：`storage:import` 采用临时文件 + 备份 + 原子替换，并按 key 进入与 `storage:write` 相同的写队列；导入绕开队列会与自动保存竞态覆盖。（09-08 深扫 P2）
11. **入口语义必须匹配对话框类型**：UI 要求用户选择“文件夹”时必须调用目录选择器，禁止复用文件选择器让用户点到内部文件。批量导入的“无结果”要区分 `ok:false` 与 `ok:true + 空数组`；后者常见于选中目标对象本身，应先探测对象本身是否合法并给“返回上一级”引导。（09-08 Folder 导入入口）
12. **浏览器入口 re-export 的传递依赖必须真实安装**：browser 入口若 re-export 另一个包（如 `@node-rs/jieba` -> `@node-rs/jieba-wasm32-wasi`），被 re-export 的包也必须安装；缺失时 Vite 预构建失败并用错误浮层盖住页面。装包后必须重启 Vite dev server 清理 `node_modules/.vite/deps`，只重启 Electron 无效。（09-16 API 直写成熟化收尾）

## §2 脚本纪律

1. 选择器必须先诊断：用 `rg` 确认 ID/class 存在且唯一，禁止凭假设写选择器。ID 选择器必须加 `#` 前缀。
2. 复杂脚本必须写 `.cjs/.mjs/.ps1` 文件执行，禁止 PowerShell 内联嵌套引号/JSON/正则；超过两层嵌套直接写文件。
3. 所有写操作必须 `try...finally` cleanup，异常退出不留脏状态；检查脚本保持 100% 只读。
4. `page.evaluate` 内 electronAPI 调用必须 async/await，返回值不能拼成 `[object Promise]`。断言持久化必须读真实业务字段。
5. CDP screenshot 必须设 3-15s 超时（`Promise.race`）并降级为视口截图，失败不阻塞状态断言。
6. 脚本执行后必须显式 `process.exit(0/1)`，禁止依赖事件循环自然结束；但 `process.exit` 必须放在顶层 `try...finally` 之后，禁止在成功路径的 try 内直接退出，否则会跳过 finally 清理，留下专用 profile 与 Electron 进程。（09-13 确认框层级修复）
7. `v-show` 元素验证用 `getComputedStyle().display !== 'none'`，不用 `offsetParent`；`v-if` 元素条件不满足时不存在 DOM。
8. 切换会话/载体前，先确认上一个 Electron/CDP 实例是否存活；启动器 PTY 不能随意 Ctrl+C。
9. CDP 探针固定三段式：前置快照 → 业务操作 + 逐操作断言 → 恢复原状 + finally 清理核销。缺任何一段不算闭环。
10. 每段结果写入同一个 JSON 输出文件，台账只引用 JSON 原始字段值；`allStepsOk` + `runtimeErrors:[]` 是最终 PASS 判据。
11. CDP 用 `Runtime.evaluate(async () => {...})` 包整段逻辑，返回值必须 `JSON.parse(result.result.value)`。
12. Node 侧没有 `document`；`Runtime.evaluate` 里的 DOM 代码是字符串模板由浏览器执行。写探针前分清 Node 跑什么、页面跑什么。
13. Promise 未 await 排查法：探针里先加 `await setTimeout(300)`，好转修探针，仍失败才升级为业务发现；探针时序问题不许顺手改业务代码。
14. 溢出扫描从正确的滚动根上找元素：全页用 `root: body`，模态框用容器选择器；按 overflow 分三类，只有 `visible-vertical-overflow` 才算缺陷。
15. monkey-patch 验证法：evaluate 里临时替换 `window.electronAPI` 方法，记录参数和返回值，finally 还原；断言“调用发生过”用调用记录数组。
16. Playwright evaluate 只接受一个参数，多参数必须包成对象 `{ sel, key }` 传递。
17. 验证后必须 restore 原始配置，finally 保证执行；真实 API 调用验证设 300s timeout，mock 与真实分开。
18. 源 Electron 启动用仓库内完整路径 `node_modules\electron\dist\electron.exe`，参数 `. --remote-debugging-port=9227`，Hidden 窗口，启动后等 8 秒再连 CDP。
19. 流水线全屏面板关闭后必须显式点击 `#btn-close-pl` 再操作主页面；倒序关闭会被遮罩拦截。
20. 恢复项目时 store getter 同步但 IPC 持久化异步；finally 读 `lastProjectId` 前要等恢复操作的 IPC promise 返回。
21. 多轮上下文探针的“当前轮次”必须读取最后一条 user 消息，禁止用整段 messages 拼接包含历史标记判定 phase；否则第二轮被第一轮历史污染。
22. mock AI 响应必须按 phase 显式映射，禁止根据“历史里是否包含某标记”返回内容；否则测试数据反向污染业务断言。
23. 覆盖 aiService 心跳重试等待的 CDP 长事务超时至少 360s；短超时会把“仍在等待”误判成失败。
24. 上下文探针前后必须清理 `ctx-probe-*` 测试键和 `wa_lastProjectId` 残留；未恢复原项目不得开始下一轮断言。
25. 本地 mock 供应商真实操作模式：备份 `_data/wa_providers.json` 及 `.bak` → 写入探针供应商（明文 apiKey 合法，store 只解密 `enc:` 前缀）→ 源 Electron + CDP 真实点击 → finally 恢复备份并清除 `wa_chat_*` / `wa_continuation_*`。
26. 源 Electron 数据目录是 `process.cwd()/_data`，打包版是 `Documents/神意助手数据`；探针断言和备份路径必须按启动形态选对。
27. 跨供应商截断探针的 mock 必须返回非标准 finish_reason（如 `max_tokens`）验证归一化为 `length`；续生成分支判定必须读最后一条 user 消息，不能扫全历史。
28. CDP 探针一律使用 Node WebSocket 载体执行 JS 文件；禁止用 PowerShell `ConvertTo-Json` 传输含中文/复杂字符串的脚本。Windows PowerShell 5 会按 ANSI 读取无 BOM UTF-8，造成中文损坏和 `SyntaxError`。
29. 批次预览切换命令项后必须恢复原选中状态再点击应用；未恢复会让 acceptedIndexes 缺失，产生“只应用 6/9”的假失败。探针状态污染先查探针，再判应用缺陷。
30. mock 服务的性能分支命令构造必须与断言的命令结构一致；过滤式构造会返回错误结构，导致产品正常但探针稳定失败。
31. 测试脚本禁止伪造元数据兜底（例如用 hash 构造 outlineBatchTarget）；前置条件不满足应直接失败并报告缺失，不得制造假失败后误判应用缺陷。
32. 多场景共用 mock 服务时，命令 target 必须按请求中的场景标记动态返回（如 `L3_MAIN` / `L3_OUTLINE`）；硬编码单一底稿会让另一场景稳定 `target_not_found`。
33. CDP 查找功能按钮必须使用功能容器级选择器（如 `.chat-edit-command .msg-btn`），不能只扫通用 `.msg-btn` 后按文本匹配；消息操作区存在多个同名 class。
34. 回归探针断言“本批次”时必须先从 store 锁定本用例的 `editorBatchRecord.targetId` 和 `batchId`，再按消息索引定位 DOM；仅按按钮文本查找会误点其他用例残留按钮。
35. 跨用例回归 runner 的 reload 初始化门必须等待项目 ID、供应商 ID 和 provider 列表全部稳定；只等 Vue 根节点会让异步 store 加载覆盖探针注入状态。
36. 脚本编辑涉及 Vue/TS 字符串时禁止内联复杂转义；每次修改后立即 type-check、diff-check，并检查字面量转义损坏。
37. Electron 33 / Chrome 33 组合下，`disableHardwareAcceleration=true` + `contextIsolation=true` + `nodeIntegration=false` 会让 CDP Runtime/Page/DOM 域完全假死：`Page.getNavigationHistory` 可用但 `Runtime.evaluate`、`DOM.getDocument`、`captureScreenshot` 全部 120s 超时。这是环境限制；应降级为构建产物扫描 + type-check + vitest + build:vue，UI 验证降级为用户实测。
38. `build:vue` 中主应用 `vite build` 必须在 `vite build --config vite.protocols.config.mts` 之前执行；主构建 `emptyOutDir: false` 会清空 dist-renderer 但保留目录，protocols 随后写入 `.cjs`。反序执行会导致 Electron `require('./dist-renderer/providerProtocols.cjs')` 崩溃。
39. 多窗口 Electron 中，`lifecycle.js` 必须拆分 `registerLifecycleHandlers()`（全局 IPC，`registered` flag 保证一次）和 `registerWindowCloseHandler(win)`（每窗口 close 事件）；`createWindow()` 末尾调用后者。混在一起会导致第二窗口重复注册 IPC handler。
40. 多窗口项目锁用 `windowMap`（windowId → { projectId, browserWindow }）+ `lockedProjects`（Set）；`window:openProject` 先查锁，已锁则 focus 已有窗口并返回 `already_open`；窗口 closed 清理两个集合。第一版禁止同项目多窗口，防止写冲突。
41. 探针断言键名前必须读真实实现：上下文存储真实键是 `wa_ctx_${projectId}`，不是设计语义里的 `wa_context_${id}`；协议字段按请求体真实命名，OpenAI 兼容请求用 `max_tokens`，mock 和断言兼容 `max_tokens ?? maxTokens`。
42. 成功路径夹具必须与断言语义匹配：带 `schema.json` 的 folder-full 夹具要求 JSON 输出，用普通文本 mock 断言成功会触发 3 次重试后 degraded。验证成功输出用 folder-minimal；验证 schema 重试才用 folder-full / folder-retry。
43. `exec_command` 不带提权执行时禁止传 `justification` 参数；该参数必须与显式提权配套，否则调用直接被拒绝，造成假阻塞。
44. ZIP 测试夹具可以手写字节流：local file header + central directory + EOCD；Electron yauzl 解包不校验 CRC，夹具 CRC 填 0 可通过。只有真实安装包强校验时才必须计算 CRC32。
45. 验证 preload 桥必须先 `npm run build:vue` 再重启源 Electron；只改 preload/主进程不重跑构建，会拿旧 dist-renderer 判定新桥不存在。
46. 源 Electron 启动失败先排查残留进程：上一轮 CDP Electron 未杀干净会占用 remote-debugging 端口和 userData，表现为新窗口无响应或启动即失败；启动前按命令行匹配 electron.exe 并确认端口释放。
47. Pinia reactive 数组/对象直接经 IPC `storageWrite` 会报 `An object could not be cloned`；探针写入前必须 `JSON.parse(JSON.stringify(...))` 深克隆成纯对象。
48. 手写 CDP WebSocket 探针必须在握手升级完成后再发第一帧；否则帧写进 HTTP 握手流导致 Runtime.evaluate 永久超时。Node 22+ 优先直接用全局 `WebSocket(url)`，不要手写 net + Mask 帧。
49. CDP 消息路由必须用数字 `id` 匹配并临时挂载/摘除 handler；共享 listener 会让无关事件污染当前断言。断言返回值兼容 `JSON.parse(result.result.value)` 与对象两种形态。
50. 探针断言必须覆盖目标语义，不能只看“脚本能跑”：验证 ZIP 中文文件名时 entries 必须包含真实中文条目，只断言 ASCII 条目通过等于假验证。
51. 独立 Node 探针 require Electron 主进程模块时，先确认目标函数在 `module.exports` 中；内部函数未导出会得到 `undefined is not a function`，应补导出后跑单测化验证。
52. Node 24 复杂内联脚本（含 WebSocket/JSON/中文断言）必须落盘 `.cjs` 执行；内联超过两层引号稳定产生 `SyntaxError: missing ) after argument list`。
53. 全应用间距统一必须用脚本批量替换，不可手动逐行改；且替换列表必须按 px 值长度降序排列，避免 `2px` 先替换 `20px` 中的子串。（09-06 间距统一）
54. stylelint-config-standard 对 Vue SFC 解析会报 CssSyntaxError，只对 `.css` 文件运行 stylelint。（09-06）
55. stylelint-declaration-strict-value 的 ignoreValues 正则参数会导致 cosmiconfig 崩溃，只使用 ignoreKeywords。（09-06）
56. UI 自动化验证脚本不得依赖易变的技能名称定位卡片，必须使用稳定结构特征（如 `.skill-card-badge.is-folder`）。（09-06）
57. 旧 Electron 进程可能持有重建前已卸载的旧页面，报“异步组件 nextSibling 崩溃/组件不存在”时，先杀进程并重启源 Electron，再判断源码缺陷。（09-07）
58. 分包策略会把被静态引用的组件打进主 chunk；不能以“异步页面 chunk 缺少新特征词”反推构建产物过期，必须同时扫描主 chunk 或直接重启源 Electron 复测。（09-07）
59. 验证 asar 内文件禁止在仓库根目录执行 `asar extract-file`；该命令会直接向当前工作目录写出同名文件，曾把安装包内精简版 `package.json` 覆盖工程清单。必须用 `@electron/asar` API 读取内容，或在临时目录 extract。（09-08）
60. 用 `git show HEAD:file` 恢复文件前必须先确认 HEAD 版本；本仓库 HEAD 停留在旧版 3.20.2，直接恢复会把旧清单带回工程。恢复优先级：未损坏构建产物/锁文件/git unreachable blob > HEAD。（09-08）
61. 运行记录面板空态时详情 Tab 不渲染是预期行为；详情区整体在 `v-if="selectedRunTrace"` 内。验证四 Tab 前必须先向 Pinia store 注入一条真实结构的测试运行，不得把空态判成 Tab 缺失。（09-08 运行记录）
62. 源 Electron CDP 验证 Pinia store 前先确认全局暴露路径；本应用开发模式可经 `window.__pinia._s.get('runTrace')` 取 store。直接假设 `window.runTrace` 不存在会导致探针空转。（09-08 运行记录）
63. 验证 scoped 样式里的 `user-select: text` 时，探针元素必须带真实渲染后的 `data-v-*` 属性；新建无 scoped 属性的探针节点会继承 body 的 `user-select:none`，把正常功能误判为失效。（09-08 运行记录）
64. 运行记录导出的脱敏必须双侧执行：renderer 的 `exportRunToJson()` 与主进程 `runTrace:export` 各自递归脱敏。只做一侧时，绕过 UI 或后续新增调用点会泄漏 API Key。（09-08 运行记录）
65. 旁路运行记录必须先核对“运行入口是否可能早退”：在 provider/API Key 校验前启动 run 的路径，每个早退 return 都要 finishRun，否则留下永久 running 残留。（09-08 运行记录三期）
66. 抽出共享面板时不能只搬当前入口的默认筛选：来源筛选按钮依赖 filteredRuns 有数据才渲染，空态探针返回 0 个筛选按钮是正常现象，不能误判为 UI 丢失。（09-08 运行记录三期）
67. 手写 CDP WebSocket 客户端帧必须设置 mask 位并携带 4 字节 masking key；未 masked 帧会被 Chrome 静默关闭，症状是脚本 0 退出且无任何输出。（09-08 运行记录三期）
68. CDP WebSocket 响应监听禁止 `once: true` 挂在通用事件总线上；Electron/DevTools 先推送任意事件就会消耗监听器，`Runtime.evaluate` 响应永远收不到，症状是脚本挂死。需要多事件匹配时用 `Promise.race` 或条件 resolve；复杂 CDP 探针优先 Playwright `chromium.connectOverCDP`，不要手写帧协议。（09-12 3.38.0 E2E）
69. “重置 API 记忆”类功能必须同时清 UI 会话与 ConversationContextService 作用域会话：模型没有跨请求后台记忆，跑偏来自应用每次重复打包历史；只清 UI 不清上下文服务会让下一次请求继续携带旧偏差。清空动作必须按 projectId + workspace + purpose 精确作用域，禁止全局清上下文。（09-08 对话上下文重置）
70. 源 Electron E2E 验证脚本若未传 `--dev`，实际加载的是 `dist-renderer` 构建产物；每次改前端源码后必须先 `npm run build:vue` 再跑验证，否则验证旧 bundle，产生“代码已改但现象不变”的假象。（09-11 运行记录深度化 V2）
71. Pinia reactive 数组滚动清理时禁止把 `splice` 返回的响应式代理用于后续目录删除等操作；应先 `slice` 出保留/移除数组并整体替换，再对普通对象执行异步清理，否则 `dirName` 等字段读取会被代理状态干扰。（09-11 运行记录深度化 V2）
72. WeakMap 不用于循环内收集多次调用记录：每次迭代会覆盖前一项，chain 每个技能的运行现场必须用数组收集，并为每次 API 调用提供独立 start/finish 回调。（09-09 chain 意图路由）
73. 意图路由的 fallback 不是重发同一请求：必须携带一次性 `routingOverride`（bypass / forcedIntent），否则点击按钮后仍会被同一路由器拦截，表现为“按钮没反应”。（09-10 意图路由 V3）
74. folder 判据必须使用显式规格字段 `format === 'folder' && folderPath`；任何“模板里有 skill 对象”式推断都会把文本技能误判成 folder。（09-10 意图路由 V3）
75. 意图路由 UI 验证前必须清空持久化会话历史：大纲聊天存在 `wa_project_<id>.outlineChat`，旧消息会改变路由结果；测试技能标识（如 `codex-e2e-`）必须在 finally 额外断言不存在，snapshot 只能回到“测试开始时”，清不掉更早的残留。（09-10 意图路由 V3）
76. 多场景顺序 mock 必须逐分支核对可达性：两个相同的 `requests.length` 条件会让后一个分支永远不可达，但请求计数断言仍通过；探针失败先核对“场景 -> 响应”映射，再判业务链路。（09-11 大纲共创阶段4）
77. 覆盖守卫与 UI 禁用状态必须同源：内部有 `criticalOverride` 守卫不代表按钮已解禁；显式覆盖类操作必须让内部守卫、按钮 disabled、提交载荷共享同一状态。（09-11 大纲共创阶段4）
78. 应用批次后弹窗自动关闭是正常状态机；收尾关闭弹窗前必须检查可见性，元素存在但不可见时继续点击会制造 30 秒超时假失败。（09-11 大纲共创阶段4）
79. 测试边界要和调研缓存一起交付：`_audit/research-cache/`、自研验证脚本若不进 Vitest `test.exclude`，会长期制造假红灯，掩盖下一次真实回归。（09-11 深度递归检测）
80. window 监听必须“注册、清理、同组件”三同：匿名函数注册等于永久注册；可重挂载组件必须具名 handler 并在 `onUnmounted` 成对移除。（09-11 深度递归检测）
81. IPC 对账不能只数通道数量：preload 多出的通道可能是主进程向渲染层推送的事件；必须按方向和发送端核对，避免把正常事件误报为断链。（09-11 深度递归检测）
82. 后台轮询的 catch 可以不中断业务，但不能完全无痕；至少 `console.warn`，否则 IPC 异常会被误判为“面板正常但没数据”。（09-11 深度递归检测）
83. 横向契约测试必须以正式协议类型为准：测试手写批次对象漏掉 `type/version` 时，即使运行时宽容通过，type-check 也会暴露契约漂移；这类红灯要修测试而不是放宽协议。（09-11 API 对话底座统一）
84. 非法 schema 用例要构造真实违规形态（如 `properties:null`）：类型系统不允许写非法值，但外部声明可能带来；用受控类型断言模拟坏数据验证校验器拒绝。（09-11 API 对话底座统一）
85. 多场景 mock server 生命周期必须在 finally 末尾统一关闭：提前 close 会让后续场景连接失败，制造与业务无关的假失败。（09-11 API 对话底座统一）
86. runTrace 的最新 run 不能按数组尾部取：`startRun()` 使用 `unshift`，最新记录在数组第 0 位；测试按 `startedAt` 倒序取第一条。（09-11 运行记录深度化 V2）
87. `innerText` 不包含 `<details>` 折叠内容：验收折叠区文案必须真实点击 Tab 和 summary，只读面板整体文本会漏掉隐藏内容。（09-11 运行记录深度化 V2）
88. SSE mock 的事件分隔符是协议要求：每个事件必须自带 `data: ...\n\n`；合并成无换行长字符串会导致解析器丢响应。（09-11 运行记录深度化 V2）
89. 测试场景切换要清技能配置并封存旧 run：大纲工作台按会话聚合，未清技能时“直接对话”会走技能链，未封存旧 run 时新请求会写入旧会话。（09-11 运行记录深度化 V2）
90. contextBridge 暴露对象在页面侧不可覆盖：`page.evaluate` 替换 `window.electronAPI` 方法不生效，真实目录选择测试必须使用主进程测试钩子 `SHENYI_TEST_DIRECTORY_PATH`。（09-10 Folder 阶段2）
91. 验证脚本选择器必须按真实 DOM 写，不按旧记忆写：先 `rg` 确认 ID/class，再写探针；断言读取范围要覆盖被测信息所在的完整组件，避免父级文本漏资源摘要。（09-10 Folder 阶段2）
92. parentPort 消息协议是宿主差异：Electron `utilityProcess` 传 `{data:request}` 信封，Node `worker_threads` 传裸值；跨宿主进程桥必须双信封测试并用源 Electron 走真实 IPC。（09-10 Folder 阶段3）
93. 单测环境会掩盖真实桥故障：只测 Node `worker_threads` 可能全绿，但 Electron 桥超时；修改主进程代码后必须重启源 Electron 再探针，旧进程不加载新代码。（09-10 Folder 阶段3）
94. 评测服务不得侵入运行记录层：评测只调用评测服务并提供 callAi 代理；trace 的 start/finish 语义由 runTrace store 统一维护，评测层自建记录会重演 running 僵尸。（09-10 Folder 阶段4）
95. 代理 callAi 必须保持 trace 一致性：先 `startApiCall`，再真实调用，finally `finishApiCall`；成功、失败、抛错三条路径都闭环。（09-10 Folder 阶段4）
96. 协议文件进入 folder 包结构后要防重复注入：`evals.json` 是元数据不是参考资料，必须加入 loader knownFiles，否则递归扫描会把它再注入 system prompt。（09-10 Folder 阶段4）
97. 跨层字段要协议化不做隐式约定：如 `caseId` 写入 `CallAiParams.meta` 类型与请求元数据，运行记录与报告才能稳定对齐。（09-10 Folder 阶段4）
98. “属性值为 undefined”不等于“属性不存在”：条件展开仍会创建键；契约测试用 `toHaveProperty` / `not.toHaveProperty` 才能暴露半删除。（09-11 chain 单一所有权）
99. 混合链路测试要测真实步序：folder 放第 1 步却断言第 2 步交接，会被意图路由过滤掩盖成假覆盖。（09-11 chain 单一所有权）
100. 降级回退是合法调用不是失败：folder 加载失败回退 text 时 `aiService.callAi` 仍应被调用；断言“不该调用”会把正常降级误判成 bug。（09-11 chain 单一所有权）
101. 重复注入类修复必须统计出现次数：只断言“包含”会漏掉 2 次、3 次注入；用 `split(text).length - 1` 才能证明单一所有权。（09-11 chain 单一所有权）
102. 公共契约改动必须追到全部调用方：`buildChainSkillPrompt` 同时被工作台和流水线使用，只改一处会造成另一半断链；改后 `rg` 全部调用点并分别验证。（09-11 chain 单一所有权）
103. 流水线 E2E 要识别非链路前置调用：确认大纲会先触发 1 次风格分析，再进入 chain SKILL；按调用内容定位链路请求后再统计次数。（09-11 chain 单一所有权）
104. folder 步骤的交付通道必须按执行器能力判定：folder executor 不解析流水线 `{{previousOutput}}`，必须走 `inline_block`，上一步输出经 user prompt 恰好注入一次。（09-12 folder 流水线 E2E）
105. folder 请求断言要检查 `template.md` 内容，不检查技能名：`SKILL.md` 名称只进元数据不进 prompt。（09-12 folder 流水线 E2E）
106. 共享 `_data` 的 E2E 必须串行执行：folder 流水线、文本流水线、大纲工作台三个 chain E2E 并行会互相覆盖 `wa_skills`，制造与业务无关的假失败。（09-12 folder 流水线 E2E）
107. 不能从已解析模板反推变量值：`resolveSkillTemplate()` 替换 `{{name}}` 后信息已丢失，启发式逐行解析只会偶发命中。跨层传变量必须走显式 `templateVariables` 通道，缺失占位符写成 `folder-template-variables-missing` 诊断。（09-12 folder chain 变量注入）
108. reasoning 流必须同时进 UI 和运行记录：`onReasoning` 回调透传到 `callAi` 后，只接进度弹窗不写 `runTrace.appendReasoning` 会让 SKILL 调试看不到思考过程。增量按累计流计算 `delta = cumulative.slice(previous.length)`，导出文本必须包含“思考过程全文”。（09-12 folder chain reasoning 可见性）

## §3 验证纪律

1. **构建成功不等于功能完成**：必须走真实 Electron + CDP 真实操作。代码能编译和运行时行为是两回事。
2. 验证必须递归：按钮存在 → 点击 → store 变化 → UI 响应 → 持久化。点击后检查弹窗、次级页面、返回。
3. 没有证据的“已完成”就是未完成：必须引用 file:line 或命令输出。报告生成后要读报告确认结论，不能只看 exit code。
4. **验证作用域不扩大**：服务层测试不能当 UI 证据，受控 mock 不能当真实 API 证据；相同 class 可能出现在多个组件，测量必须限定作用域。
5. Vue 渲染等待：v-if 组件需异步渲染，CDP 检查前等 2.5s 或用 waitFor；点击后立即不存在可能只是时序误报。
6. 启动态清理：验证前先处理可见的遗留弹窗/面板，禁止盲点隐藏按钮。
7. 夹具检查：重启持久化验证必须先确认测试项目存在，否则结果是“夹具缺失”不是“功能失败”。
8. **生成前置条件铁律**：记忆抽取必须以真实已生成正文为输入。新建项目只有卷纲/章节概要时，编辑器 disabled 是合法空态。取消/失败重试/断点恢复必须在真实生成请求中核验；受控隔离项目可以验证入口但不能注入假数据制造通过证据。
9. **目标续验以当前轮新鲜证据校准旧日志**：历史记录与当前状态冲突时保留历史记录并在新日志说明冲突，不得直接沿用旧结论或扩大范围。
10. 安装包验证至少三层：安装包生成 → 解包程序启动并可连 CDP → 真实页面入口/边界操作。最小烟测通过不能扩展为完整业务验收。
11. 构建、类型检查、测试 runner、CDP 行为、安装包客户路径是五个独立验证门；一个门通过不得覆盖另一个门的未核销状态。
12. `start-electron.bat` 输出 `[OK] Application started` 不是进程存活证据；必须再检查实际进程、CDP 端口和页面 URL。
13. 阶段只有在前置条件、真实操作、DOM、store、持久化和下游联动均有本轮证据时才可勾选完成。
14. 验证报告写完后必须读报告确认结论行；多个测试按钮都要遍历检查，不能只检查第一个。
15. 死 CSS 清理必须在模板改完后用源码搜索确认无引用再删；构建不会报 CSS 选择器无引用。
16. 持久化与解析层分离取证：重启后功能失效时先对账磁盘 JSON 与 DOM 渲染数。磁盘完整但 DOM 为空（如 msgCount=0 而 wa_chat_*.json 完整）即可锁定“会话解析竞态”而非存储缺陷。
17. 源 Electron 不是 Vite 热更新载体；改 renderer 源码后，真实 UI 探针前必须先 `npm run build:vue`，否则拿旧 dist-renderer 制造假缺陷。
18. 验证脚本与源 Electron 的启动参数要对账：没有 `--dev` 时页面加载的是 `dist-renderer`，不是 Vite 开发服务。验证结论必须绑定“当前渲染产物版本”这一前置条件。
19. 真实记忆验证必须固定真实 projectId，并分别证明“磁盘来源真实”和“调用消息实际注入”；仅读取 memory 不能证明已注入。
20. 居中弹窗验证必须计算几何中心：`left + width / 2` 与视口 `innerWidth / 2` 差值接近 0 才算居中；只断言 `display:flex; align-items:center` 会被父级宽度异常欺骗。（09-08 运行记录）
21. 遮罩弹窗关闭验证必须覆盖 `@click.self` 路径：点击 overlay 空白处后 overlay 消失、panel 消失，且不存在残留遮罩拦截主界面点击。（09-08 运行记录）
22. “完整全过程”类需求的验证不能只看 UI 条目数；必须同时证明请求消息、流式累计、返回全文、诊断对象和时间线事件在同一 run 对象内成组存在。（09-08 运行记录）
23. `saveSkills()` 为异步写盘，UI 保存验证必须等写盘完成后再读 `wa_skills`；仅点击保存不是持久化证据。
24. 真实 UI 探针失败必须保存气泡文本、操作区文本、截图和请求日志；这些证据用于把“按钮缺失”精确到“旧构建产物”，避免误改业务代码。
25. CDP 探针结束后必须核销 `wa_lastProjectId`、探针对话、可见弹窗与 `_data` 探针键；探针把 lastProjectId 写成探针项目会让下一轮进入错误项目，制造编辑器无页签假缺陷。
26. 探针等待流式结束不能只等状态条消失，还要等消息操作按钮从 disabled 恢复可用；否则会在 busy 清理前点击，制造假失败。
27. 断言不得依赖模型输出里必须出现特定英文词；重生成验证以“消息对被替换且新回复非空”为准。
28. **UI 完全无响应排查顺序**：首查 store 持久化函数是否存在无限循环（saveConfig 重新赋值 config.value → watch → saveConfig）。路径：Electron console 模块加载错误 → 源码搜 saveConfig/persist 是否重新赋值响应式状态 → 消费组件是否 watch({deep:true}) 回调持久化。三步锁定根因，不需要 CDP。
29. 版本回退类功能必须做“UI 操作 → store 更新 → 磁盘版本目录切换 → 重启后不回跳”四段验证；只验证点击成功不等于版本选择生效。
30. 目录选择类功能至少验证两条真实路径：选中目标对象本身时的引导路径，以及选中父级根目录时的正常路径；只验证正常路径会把误选留成客户实操缺陷。
31. **技能身份必须包含 format 命名空间**：不能只看来源 ID 或名称；第三方 SKILL 与既有文本技能同名时会被误判重复导致导入无效。文本与 folder 必须按规格区分。（09-08 同名共存）
32. **E2E mock 请求断言先对账记录器结构**：本工程 mock 记录的 `body` 已是请求体本体，再写 `body.messages` 会永远取空；断言前先打印或读取一条真实记录。（09-12 产物有效性修复）
33. **E2E 断言必须绑定产品实际语义**：folder skill 显示名由 `displaySkillName()` 统一加“（文件夹）”，验证脚本不得沿用原始导入名；安装版验证前还要确认启动的 exe 确实是目标产物，否则会把验证脚本漂移误判成产品缺陷。（09-12 挂死修复）
34. **安装版验证必须用干净 profile**：沿用旧 profile 会把历史会话文本混进 mock 请求，制造假失败；专用 profile 测完后必须删除并复核。（09-12 挂死修复）
35. **验证脚本与应用语义不同步时先判责**：同一现象在源 Electron 与 E2E 间不一致，先检查脚本是否读旧产物、断言是否读错字段，确认后再改业务代码；不允许直接改产品迁就脚本。（09-12 挂死修复）
36. **验证脚本的磁盘断言路径必须跟随 `SHENYI_TEST_USER_DATA_DIR` 隔离目录**：不能沿用 `ROOT/_data` 旧路径，否则成功运行也会读错目录或留下临时 profile。脚本清理逻辑必须有 `try...finally`，并提供 `SHENYI_E2E_KEEP_PROFILE` 保留开关；默认路径下测完必须删除专用 profile 与导出产物并复核。（09-13 全应用统一性修复）
37. **immediate watch 禁止引用后置声明**：computed/watch immediate 引用 `ref` 时必须先确认声明顺序；后置声明会导致组件初始化 TDZ 崩溃，type-check 不能覆盖此运行时问题。被修改组件必须做自身真实渲染 E2E，不能只验证父级路由或全局队列。（09-13 技能页消失回归）
38. **多场景 mock 的能力分支必须完整覆盖每个场景**：同一供应商能力（如 HTTP tools 400 后降级）被多个测试场景复用时，不能只在第一个场景分支实现；切换 `scenario` 后响应形态改变，会让后续请求走错协议路径，制造“业务降级失败”的假缺陷。mock 能力要用集合/常量集中声明，再按场景返回不同载荷。（09-14 API 直写 V2）
39. **E2E 断言文案必须跟随产品语义升级**：直写模式替代提案模式后，写入安全语义又从“单次写入上限”升级为“连续相同写入拦截”；脚本继续等待旧文案会永远失败。产品语义变更时必须同步 `rg` 全部验证脚本里的旧断言。（09-14 API 直写 V2；09-18 修订）
40. **测试脚本也要有截图/证据与场景数对账**：声明 13 个场景却只生成 12 张截图，说明无截图场景无法在交付对账中可视化；结果 JSON 的 `scenarios` 必须与实际证据文件数量对账，导出/深检场景也要落截图。（09-14 API 直写 V2）
41. **多视图截图证据必须做防伪对账**：截图前先清空旧 PNG，截图后计算 SHA256 并断言互不相同；不能只断言文件存在或字节数大于 0。若通过 URL/hash/路由变量切视图，必须先证明该变量真实驱动 UI 状态，否则会产生“脚本通过但截图全同”的假验证。（09-14 安装级烟测）
42. **新增 AI 能力必须同步对账诊断日志覆盖面**：runTrace 记录完整不等于 DiagLogger 覆盖完整。新工具、新降级、新呈现方式上线时，E2E 必须同时读取 renderer 与主进程诊断日志，对账类别、数量和缺失项；只验证 runTrace 会把 SKILL 调试盲区留给客户。（09-14 API 直写 V2 补验）
43. **测试日志必须随专用 profile 隔离与清理**：安装版/源码 E2E 的诊断日志通过 `SHENYI_TEST_LOG_DIR` 或专用 userData 写入，测试结束随 profile 删除并复核不存在；不得写入用户真实日志目录。（09-14 API 直写 V2 补验）
44. **截图互不相同断言必须绑定真实 UI 状态变化**：导出文件、保存配置等无 UI 变化的场景不能直接截图凑数；应先打开可见结果面板/详情页再截图。若两张截图相同，先判断是测试设计未制造可见状态，还是产品缺陷，不允许放宽断言迁就测试。（09-14 API 直写 V2 补验）
45. **真实点击失败先做命中点取证**：按钮被拦截时不能直接判业务失效；必须记录实际挡住点击的祖先/全屏层，并在关闭前置层后复测目标入口。（09-14 主页重置假缺陷复核）
46. **`--dev` 模式选择页面必须排除 DevTools**：Electron + Playwright 下按 `url().includes('index.html')` 找页面会错选 DevTools 页，导致探针拿不到业务 DOM。应使用 `!page.url().startsWith('devtools://')` 选择主页面。（09-16 API 直写成熟化收尾）

## §4 删除纪律

1. 死代码清理先做三面引用闭包：生产源码、测试脚本、历史资料；引用未隔离前只关闭入口，不删实现。
2. 历史引用未隔离前不得删除旧模块，避免误删行为等价基准。
3. Electron IPC handler、preload 暴露项先做引用闭包再删；dialog.js 旧 sync handler 不能直接删，preload 有引用。
4. CSS 自动去重脚本禁止使用；每个删除必须手工确认。
5. 删除前确认用户要求的是“彻底删代码”还是“关闭入口”，默认后者。

## §5 UI 纪律

1. `tokens.css` 是唯一颜色/字号/间距变量来源，组件内禁止硬编码（组件级设计需除外）。
2. v-show 导航（流水线五层）是有意状态控制，禁止移除 v-show 改为 v-if 或全渲染。
3. 常驻 UI 卡片不能条件隐藏；空态显示“待 AI 分析”，不能整个消失。
4. 隐藏弹窗/未打开节点不能作为可见配色/布局证据，必须真实打开目标界面。
5. 死按钮扫描必须排除 v-show 隐藏区域。
6. 文字溢出验证必须逐弹窗、逐按钮、逐标签实测，不能只看一处通过就全量声明。
7. 弹窗递归验证三层：主页面 → 弹窗 → 弹窗内子弹窗。
8. flex 布局中标题类元素用 `min-width:0 + flex:1 1 auto`，禁止 max-width 固定截断。
9. 页面级 `scrollWidth === clientWidth` 不等于内部控件没有溢出；必须递归扫描可见后代并读取矩形边界。
10. `scrollWidth > clientWidth` 不等于溢出：若同时有 overflow:hidden + ellipsis + nowrap，这是设计内省略，必须结合边界矩形和可见性判断。
11. 小视口下 flex 子项被压缩为 0 是真实缺陷；overflow:hidden 会静默截断。应由明确滚动容器承载内容并保留可用最小高度。
12. 流水线进度反馈的可见性必须绑定“当前活跃层”，不能写成 `isGenerating || 本层日志存在`；其他层有历史日志时会跟着亮，形成跨层双反馈。回归断言覆盖 `visible.length === 1`。（08-31 弹窗重叠）
13. 链式步骤的按钮语义决定作用域时，作用域必须在应用层双向强制：请求端 prompt 是建议，响应端必须按模式钳制数量（single=1、continue=1），模型违反时截断并写日志。卷纲“续生成”用户语义是“继续下一卷”，不是批量补齐剩余卷；空列表时同样只能生成第1卷。（09-13 卷纲续生成单卷修正）
14. 设定项多时采用紧凑列表 + 唯一当前项编辑区，避免框对框纵向拥挤；列表选择状态用稳定 id，不能用显示索引。
15. 大型列表必须有 `max-height` + `overflow-y:auto`，内容区 `flex:1 1 auto`。
16. DOM scroll 尺寸超出 client 若父容器明确为滚动容器，不应直接判布局溢出；必须区分可滚动内容、横向溢出和祖先裁剪。
17. CSS 变量 fallback 清除必须用两阶段正则；单阶段会误吞产生空 `var(--)`。清除后必须 rg 扫描验证零残留。
18. 正则替换含 `)` 的 fallback 值会产生双括号导致 lightningcss 构建报错。设计系统升级覆盖组件时必须保留功能链路验证。
19. 竞品视觉优势主要来自第三方 UI 包内置能力，评估风险后经用户确认可加装依赖。Vue3 + 原生 CSS 可通过等价实现达到接近的视觉成熟度，无需换架构或装包。
20. 亮色主题对齐成熟 UI 框架实际源码值：背景 `#FFFFFF`、surface-light 层 `#EEEEEE`、surface-variant `#424242`；层次靠明确色差而非微弱偏移。选中态 alpha 暗色 0.12、亮色需 0.16 才可见。
21. 旧亮色色值清理必须删除残留重复声明，否则 CSS 后声明覆盖新值；rg 扫描硬编码色值确认零残留是必要步骤。
22. 密度系统用 `[data-density]` 属性选择器，对齐三档 default/comfortable/compact；偏移 default=0px、comfortable=-8px、compact=-12px。默认值与启动初始化必须一致，否则不选密度时无属性。
23. 默认主题从 dark 改 light 只改 theme.ts 默认值，不改存储逻辑；用户已保存主题由 localStorage 优先。
24. chapterConfigLocked 类前置条件不得绑死生成按钮：每章字数输入不应是 AI 生成章节的前置条件；输入框不得因保存动作变 readonly，保存后用户仍可修改。（09-04 章节层字数锁定）
25. CSS 变量引用前必须确认 tokens.css 存在定义；`--bg-panel` 不存在会导致弹窗透明。弹窗关闭函数必须重置全部 loading 状态，否则按钮 disabled 永久锁死。`insertToEditor` 的 CustomEvent 必须包含 `openEditor:true` 才能触发 App.vue 面板切换。展开式卡片父层 `overflow:hidden` 会裁切子内容，应改 visible + 子容器滚动。（09-04 三联修复）
26. 全屏阻断式生成弹窗应替换为内联进度条：独立 GenerationProgressBar 组件，通过 `logContainerId` prop 保留原 DOM id；嵌入各层面板底部，不阻断编辑器。四层共用组件，step prop 区分，日志数组独立。删除旧 overlay 时必须保留 computed 可见性、close 函数、appendPipelineStream、autoScrollLog、LOG_CONTAINER_IDS、watch，只删 DOM 模板和 CSS。（09-05）
27. SKILL 拖拽排序必须在组件内写内联 drag handler：drag 事件需要直接访问 reactive state 和 DOM ref，外部 composable 闭包会丢失响应性。（09-05）
28. 右键菜单用 TopSheet 替代 fixed ctx-menu：顶部滑入、max-height + overflow、Transition 动画；替换时保留所有按钮和 action 处理函数，只改外层容器。统一弹窗队列 useModalQueue 用 isGenerating guard 防生成中叠加。（09-05）
29. 面板拖拽分隔条必须用 composable 抽离：百分比替代像素、localStorage 持久化、RAF 节流 DOM 写入、鼠标/触摸双路、MutationObserver 重绑、dblclick 重置；评估风险后经用户确认可加装依赖，等价实现为备选方案，不动布局 DOM。（09-05）
30. GenerationProgressBar 展开收起按钮必须居中高亮，不能放最侧边：margin 0 auto + fit-content，accent 边框与背景高亮，展开实心、收起描边，结构为箭头 + 文字 + 行数标签。（09-05）
31. GPU 与合成层：禁止给常驻交互元素挂 `will-change: transform/opacity`，该声明会长期占用 GPU 合成层并放大内存；仅允许在明确动画周期内临时提升。`.panel`、`.statusbar`、`.scroll-area` 继续用 `contain: layout style paint` 隔离重排。动画必须有活跃消费者，遮罩模糊必须走 `--overlay-blur` 单源 token，由 `scripts/verify-design-fusion-legacy.mjs --phase=P5` 机器守护。（09-04 性能；09-20 Graphite Ink P5 修订）

## §7 存储纪律

1. **原子写盘四步**：写唯一 tmp 文件 → 旧主文件 rename `.bak` → tmp rename 主文件 → 失败时从 `.bak` 回滚。主文件永远是完整旧版或完整新版。
2. 并发写同一 key 必须按 key 串行化（写队列 Map）；唯一 tmp 文件名只解决文件级冲突，不解决同 key 顺序冲突，两者都要。
3. 同一 run 的自动保存必须双侧串行：renderer 按 run id 排队 `finishTurn/finishRun` 触发的保存，主进程按目标目录排队 `rm + write`。只串行一侧时，同一 tick 的两次自动保存会在 Windows 下交错，把 `run-trace.json` 写成两个 JSON 尾巴拼接。（09-11 运行记录深度化 V2）
4. 删除运行目录必须等待该 run 的保存队列结束，并复核排队期间是否拿到新的 dirName；否则滚动清理刚删完目录，未完成保存又把目录重建，形成“清理失效”假象。（09-11 运行记录深度化 V2）
5. 读路径恢复语义：主文件 JSON 损坏 → 尝试 `.bak` → 恢复成功转正并写 `restored=yes` 日志。单代 `.bak` 恢复的是上一次保存版本而非最新。
6. 验证损坏恢复必须制造真实损坏（直接改磁盘文件为非法 JSON），不能用 mock。重启后断言三点：数据从 `.bak` 恢复、`storage-corruption.log` 新增条目、读回值有效。
7. **导入默认合并**，覆盖必须用户主动选择高级操作。
8. 项目数据隔离：不同项目 storage key 必须含项目 ID（`wa_project_<id>`），禁止全局覆盖。
9. 旧配置兼容：读取时兼容老字段，保存后写新字段。
10. IPC 暴露三处同步：electron/ipc 注册 handler + preload 暴露 + renderer 调用。
11. 所有 IPC 从 sendSync 改为 handle + invoke 异步；同步 IO 改 `fs.promises`。
12. 异步化后调用方必须 async/await；搜索所有调用异步 IPC 的文件逐一改。
13. App.vue 启动多个 store 初始化改为 `Promise.all` 并行加载，可降启动时间 30-50%。
14. 跨重启持久化验证拆成 A/B/C 三段脚本，状态文件是段间记忆载体。
15. 没有 `wa_project_*` 真实快照时，不得为核验关闭重启而注入项目；正确结论是 UNVERIFIED。
16. 数据目录存在 `wa_project_*.json` 只证明有历史文件，不证明本轮恢复通过；必须有导入前/后配对快照和重启后读取证据。
17. `loadProject()` 必须信任磁盘状态，不得加载时自动预建卷/章节/正文；`ensureVolumesFromOutline()` 只允许在用户主动锁定大纲或创建项目等明确入口调用。
18. store 异步加载未 await 就执行依赖解析（如 loadSessions 后立即 ensureSession/restoreContinuation）时，activeSessionId 会指向加载前空会话；加载完成后必须重新解析活跃会话。
19. 清空聊天必须同时清理旧聊天存储与 `wa_ctx_<projectId>` 的同一 workspace/purpose scope；只清旧 key 会造成 UI 空白但上下文残留。
20. 会话保存必须显式传当前 projectId；无参 saveSessions 会在项目切换竞态时把会话写入 `default`。
21. AI 批次等外部写入不得调用 `undoRedo.pushState()` 进入用户撤销栈；必须使用“替换当前快照”的专用方法并保留批次回滚栈，否则用户第一次 undo 先回滚 AI 批次。
22. 消息操作按钮不得提前显示成功反馈；反馈必须发生在真实操作成功之后。
23. 退出保存超时不得固定 5000ms；大项目序列化+写盘可能超 5 秒。改为 15000ms，且 `app:saveComplete` 监听必须在 `app:closeChoice` handler 内注册 once，防残留。
24. `loadProject(id)` 不得先设 `currentProjectId` 再 await storageRead；中间窗口期读取 currentProjectId 的代码会拿到新 ID 但 volumes/chapters 仍是旧值。先 await 数据再设 ID。
25. `persistProject` 的 microtask 回调不得无条件写盘；用 `dirtyFields` 标记脏状态，只有 true 才写盘，写完立即清零。
26. `persistProject` 写入顺序：先写 `project_<id>` 成功后才写 `lastProjectId`；反序在崩溃窗口会让重启读到指向不存在项目的 lastProjectId。
27. 项目自动保存不得依赖 EditorPanel 的 `startAutoSave()`（只管 editor dirty tab）；项目 store 必须有独立 start/stopProjectAutoSave，在 EditorPanel onMounted/onUnmounted 管理。
28. `toPlain()` 深拷贝优先 `structuredClone()`，JSON 序列化仅作 fallback。
29. 项目 schema 版本必须随结构变更递增；`loadProject` 必须调用 `migrateProjectData()` 链式迁移。
30. 会话恢复持久化 `lastSession`（pid/vid/cid/ts），App.vue onMounted 读取并派发 `restore-session`；7 天时效防止恢复过期会话。
31. 死代码文件即使内容为空壳也必须删除；残留文件会被搜索匹配干扰开发判断。
32. Folder SKILL 在设置页必须只读展示，禁止应用内编辑入口；编辑只写应用副本不写回磁盘会造成漂移。需要修改时通过“打开文件夹”进入磁盘源目录。（09-06）
33. 磁盘数据被运行中的应用持有内存状态时，直接改文件可能被内存写回覆盖；清理测试数据必须先结束应用进程再改磁盘。（09-06）
34. Folder 技能内部 ID 固定为 `folder:来源ID`，`sourceId` 保留 YAML 原始声明；展示层用 `displaySkillName()` 加“（文本）/（文件夹）”后缀，数据层与 UI 层职责分离。（09-08）
35. 导入冲突判断必须限定同规格：文本只与文本冲突，folder 只与 folder 冲突；跨规格同名必须允许共存，设置页徽标与来源 ID 负责区分。（09-08）
36. Folder 状态写入键必须与卡片渲染键完全一致；任何 `folderStatusMap` 写入都必须先经过 `normalizeSkillId(id, 'folder')`，来源 ID 只用于展示和 sourceId。（09-08）
37. 导入类功能不允许“选完直接入库”：单个导入也必须与批量一致，走“选择 → 预览 → 冲突策略 → 确认”两段式；预览冲突判断沿用归一化 ID，防跨规格误判。（09-08）

## §8 AI 服务纪律

### M51 路由阈值校准纪律（09-22 意图语义路由 Phase 2）

1. 意图路由引入新判定层（OOS、分意图 margin、风险分层）时，必须先在社区源码中确认失败处理与指标口径，再改生产常量。
2. 校准脚本的排序方向必须显式核对：accuracy 之后优先更少 falseRejections、更少 discussBlocked、更少 missedRejections；不得把“更多误拒”当成更优结果。
3. 校准产物必须记录 baseline；若最佳组合与生产常量不一致，必须回写并同步 `thresholdSource`。
4. OOS 属于可诊断的 no_match 子类，降级路径保持 readonly-discuss；不得因 OOS 引入 await-user 或写入工具面。
5. trace 必须透出 `ambiguityThresholds`、`oosThreshold` 与 `thresholdSource`，否则 SKILL 调试方无法复现阈值决策。

### M52 路由语料切分与证据口径纪律（09-22 意图路由 V6 Phase 6）

1. 校准语料必须先做确定性 train/dev/test 切分，并用结构测试锁定三份互斥、全覆盖与确定性；阈值只允许在 dev 集选择，test 集只能做最终报告，禁止“同一份语料既当练习册又当考卷”。
2. 排序硬约束不得把当前缺陷固化成策略：不得使用 `falseRejections <= N` 这类现状上限；写入安全硬约束（writeFalseTriggers、missedRejections）必须保留为零才可成为候选。
3. falseRejections 需逐条定性后分流：embedding margin 拦截、合理 ambiguous、语料覆盖缺口、路由结构缺陷是四类不同问题；只有语料覆盖缺口才允许扩充示例库解决。
4. `thresholdSource` 版本标签中的样本数、示例数、切分方式必须与 `CHAIN_INTENT_EVAL_*` / `INTENT_EXAMPLES` 实际结构逐项核对；标签写错即视为校准证据失效。
5. margin-gate 异步裁决优先复用既有 LLM fallback，并验证 request-failed / invalid-json / low-confidence / timeout 全失败路径；失败时保持 readonly-discuss 或 await-user，不得为提升执行率放宽写入权限。
6. 语料扩充后必须重跑完整校准与 Electron 级验证，trace 中透出的阈值、margin、OOS 与 thresholdSource 必须与生产常量同源一致。

### M53 校准脚本完整重跑纪律（09-22 意图语料自成长 V2）

1. 校准/评估/验证脚本每次新增数据源接线、输入组装、声明顺序或导出逻辑改动后，必须完整执行该脚本，并以本轮新产物作为唯一接入证据；禁止用局部测试、模块导入成功或历史时间戳产物证明“已接入”。
2. 回头看必须包含“脚本自身执行验证”：生产 `src` 与验证 `scripts` 属于同一改动面，脚本内 TDZ、变量声明顺序、环境变量路径校验不得只靠静态阅读判定。
3. 长耗时校准脚本不允许因耗时原因跳过重跑；耗时本身就是证据口径的一部分，跳过时必须在 DEV_LOG 明确登记“未重跑原因 + 风险 + 后续补跑条件”，不得默认豁免。
4. 校准产物必须记录 generatedAt、输入源、样本/示例计数与硬约束结果；产物时间戳早于最后一次源码改动时，禁止用于完成声明。

### M54 验证脚本 mock 序列对齐纪律（09-22 意图对抗语料工厂）

1. mock 的触发条件必须按场景显式声明并与真实请求序列对齐；禁止用全局请求计数、跨场景残留状态或“第 N 次请求”这类脆弱分支模拟用户行为。
2. mock 回放同一工具/写调用被服务层守卫（如重复写入守卫）拦截时，必须先区分“产品守卫按设计生效”与“测试脚本制造假失败”；守卫本身不得为绿灯被削弱。
3. 位置咨询、权限询问、生成后讨论这类产品语义必须写入测试契约；验证脚本不得把既定只读语义误断言为路由缺陷。
4. 验证脚本自身改动后，必须重跑脚本本体并保留新证据；mock 分支修复不能只靠源码阅读判定。

### M55-M57 意图对抗工厂收敛纪律（09-22 收敛 V2）

1. M55：停止审计的 S1-S6 六门是唯一“允许收敛封装”的判据；Silver writeFalseTriggers / missedRejections 永远是硬零，falseRejections、discussBlocked、intentMismatches 在本轮收敛口径内也必须清零或获得合法 qualification。
2. M56：连续有效轮不能按时间戳计数，也不能按 inputHash 计数；每轮必须在账本里登记 actions、metricsDelta、evidence，且报告可复查。若中间轮失败，后续全零轮只有在问题闭环后才能计入末尾连续序列。
3. M57：扩库批次先跑工厂再定性失败：先区分“种子标签错误”、“路由结构缺陷”、“安全阈值误配”三类。种子错误修数据源，结构缺陷修路由，安全阈值禁止放宽；修复后必须重跑路由专项测试和当轮工厂报告。

### M58 编辑任务工具面状态归一纪律（09-23 EditTask Phase 5）

1. 任务上下文进入授权函数时必须先归一活动状态：终态任务视为“无活动任务”，普通 edit 请求恢复 `editor.write`，task 控件移除；禁止把终态对象继续当活动闸门。
2. 活动任务的写入语义必须区分：`awaiting_batch` 是模型重试轮，`editor.write` 恢复；其他活动状态走 `task.resume` / `task.cancel`，由任务执行器校验并写入，模型不得绕过执行器。
3. system prompt 必须声明本轮实际工具面和任务语义，明确禁止模型凭历史对话宣称“没有写入权限”；声明内容必须与 `authorizeDialogueTools()` 输出同源。
4. 任务状态变化类改动必须有终态守护测试：活动任务、等待重试、终态、二次授权去重四类都要断言工具面，且真实 Electron 实测要覆盖“任务结束后下一轮普通写入”。
5. 验证器 mock 分支必须按场景轮次显式声明行为；修验证器时先判定是产品缺陷还是脚本假失败，禁止为绿灯削弱生产守卫。

### M59 终态收敛与控制语义纪律（09-23 EditTask 20 轮回头看）

1. 任务终态收敛必须覆盖三个面：`activeTask` 引用清空、UI 任务条消失、runTrace 保留终态事件。禁止让“事件仍在 trace”变成“终态对象仍挂在活动 UI”的理由。
2. 事件同步层禁止使用 `getActiveTask() || getCurrentTask()` 这类终态兜底表达式；`getCurrentTask()` 会返回终态对象，导致取消后的任务条永久残留且取消按钮可重复点击。事件回调只允许写入活动态任务。
3. 控制工具（resume / cancel）必须在 handler 层做状态门禁：终态任务调用 `task.resume` 必须返回 `task_not_resumable` 之类的明确错误，禁止返回 `ok: true` 让上层误以为任务已恢复。
4. 终态测试必须三面齐备：成功终态、取消终态、失败终态都要断言活动引用清空与 UI 收敛；Electron 真实 UI 断言方向必须与单测契约一致，禁止验证器为既有缺陷放行。
5. 弱实现与强实现并存时（如 manager 兜底 handler 与 session 强实现），弱实现也必须守住状态门禁，不得依赖“生产入口不会走到”作为唯一防线。

### M61 用户级验证与断言口径纪律（09-23 API 直写 V3）

1. 长文档断言必须按作用域定位：同一句式可能在多节重复出现，删除/修改断言若用“全稿不存在该短语”会制造假失败。测试稿要么全局唯一锚点，要么按目标节局部断言。
2. 受控 mock 的 Electron 实测只能证明应用侧协议、工具链、trace 与 UI 闭环，不能写成外部真实供应商实测。方案与执行的差异必须登记在 DEV_LOG，不得静默替换验收口径。
3. 路由补语料/补分支时优先局部放行：新判定必须同时覆盖目标正样本与只读负样本；全局 `hasWriteDirective` 这类被多分支复用的函数，禁止为单点失败直接放宽。
4. 修改匹配逻辑时先确认 API 语义：`String.matchAll` 要求全局正则，只需存在性判断时使用 `.test()`，避免把业务修复变成脚本级崩溃。

### M60 交互态与伪元素溢出纪律（09-23 侧栏 tooltip 溢出修复）

1. 默认态 `scrollWidth` 扫描不能替代交互态扫描：hover/focus 才出现的 `::after` tooltip 是默认态盲区，且伪元素本身可能污染 `scrollWidth`。默认态文字溢出必须区分真实文本宽度与伪元素贡献，交互态必须单独触发并单独测量。
2. 交互态溢出验证必须读真实 used geometry：`getComputedStyle(host, '::after')` 的 used width/height、placement class、内联钳制变量都要从页面读出；禁止在脚本里按 CSS 常量自拼“期望矩形”再自证通过。Chrome 在 mouseenter 同步段可能返回 `auto`，需要估宽兜底并用 rAF 二段校验。
3. 四缘宿主都要有合成测试：left/right/top/bottom edge 各自的可用空间不同，不能只测中栏或右缘。断言必须包含四边在视口内、宽度不小于可用下限、右缘宿主选择更宽侧。
4. 左右空间必须独立计算，并显式处理“两侧都放不下自然宽度”的场景：选择空间更大的一侧并按该侧空间收窄；禁止只写“左侧完整放得下才翻转”，否则窄视口会把 tooltip 压成最小宽度细高条。
5. 定位控制器必须清理状态：退出 hover/focus 时清空翻转 class 与内联钳制变量，避免下一个宿主继承旧状态；实现替换后旧控制器必须删除，禁止新旧定位逻辑并存。
6. 封装级 tooltip 核验要测打包产物本体：asar 版本、renderer 新鲜度、electronAPI、真实启动渲染与 7 个侧栏 tooltip 的真实几何都要在打包应用中断言。验证脚本自身必须先过验证门：退出码必须由验证结果控制，异常必须打印完整错误；`boundingBox()` 用 `x/y/width/height` 换算；Electron 页面视口以 `innerWidth/innerHeight` 为准；短标签宽度下限按真实文本宽度估算，禁止套用长文本压力用例的绝对下限。

### M64 cursor 语义先定口径再写断言（09-23 API 直写 100% 闭环 Phase 2）

分段读取的 cursor offset 必须在设计时明确“相对谁”：本应用定义为相对 section 起点，且 section 内容包含标题行。若测试按正文切片断言，会出现“实现正确、测试口径错误”的假失败；同理，工具返回新增同类工具会改变“可用同类工具”精确字符串，测试只能按包含校验，不能锁定完整列表。新增分页/游标协议时，先写语义说明，再写实现与断言。

### M65 直写链路路由回归纪律（09-23 API 直写 100% 闭环 Phase 3）

1. 意图路由是直写链路的隐形闸门：EditTask、工具面、长文档策略任何一处变化，都必须把“路由能否放行写意图”纳入回归面；只测执行器与工具面会漏掉请求在入口被 `no-keyword-overlap` 拦死的形态。
2. 结构性范围词必须与名词目标等价参与 edit 计分：`第N章/节/段/卷`、`第N到M节`、`首尾/开头/结尾两节`、`全文/整篇/全篇` 是显式写入目标，不是讨论词。修复范围词时必须同步守护只读负样本（“第3节写了什么”“改成什么样”“帮我整理一下”），禁止用放宽阈值换取放行。
3. 旧裸词匹配（单独“大纲/正文/设定/章节”等名词）必须删除：它们会把作者解释、补充、质疑类讨论句推向 edit。范围词与裸词分开治理，是误放行与误拦截的双向边界。
4. 多批任务收口必须绑定用户轮次终态：批与批之间保持活动任务，轮次结束后按成功/失败收敛到终态；中途收口或提前 `task_finished` 会把后续批次错误挂进终态。

### M66 长文档工作流写授权纪律（09-24 API 直写 100% 闭环 Phase 7）

1. 长文档 EditTask 是会话级工作流事实，不能被单句意图分类降级。工作流成立时，双入口必须携带同一 `long-document-workflow` 授权，并在工具面与服务层同时放行写入。
2. `discuss` 意图只代表本轮默认语义，不代表长文档任务没有写权限；若模型需要继续读取或写入，系统 prompt 必须声明真实工具面，禁止让模型凭旧对话宣称“没有写入权限”。
3. 验证器断言要绑定 `turnId`：跨 turn 合并计数会把历史批次计入当前轮；事件序列化白名单漏字段会让“真实存在的证据”显示为 0。修验证器时先分层判断产品缺陷、序列化缺口、断言口径错误。
4. 长文档负向路径必须入实测：整篇 `replace_document` 要被硬拦截，`write_only_mode` 要能阻断多余读取并把请求导回 `editor.write`。只测正向写入不能证明长文档安全闭环。

### M63 trace 字段与验证器白名单同步纪律（09-23 API 直写 100% 闭环 Phase 1）

1. 新增 trace / API call 字段时必须五面同批扩展：存储类型、服务层返回、入口回填、导出通道、验证脚本白名单映射；缺任何一面都视为接线不完整。
2. 验证脚本读取新字段为 `undefined` 时，先核对脚本自身映射是否遗漏，再判断产品缺陷；禁止为让脚本变绿直接放宽产品断言。
3. 字段在成功、失败、heartbeat、retry、工具轮、物理请求等所有返回路径保持同一口径；单路径补字段而其他路径缺失属于隐蔽分叉。
4. Electron 级验证前必须执行 `node --check`，验证脚本修改后必须完整重跑脚本本体，禁止只靠源码阅读或局部测试声称口径已修复。

### 入口与供应商

1. 所有 AI 调用必须走 `aiService.callAi` 统一入口，禁止直接 fetch；SkillExecutionEngine 的 aiRequest 回调必须来自 aiService 适配器。
2. `provider.callApi` 保留为兼容壳但内部必须委托 aiService；删除旧入口前先做源码引用扫描。
3. `stream` 默认值由统一服务层按用途决定，调用方只有在确有业务理由时显式覆盖；统一入口不等于所有请求强制流式。
4. 取消必须中止真实请求并清理空占位消息；统一入口进入重试循环前检查外部 AbortSignal，已取消请求不得发 fetch。错误路径测试同时断言错误分类和副作用（网络调用次数为 0）。
5. 流式/非流式超时分别配置；错误分类 network/timeout/http/json/auth/canceled，统一 error 对象结构。
6. 重试策略 MAX_RETRIES=3，RETRY_DELAYS=[1,2,3]s；用户 6 秒内获知失败。应用层判失败后由供应商重试兜底，但必须有错误提示，不能静默失败。
7. 诊断日志单路径写入：executionLogStore.addLog → DiagLogger.log + trackApiCall，禁止重复写；detail 必含 providerId/purpose/model/durationMs/skillId/result。
8. 诊断面板支持按 purpose 过滤；新增数据维度同步加过滤入口。
9. 链式步骤失败明确区分 failed/skipped/fallback/continued，不伪装正常完成。
10. 供应商用途必须是数组，支持一供应商多用途；卡片用 toggle 组，编辑表单用 checkbox 组，禁止单选 select。旧 string 自动归一化 array。
11. “统一入口”必须按网络请求类型逐项列清：生成/验证/检测/模型获取/插件/MCP 不是同一语义；只有同一语义才合并。
12. Pinia store 字段读取路径确认后再写验证脚本；getVerifyProvider() 读 verifyProvider ref，不是 providers 数组 purpose 字段。
13. 模型列表获取与生成调用统一到同一入口，错误边界一致。
14. 供应商协议显式类型化，完整 endpoint 识别优先于默认路径拼接；旧配置无 providerType 时默认 OpenAI 兼容。模型列表与连接测试不是同一语义，models 404/405 才允许最小 chat 降级。
15. Electron 主进程网络桥接入后，非流式与流式互斥：非流式走 `providerNet:request`，流式走 `providerNet:stream`。禁止 renderer 先 fetch 获取 Response 再调主进程流式桥，否则每条流式消息双发真实请求。
16. 供应商保存是异步 IPC 写盘，探针点击保存或切换用途后必须等磁盘值稳定再断言；同时保留 store 即时状态作为行为证据。
17. 诊断日志字段按实际实现断言：分类 `cat === 'ai-service'`，时间 `tsMs`，详情在 `detail` 字符串解析 providerId/providerType/transport/finalUrl；不能按设计文档字段名猜。

### 上下文与续生成

18. 上下文服务只提供消息组装和会话存储，不得发起 API 请求；请求入口必须显式构建消息，禁止“服务顺手调用”。
19. 续生成必须读取会话状态，禁止靠解析历史消息猜测；会话状态丢失时引导用户重新发起，不得静默续错。
20. 同一续生成任务必须复用同一会话 id；新建会话 id 会把上下文切断，模型重复输出已生成部分。
21. 跨供应商 finish_reason 归一化为统一语义；截断判定不能只看 `[DONE]` 或文本结尾，必须读取 finish_reason。
22. 续生成请求必须携带前文摘要与续写指令，禁止只传“继续”。
23. 长文本续生成拆分任务必须记录断点；失败恢复时从断点继续，不得从头生成。
24. 会话上下文按 projectId + workspace + purpose 隔离；切换项目/工作台必须切换上下文作用域。
25. 上下文压缩必须保留最新用户目标与关键事实，禁止只按 token 截断历史导致“忘了当前要求”。

### AI 编辑与工具协议

26. API 直写编辑器必须走统一对话底座与安全执行链：意图权限门（discuss/analyze 只读，edit/generate 才可写）、`editor.write` 统一执行器、定位唯一性校验、内容 hash/版本冲突保护、连续相同写入防护（连续 3 次完全相同输入才拦截，不限制有效写入次数）、锁定态只读、批次回滚与运行记录留痕。禁止任何入口绕过服务层权限门直写；兼容供应商降级 JSON 直写必须与原生工具走同等安全校验，并在日志中标记 `compatibility_write`。（09-14 API 直写 V2；09-18 修订：写入次数上限改为重复写入守卫）
27. 工具协议按供应商归一化（OpenAI tool_calls / Anthropic blocks / Gemini functionResponse），内部统一为工具调用对象。
28. 工具调用失败返回结构化错误给模型，允许其修正参数重试；同一工具连续失败 3 次终止并向用户报告。
29. 批次部分接受后必须重规划剩余项，不能把未接受项静默丢弃。
30. 撤销栈与 AI 批次回滚分离，用户 undo 不回滚 AI 批次；AI 批次有独立回滚入口。
31. AI 编辑目标必须带内容 hash；应用时 hash 不匹配则拒绝并提示内容已变化。
32. AI 批次元数据必须与消息绑定；重生成消息时清理旧编辑批次元数据，禁止旧批次操作新消息。
33. 按钮失败必须提示用户；禁止失败分支直接 return 无反馈。
34. 原生工具调用必须按供应商协议组装请求与解析响应；OpenAI 兼容供应商未显式支持 tools 时不得强行发送 tools 字段。
35. 工具调用轮次内保留工具结果消息，不能把工具结果折叠进 assistant 文本导致下一轮模型失去状态。

### 上下文优先级与流水线

36. outlineContent 上下文字段不能恒注入完整大纲；buildTemplateContext 和 sendMessage 的 chatCtx 两处必须按 activeTab.mode 区分：vol-outline 取当前卷纲要，ch-plot 取所属卷纲要，ch-body 取当前章节剧情，主编辑器取 outlineText。止血式置空等于丢上下文。
37. 主页编辑器 API 上下文优先级：编辑器内容为主创作上下文，大纲降级为参考资料。`outlineContent` 改名 `referenceOutline`，新增 `editorContent` 按页签模式填充；系统提示注入顺序：agentPrompt → 编辑器内容 → 设定 → 记忆 → 参考大纲。大纲工作台锁定服务流水线与主页编辑器共创是两套独立闭环，上下文优先级不能混用。旧模板变量 outlineContent 保留兼容。
38. referenceOutline 不得固定字数截断，必须使用 buildSOI 结构化大纲索引：全局卷概览（每卷卷名+100字摘要）+ 当前上下文锚点（按页签模式分级提取）。token 预算 800-1500，信息密度比 500 字截断提升 3-5 倍；主编辑器页签仍用完整大纲。buildSOI 只读 volumes/chapters，不写 store。
39. buildSOI 边界：空项目返回空字符串；单卷概览一行；20+卷仍可控；无章节卷显示“本卷暂无章节”；ch-plot/ch-body 找不到 chapterId 回退全局概览。SOI 只影响 ChatPanel 的 referenceOutline，不影响 OutlineWorkspace/PipelinePanel/chapterExecutionPackage 独立路径。
40. 正文字数必须从 `vol.wordsPerChapter` 优先取值，不能直接用全局 chapterWords ref；chapterWords 初始 3500 会被多种路径覆盖导致乱跳。所有消费点统一 `Number(vol.wordsPerChapter || chapterWords.value || 3500)`；卷标号显示 `{volumeCount}/{i+1}` 让切项目后记住卷数选择。
41. 共创按钮冗余：sendMessage 内部已检测 selectedCoCreationSkills 自动走 SKILL 流程，不需要单独按钮；删除冗余按钮时同步删除事件函数和空占位区域。
42. 流水线每层进度反馈必须绑定独立 `activeGenerationFeedbackStep` 值与独立日志数组：设定=1、卷纲=2、章节=3、正文=4。`genBody()` 在 startGeneration 后设 4 并初始化 bodyGenerationLogs；appendPipelineStream 的 step===4 推送 bodyGenerationLogs。切换章节后反馈不消失。
43. 降AI内嵌正文层两步闭环：前置层在 callApiWithAgent 中 `step === 4` 注入 DEAI_METHODOLOGY_PROMPT 到 system prompt；后处理层在 genBody 的 bodyResult 赋值前调用 DeAiProcessor.process()，失败用原文继续。DeAiProcessor 自带 75% 字数保护；UI 标识是纯展示 span，不涉及状态控制。

### 真 SKILL / Folder SKILL

44. folder SKILL schema 校验失败必须以 degraded 状态携带最后输出和诊断返回，消费侧禁止把 degraded 伪装成 success；探针按“最终非静默成功”断言。
45. composite 编排独立于单 SKILL executor：父 SKILL 只 plan/afterStep 不直接调 API；子 SKILL 缺失、深度超限、循环依赖、预算耗尽返回 BLOCKED。router 归一化后 failed/blocked 必须抛错并携带 folderResult，不能静默续跑。
46. folder SKILL 接入新执行路径时，必须逐项对账 text SKILL 已有注入项：template.md、Agent systemPrompt、DEAI 约束、上一章摘要、chain 前序输出；缺任何一项都是回归。验收探针同时覆盖 chain 和 compose。
47. compose 保全 folder 技能必须同时保全两份数据：skill 引用（执行 script/schema）+ 水合后的合并模板（进入 system prompt）。runStepSkills 水合后的数组必须传入内层执行函数，内层禁止重新 getStepSkillTemplates 重建未水合数组。
48. preProcess 返回的 template 只能作为动态模板能力，不得覆盖 compose 的 baseTemplateOverride；优先级固定为 baseTemplateOverride > pkg.template > preResult.templateOverride。冲突时 preProcess 只改 input。
49. 测试夹具 schema 必须与 mock 输出协议一致：schema required 为 body+metadata 时 mock 不能输出 output 字段；夹具协议漂移会制造假失败，先对账 fixture 再判产品缺陷。
50. chain 模式 folder 模板变量必须在调用点显式传入 resolvedTemplate；executor 优先级 baseTemplateOverride（compose）> resolvedTemplate（chain）> pkg.template。`keepMissing:false` 表示空值替换为空字符串，第一章 prevChapterSummary 为空是正确行为。探针不得假设变量字段连续出现，分别断言每个字段值。
51. 上下文注入必须有单一所有权：appendMemoryPromptOnce 已把记忆并入 generationPrompt 时，chain 首步只能透传 initialPrompt，禁止 buildChainSkillPrompt 再拼 memoryPrompt；验收统计最终 user prompt 中 `[相关记忆]` 出现次数，不能只断言存在。
52. OutlineWorkspace 的 askAi 函数和 skill-mode 路径各自有独立 appendOutlineChat 调用，toolCallStream 必须分别注入到各自调用点；不能在 skill-mode 引用 askAi 局部变量，会导致 TS 语法错误。
53. Vite production build 会 tree-shake/minify 内部函数名，CDP 验证搜索原始函数名会误判 FAIL；验证应搜索函数体中保留的字符串特征词，或直接检查源码导入和使用位置。
54. ChatMessage.vue 模板中嵌套 v-if 块必须有正确 div 闭合层级；在 breakpoint 块和 message-actions 块之间插入新功能块容易 tag mismatch，导致 Vite build 报 Invalid end tag。
55. JSON 提取禁止在各组件写贪婪正则：`/\{[\s\S]*\}/`、`/\[[\s\S]*\]/` 会把解释文本和多个 JSON 块连成一个非法候选。统一走 `src/services/jsonExtraction.ts` 的平衡括号解析；公共契约改动后必须 `rg` 追全部调用方，并把新 spec 纳入 `test:services`。
56. `samples.txt` 是风格参考，不是输出范例：禁止放置完整成品。超过 8 行、单行超过 400 字符、或以 `[`/`{` 开头且无 `{{占位符}}` 的结构化样本要触发 warning；健康检查只提示，不修改第三方 folder SKILL 文件夹。
57. Vue 模板事件绑定 `@event.prevent="fnName"` 会把原生 Event 作为第一个参数传入；函数签名期望 string 时会抛 TypeError。必须用箭头函数包装或加 typeof 守卫，`@click` 同理。
58. CDP Runtime.enable 会先刷新缓冲的历史控制台消息（含上一版本 build 报错），不能用于判断当前 build；必须杀 Electron、干净重建、重启，再查 console buffer。
59. 运行记录接入链路时，除显式 `callApiWithAgent` 外还必须覆盖 split-merge、multi-step、folder 引擎等旁路 API 调用；否则 UI 显示“完整记录”但缺请求体，第三方调试时才发现现场不完整。（09-08 运行记录）
60. 应用内运行记录列表只做最近 20 次滚动窗口；单次运行内部不设条数上限，完整现场同步写入应用数据目录 `run-trace/`。用户按次导出 JSON，导出与落盘都要先做递归脱敏。（09-08 运行记录）
61. 对话型入口（大纲工作台、主页编辑器）的运行记录必须按会话聚合，禁止把每次用户请求切成独立记录；轮次边界以“用户新请求”为准，chain 多次 API、续生成、意图路由短路全部归属同一轮。生成流水线保持单任务粒度，禁止套用会话聚合。（09-10 会话聚合）
62. 会话聚合后的长会话必须每轮 `finishTurn()` 即落盘，禁止等 `finishRun()` 才写盘；磁盘文件名绑定会话开始时间戳并覆写同一文件，写入必须走临时文件 + rename 原子替换，防中途崩溃丢失完整调试现场。（09-10 会话聚合）
63. chat 会话聚合有三个隐蔽陷阱：入口失败提前 return 必须同时复位 generationState；`startRun()` 对 chat 会话禁止无条件 `abandonRunningRun()`；页面 reload 后用 `getLastRunId(source)` 恢复 chat run 指针。主页默认会话的会话键要归一空字符串，`'' === undefined` 会把连续对话拆成碎片。（09-10 会话聚合）
64. 流式累计回调只接受严格前缀增长：`text.startsWith(previous)` 时追加差量，否则一律丢弃；不得用“重叠后缀”推断非前缀回调，否则不同协议的重复/重试回调会被错误拼接进调试现场。（09-11 运行记录深度化 V2）

### 大纲长文档共创（读取、写入、审批）

65. 大纲上下文禁止用固定 12,000 字截断冒充全文；默认注入“当前焦点全文 + 结构地图”，其余通过 `outline.get_structure/read_range/search/get_summary` 按需读取。设定/记忆/选区可保留各自上限，但每个上下文块必须带来源与版本标记，禁止制造“开头即全部”的假象。（09-10 大纲共创阶段1）
66. 结构解析必须有降级路径：编号重复、无标题纯文本降级为段落块索引并标记 degraded；索引区间并集必须完整覆盖原文。读取工具超限分页返回 nextOffset，search 空结果返回引导而不是让模型幻觉；outline 工具组全部只读。（09-10 阶段1）
67. 编辑器写入定位必须统一走 locate 引擎：精确唯一命中才允许执行 `editor.write`，多命中返回 ambiguous_target 并拒绝写入，模糊候选只作诊断；editor.locate 与 editor.write 对同一文本必须给出一致判定，禁止任何路径退回 indexOf 首次命中。（09-16 API 直写成熟化修订）
68. 部分失败批次必须支持“只重提失败条”：诊断返回失败索引、原因、候选位置和建议动作；修正版仍走唯一性与版本校验，成功条目保持原提案。（09-11 阶段2）
69. SKILL chain 与 plain 对话共享同一权限矩阵：意图与阶段决定是否可写，writeMode 只决定写入呈现为提案还是直写；加载 SKILL 不改变权限边界，也不能因为入口不同而绕开统一执行门。所有入口（主页、大纲、共创、plain）必须显式传入同一 intent/writeMode 语义，禁止硬编码 direct 打穿权限。（09-14 权限矩阵修订）
70. 长文档编辑协议注入结构地图、焦点局部、目标节点上下文与结构锚点（volumeTitle/chapterTitle/sectionTitle 双层定位）；兼容 JSON 协议保留但必须在 UI 明示“定位可靠性较低”。（09-11 阶段2/3）
71. pending 编辑批次是会话级状态机：过期批次不可应用、同一批次首答不可变、切换目标/重新生成标记 expired；台账必须完整覆盖 pending/applied/expired/rolled_back。（09-11 阶段3）
72. Diff 卡片化与原文定位：critical override 让内部守卫、按钮 disabled、提交载荷三处同源；完整性面板“有问题才显示”。（09-11 阶段3/4）
73. 影响分析引用必须去重：同一文本范围因二元词碎片被重复计入会灌满 diff 面板；范围重叠检查后只保留有效引用。（09-11 阶段4）
74. chain 中间产物单一所有权：上一步输出只允许一个通道进入下一步（folder 走 inline_block，text 模板引用走 template_variable，否则 context block）；输出契约禁止回显，echo 检测只诊断不阻断。（09-11 单一所有权）
75. 超长聊天气泡渲染门控放在统一入口：`renderMarkdown()` 超 20 万字符直接纯文本预览；原始消息数据不截断，复制、插入、导出仍用完整内容。（09-11 记录深度化 V2）
76. API 对话系统底座统一：主页、大纲、流水线共享权限矩阵、上下文结构、工具声明、批次事件与写入安全模型；横向契约测试 + 三入口真实 UI 验证缺一不可。（09-11 底座统一）
77. 运行记录闭环必须以“导出包能还原完整执行”为验收标准，不以 UI 显示或执行完成回调为准；folder 执行中必须同步 request/system/stream/physicalCalls，异常路径必须由 `finishRun()` 强制清扫 running API。（09-12 卷纲记录六缺陷）
78. 导出 payload 采用 `kind + sha256(规范化内容)` 内容寻址去重：同内容逻辑/物理字段共享同一 payload 并记录 duplicateCount；诊断完整输出移入 `folder-output` payload，主文件只保留 preview/length/ref。（09-12 卷纲记录六缺陷）
79. chain 中间产物注入前必须剥除上一步回显的 `[相关记忆]` 与上一步标题块，并记录 `chain-dedupe`；非末步 `schema.json` 契约失败只 warning 不阻断，默认末步校验语义保持不变。（09-12 卷纲记录六缺陷）
80. **产物有效性门必须在 postProcess 之前执行**：空正文、reasoning 耗尽、截断要在进入后处理与 chain 传递前判定；“请求没有抛异常”不是产物有效证据。（09-12 产物有效性修复）
81. **run 状态必须由 API 终态与 folder diagnostics 共同归并**：failed > canceled > degraded > success；任何一层禁止把 degraded 折叠成 success。（09-12 产物有效性修复）
82. **folder 失败路径必须完整落 trace**：返回对象要携带 `folderPackageCache/postProcessReport/apiMeta`，Pipeline catch 要消费 `error.folderResult` 并写入运行记录，否则 SKILL 调试方无法还原失败现场。（09-12 产物有效性修复）
83. **显式零值禁止被默认值回退吞掉**：`sampleCount: 0` 表示禁用全局样本注入，不能被 `|| 3` 归一回默认数量。（09-12 产物有效性修复）
84. **长流渲染必须 delta + 节流**：流式回调输出新增文本，UI 只在帧级或 50-100ms 节流点合并更新；每个 chunk 全量过滤、截尾、滚动会把长 reasoning 流放大成 O(n²) 压力并触发 Windows Application Hang。（09-12 挂死修复）
85. **静默重试必须可见可取消**：空正文直出重试必须发出 `generation-invalid`、`direct-retry-start`、`direct-retry-finished` 结构化事件，进入进度 UI 与运行记录；重试期间允许用户立即取消，失败消息要给出换模型、调配置、导出 trace 的行动指引。（09-12 挂死修复）
86. **重试与失败路径必须落完整 trace**：开始/结束时间、duration、status、reasoning 长度、final text 长度、finish_reason、usage、重试阶段与物理请求都要可从导出 JSON 还原；三入口共用同一事件结构。（09-12 挂死修复）
87. **降级终态不得折叠为失败**：run/turn/API 的 `degraded` 必须走 `finished`/`turn-finished`/`api-degraded` 事件、`warn` 级和“完成（降级）”标签；只有 failed/canceled 才是失败态。（09-12 降级运行记录）
88. **降级必须用影响产物的 warning 白名单判定**：协议/调试类 info 或 warning（模板变量缺失、非末步 schema 契约提示）只进诊断，不改变成功状态；新增降级码必须先证明它影响交付输出。（09-12 降级运行记录）
89. **chain 记忆单一所有权适用于每一步**：任意步骤追加 `[相关记忆]` 前都必须检查 prompt 中是否已存在，首步透传、非首步拼接、folder 回显三条路径都要防双注入。（09-12 降级运行记录）

90. 存储腐败日志必须封顶并去重：`appendCorruptionLog` 超过 50 条只保留最后 50 条，迁移前先 JSON.parse 校验，损坏文件直接跳过；UI 只报告新腐败记录，不得用 error 级别反复刷历史问题。（09-09 日志修复）

96. 兜底逻辑要有边界：技能配置“空了就自动补一个”的下标兜底会悄悄执行别的层的技能，比直接报错更危险；未配置就是空。（09-09 流水线注入链路）
97. 正文层硬规则必须白名单化：通用文章降AI规则不能直接复用给小说正文；带标点正则必须用捕获组回填标点；所有改写正文的入口统一走 `processBody()` 安全入口。（09-09 正文安全化）
98. 结构回滚门是最后保险丝：段落数、句尾标点数、长度比例任一异常整段回滚原文；未来有人往替换表加危险正则也砸不穿正文。（09-09 正文安全化）
99. 降AI职责分层：前置方法论注入模型生成，本地层负责检测、报告、门禁；深度修复只允许最小编辑并通过完整性校验，自动改写不作为默认路径。（09-09 降AI V2）
100. 导出对象也要完整性核查：服务内实现了函数不等于导出了函数；新增服务 API 的单测必须覆盖“从导出对象调用”这一层。（09-09 降AI V2）
101. mock 协议必须匹配真实请求形态：`stream:true` 时 mock 只回普通 JSON 会得到空文本，伪装成“API 成功但字数 0”；先确认 stream、消息结构、finish_reason。（09-09 降AI V2）
102. 验证脚本要有防假通过门槛：mock 必须收到探测请求才算验证生效；未收到请求时不得用真实供应商兜底。（09-09 降AI V2）

104. folder 路径每个技能必须有独立 API 记录：调用前 start、成功/失败/抛错都 finish；复用第一步 callId 且不关闭会制造永久 running 僵尸记录。（09-10 记录膨胀）
105. 被污染的调试数据会误导诊断：第三方基于膨胀 streamText 统计词频会误判上下文滚雪球；真实请求以 `folderDiagnostics.apiMeta.requestMessages` 为准。（09-10 记录膨胀）
106. folder 包 `SKILL.md` frontmatter 后的完整正文必须进入 system prompt，注入顺序固定：智能体 -> SKILL.md 正文 -> template.md -> 资源 -> 后缀；body 与 template 相同去重。（09-10 Folder 阶段2）
107. 激活后的 folder 资源无截断注入：每个资源带 `[folder resource: 相对路径]` 标头完整进入请求；目录披露只发生在选中前，激活后上下文完整。（09-10 Folder 阶段2）
108. `skill.json` manifest 优先于 frontmatter：id/name/version 冲突产生 warning；坏 JSON 降级 warning 不阻断导入；同路径绑定不同 id 也要显式 warning。（09-10 Folder 阶段3）
109. postProcess 支持纯 stdout 结构化 JSON：executor 对 `consumedStructuredOutput` 白名单归一化，社区脚本无需强制导出函数。（09-10 Folder 阶段3）
110. folder 评测必须 with/baseline 双路：六种本地断言可判定；执行失败降级 failed case 不中断整轮；评测按钮显式触发，不自动调用 API。（09-10 Folder 阶段4）
111. payload 外置引用只能携带 id：`__payload` 禁止内联 `value/kind/identity` 等完整对象，否则首次出现的载荷仍留在主 trace；外置化改造必须用真实大体积 trace 复测主文件体积与零内联断言。（09-13 卷纲三缺陷）
112. 所有诊断嵌套大文本字段必须逐项盘点：`folderDiagnostics.apiMeta.requestMessages`、`postProcessReport.output` 等会绕过既有外置点；新增长文本字段时同步注册 payload 收集与 preview/ref 替换。（09-13 卷纲三缺陷）
113. postProcess issue 的 code 可能为空：降级判定不得依赖 `post-process-issue:` 后缀恒存在，必须对裸 `post-process-issue` + message/code 白名单做分级；run 终态必须归并 folder diagnostics。（09-13 卷纲三缺陷）
114. 请求级元数据必须在结果可用前写入：`lastRunMeta` 只在成功路径 set 会让空响应/异常丢失 finishReason；可结束点（空输出、超限、异常、取消）之前先落元数据，再进入失败分支。（09-14 大纲空等修复）
115. 外置化改造必须兼容旧导出格式：旧 trace 可能已在字段里保存 `{ __payload: { kind, value } }`；再导出前必须先解包旧 value，再统一走 preview + ref。验证断言不能只看新造数据，要用旧导出文件复测零内联与主文件体积。（09-13 卷纲三缺陷复验）
116. payload 哈希与落盘字节必须同源：prompt 先做语义规范化（剔除 `id/builtAt/apiCallId/turnId/payloadRef`）后，哈希计算与文件写入必须使用同一份内容；否则真实快照会全部 hashMismatch。合成测试夹具必须覆盖真实易变字段，否则导出校验假绿。（09-13 compose folder V2 复验）
117. **chain 交接必须协议化对账**：上一步输出进入下一步前先生成 handoff artifact（hash、长度、delivery、必要片段、全文权限）；重复 hash 必须发事件。第三方 SKILL 未声明全文权限时默认 handoff + 全文存档可读，strict 前先 warn-only 收集真实样本。（09-15 调用路径审计 V2）
118. **隐藏 AI 外呼也要有 Trace 归属**：provider 拉模型/测连接归 `infra`，后台写作工具归 `background`，业务 run 归各自 source；Electron 的 traceDir、导出、删除路径必须同步识别 source，否则 UI 有记录但落盘/清理走错目录。（09-15 调用路径审计 V2）
119. **finally 只做安全封尾，不得改写业务终态**：catch 已产生 failed/canceled 时，finally 遇到终态冲突只发 `status-conflict-ignored`，禁止把 run 折叠成 success；结果归一统一走 `classifyRunOutcome()`，空产物、截断、取消、失败和 degraded 语义一处维护。（09-15 调用路径审计 V2）
120. **UI 导出通道必须验证 IPC 边界两端的递归序列化**：`String()` 直接包装对象会产出 `[object Object]`；diff/trace 类导出前必须在渲染层递归脱敏，主进程侧保持同规则双层防护。（09-16 RunTraceDiff）
121. **测试钩子禁止在模块加载期固化**：读取 `window.__TEST_OVERRIDE__` 一类运行时钩子时，必须在每次创建实例/消费时点实时读取；模块加载期赋值会把覆盖固化成加载时的空值，E2E 运行期注入永远失效，制造“修复未生效”的假失败。（09-16 tool-loop 悬死修复）
122. **取消/中止收口必须同时覆盖 API call 与 physicalCalls**：服务层回调可能因 abort 竞态没有机会执行；观测层兜底必须同步闭合同 call 下的 running 物理请求，否则 trace 留下 api-call 已结束但 physical-call 永远 running 的僵尸现场。（09-16 tool-loop 悬死修复）
123. **请求级 supervisor 只 abort 不抢终态**：停滞/总上限/重复工具错误的终态仍由业务 catch 与 `finishRun/finishTurn` 收口；supervisor 只负责 controller.abort 与 runTrace/DiagLogger 双侧报告，禁止观测器改写业务终态。（09-16 tool-loop 悬死修复）
124. **警告不等于收束**：工具循环到达上限后，仅提示“模型未输出正文”无法改变模型行为。必须在下一请求里移除 tools 并注入“停止调用任何工具、基于已有工具结果直接输出最终回答”的收敛指令；否则模型会继续工具调用，应用只能返回空正文。收敛请求默认保持非流式，与工具轮响应形态一致。（09-17 tool-loop 收敛补漏）
125. **多流契约必须按字段分层**：同一请求里不同流字段可以有不同契约，但必须显式声明并对齐全部消费者：正文 `onChunk` 保持累计/严格前缀守卫，reasoning `onReasoning` 是 delta；记录层只做各自语义的追加，禁止把一个字段的累计/delta 规则复制给另一个字段。契约变更时必须同步 aiService、runTrace、PipelinePanel、OutlineWorkspace、ChatPanel 与旁路入口的入口矩阵，并在最终 API call 回填完整 `reasoningText`；所有 `finishApiCall` 成功终态必须显式回填 `reasoningText`，trace 接口字段与实现同步演进。回调累计值与返回值不是天然同源，最终回填必须以同一份过滤后全文为准，并用“回调拼接等于返回值”做回归断言；流式过滤器的 `flush()` 尾巴必须同时进入回调和返回值。终态或同 physicalCall 的文本更新禁止“非空即覆盖”：必须先归一 `undefined`，再用长度门允许更长 canonical 全文替换局部累计、阻止短 legacy/迟到空载荷倒退；物理记录已终态时 running 回调不得覆盖任何现场。正文流式与 reasoning 流式在记录层必须拥有同样的终态守卫，禁止只有一个字段防迟到 delta、另一个字段可继续写入；UI 流式缓冲不得隐式依赖 `currentApiCallId` 归属，后续结构改动必须携带显式 callId。物理记录回填逻辑记录时必须同向处理正文与 reasoning，触发条件不能只看正文；多调用合并（重试/续写）后的最终 meta 必须使用最后一次有效调用的 canonical reasoning。reasoning、responseText、streamText 分别用短旧值、长新值、迟到 running 空载荷、迟到正文 delta、空逻辑字段物理回填、多调用合并回填回归。（09-19 reasoning 契约分叉、flush 尾巴截断、物理终态载荷倒退、共享流式入口缺守卫与旁路现场缺口）
126. **卷纲计划变量必须单一事实源**：计划卷数、已生成卷数、当前卷预算与剩余字数由 `volumePlanIntegrity` 统一计算；生成、续生成、自动生成、模板上下文与 prompt 共用同一结果，写回前统一钳制，超预算与计划冲突必须发 `volume-budget-clamped` / `[卷纲计划冲突]` 可见记录。禁止入口各自读取设置或按数组长度临时推导，防止“已生成部分卷后继续补齐全量计划”。（09-19 卷纲计划分叉）

### 防无限回滚铁律

1. 每项任务完成勾选并经验证后视为终态闭环，不可整体回滚重做。
2. 后续任务发现前期问题，只能在当前状态上精准修复，不得回滚整个阶段。
3. 精准修复后必须重新验证该修复项，但不需要重验该阶段其他已通过项。
4. “我觉得可以做得更好”不是回滚理由；只有“功能行为与旧架构不一致”才是修复理由。
5. 回滚请求必须附具体证据（哪个行为不一致、哪个按钮失效、哪个数据丢失），不得笼统回滚。
6. 已验证的截图和日志保留为不可推翻证据，不得以“怀疑有问题”推翻。
7. 修复导致新 bug 时修复新 bug 即可，不需要回滚到修复前状态从头来。
8. 勾选清单中每一项一旦标记完成并附验证证据，即视为永久完成，不可撤销。

### 经验回写铁律

1. 每次开发前必须读取本文件，确认已遵守全部规则。
2. 每次开发完成后必须更新本文件，记录新错误/新经验；新经验按区块归位，禁止尾部日期章节。
3. 每次开发完成后必须更新 DEV_LOG，按日期追加；DEV_LOG 写“发生了什么、怎么修、怎么验”，本文件只写“以后怎么做”。
4. 经验总结和开发日志必须与代码变更一起提交 GitHub。
5. 禁止出现“改了代码但没更新文档”的未闭环状态。
6. 新经验先提炼成规则进入 §1-§9；只有当时有用、事后价值衰减的一次性快照不写入本文件，只进 DEV_LOG。
7. 本文件是唯一经验规则文件；出现新版本重整时，旧经验规则文件必须删除，主索引和活跃文档必须指向新版本。（09-13 经验文件 v5）
