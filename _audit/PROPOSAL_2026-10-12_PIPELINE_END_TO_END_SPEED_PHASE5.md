# 生成流水线全层速度优化 Phase 5 方案

## 状态

待审核。本方案是对用户纠偏的正式响应：不能把“正文层生成慢”当作单层问题，必须把整个生成流水线作为同一个速度系统分析。方案本身按 G0.6 判定为成熟，附执行证据边界：未采集的层耗时数据是 Phase 5A/5B 的输入，不构成方案设计断点。

## 原始目标

用户定义的效率不是省 token，而是：

1. 加载速度：进入一层、构造请求、拿到可执行上下文的耗时。
2. API 响应速度：首 token 等待。
3. 流式生成速度：持续输出吞吐，不允许十位数缓慢跳动。
4. 全任务总耗时：Step 0 到 Step 4 的端到端墙钟时间。
5. 请求形态：不能把长任务拆成几十次低效物理往返。
6. 用户体验：10 小时级生成属于系统性效率问题，不是正常模型耗时。

## 范围

### Step 0 大纲风格分析

- 独立 API call，当前仅记录普通 runTrace，没有 `timingLedger`。
- 需要补齐：请求构建、首 token、流式输出、本地解析、状态保存。
- 重点疑问：是否阻塞后续层；分析结果是否重复请求；供应商返回速度是否合理。

### Step 1 设定层

- 使用 `generateSettingsArtifact` 编排器。
- 需要补齐：单次请求结构、契约验收、修复请求次数、上下文长度。
- 重点疑问：是否每次全量大纲注入；是否有重复上下文；修复请求是否放大总耗时。

### Step 2 卷纲层

- 已有 Phase 1-4 观测与真实 live 采样。
- Phase 2 结论：12 API call / 13 physical requests，3 卷成功，模型流式输出占主导。
- Phase 3 已修复：物理重试计时口径、活跃流式不被 600 秒总时长切断、idle supervisor 盲区。
- Phase 4 已做：历史块去重、重复块观测、full handoff 契约观测。
- 本层作为其他层的基线模板，不是唯一优化对象。

### Step 3 章节层

- 使用 `generateChapterBatch` 编排器。
- 当前按批次生成章节，默认每批最多 5 章。
- 重点疑问：批次数是否过多；每批是否重复携带全量大纲、设定、风格；断点恢复是否重复读取。

### Step 4 正文层

- 使用 `generateBodyArtifact` 编排器。
- 当前单次只生成一章正文，依赖上游执行包。
- 重点疑问：单章生成耗时、目标字数、模型输出上限、供应商吞吐、流式状态、重试策略。

### 记忆抽取

- 独立 API 调用链路。
- 当前未纳入同等级耗时账本。
- 重点疑问：是否阻塞正文确认；是否可以异步；超时配置是否合理。

### 层间等待

- 当前缺少 step-boundary 耗时观测。
- 重点疑问：Step 0 完成到 Step 1 开始之间的等待、Step 2 到 Step 3 的等待、Step 3 到 Step 4 的等待、用户确认等待。

## Phase 5A 全层耗时账本补齐

### 目标

让 Step 0、Step 1、Step 3、Step 4、记忆抽取达到与 Step 2 同等级的耗时结构观测。

这一步是执行数据补齐，不是方案设计补丁。任何层无法套用现有字段时，先扩展 schema 并补充测试，不得为凑字段改变执行行为。

### 设计

扩展 runTrace schema，新增 step 级 `stepTimingLedger`：

- `promptBuildMs`
- `contextLoadMs`
- `apiCallCount`
- `physicalCallCount`
- `retryCallCount`
- `schemaRetryCallCount`
- `continuationCallCount`
- `firstTokenSumMs`
- `outputSumMs`
- `postProcessSumMs`
- `validationSumMs`
- `persistenceSumMs`
- `stepBoundaryGapMs`
- `repeatedPromptBlocks`
- `contextChars`
- `outputChars`
- `physicalDurationSumMs`

### 关键点

1. 不改变任何执行行为，只补观测。
2. 不允许用上游 prompt 长度冒充物理请求长度。
3. 不允许分段计时重叠。
4. 不允许把“模型生成慢”和“应用等待慢”混在同一个字段里。
5. 所有新字段必须可选，旧 trace 不回填。

## Phase 5B 全层真实运行采样

### 目标

不是只跑正文层，而是每一层都拿到真实耗时结构。

### 采样矩阵

| 层 | 真实 API | Electron 真实 UI | 采样目标 |
|---|---|---|---|
| Step 0 | 是 | 是 | 首次分析与二次进入耗时 |
| Step 1 | 是 | 是 | 请求次数、上下文长度、修复放大 |
| Step 2 | 是 | 是 | 继续复用 Phase 2 作为基线 |
| Step 3 | 是 | 是 | 批次数、每批上下文重复度、总耗时 |
| Step 4 | 是 | 是 | 单章生成耗时、流式吞吐、重试放大 |
| 记忆抽取 | 是 | 是 | 是否阻塞用户确认、超时合理性 |
| 端到端 | 是 | 是 | Step 0→4 完整耗时结构 |

### 采样原则

1. 使用真实供应商，应用内默认 API 凭据。
2. SKILL 通过真实 UI 下拉选择，禁止脚本注入。
3. 每层至少跑一次成功 run 和一次重试路径。
4. 端到端 run 必须覆盖至少 3 卷，章节层和正文层必须有真实生成量。
5. 导出 deep trace、payload、heartbeat、summary、timing-analysis。
6. 不删除证据目录，失败 run 归档。

## Phase 5C 耗时结构分析

### 目标

把“慢”拆成可归因的四类：

1. **模型输出耗时**：`firstTokenSumMs` + `outputSumMs`，这是模型侧结论。
2. **请求形态耗时**：物理请求次数、重试次数、批次切分数造成的总耗时放大。
3. **本地处理耗时**：prompt 构建、校验、后处理、持久化、状态同步。
4. **层间等待耗时**：用户确认、UI 等待、队列等待、跨层依赖等待。

### 分析矩阵

| 层 | 请求形态 | 上下文膨胀 | 物理请求放大 | 输出吞吐 | 层间等待 |
|---|---|---|---|---|---|
| Step 0 | 是 | 是 | 是 | 是 | 是 |
| Step 1 | 是 | 是 | 是 | 是 | 是 |
| Step 2 | 是 | 是 | 是 | 是 | 是 |
| Step 3 | 是 | 是 | 是 | 是 | 是 |
| Step 4 | 是 | 是 | 是 | 是 | 是 |
| 记忆 | 是 | 是 | 是 | 是 | 是 |

## Phase 5D 系统性优化方案

### 1. 请求形态优化

目标：减少不必要的物理请求和重复携带上下文。

措施：

- 审计每层的批次切分依据。
- 章节层批次数与请求耗时建立函数关系。
- 正文层评估单章请求与输出上限的关系。
- 设定层、章节层、正文层复用 Phase 4 的重复块观测。
- 建立每层“最少必要上下文”标准。

### 2. 流式输出吞吐优化

目标：让生成速度达到供应商正常吞吐水平。

措施：

- 记录每秒字符数，识别是否十位数缓慢跳动。
- 对比同一供应商同一模型在网页端的正常生成速度。
- 检查 `maxTokens`、流式配置、模型路由、供应商配置。
- 保留 Phase 3 的活跃流不切断策略。
- 识别慢流是否由供应商、网络、应用限流或输出模式造成。

### 3. 本地处理优化

目标：消除应用自身造成的阻塞。

措施：

- 分段计量 `promptBuildMs`、`validationSumMs`、`postProcessSumMs`、`persistenceSumMs`。
- 识别 `saveProject` 是否在生成过程中造成卡顿。
- 识别 `refreshTree`、编辑器插入、UI 状态更新是否阻塞主流程。

### 4. 层间等待优化

目标：消除无意义的空闲时间。

措施：

- 新增 step-boundary 耗时。
- 识别用户确认等待与应用空闲等待。
- 记忆抽取评估是否可以异步，不阻塞正文确认。
- 可并行且无状态冲突的任务评估受控并行，不得破坏依赖。

### 5. 上下文与产物复用

目标：避免同一内容在层与层之间反复注入。

措施：

- 全流水线统一使用 canonical excerpt 或产物契约。
- 不再每层重复携带全量大纲、全量设定、全量风格上下文。
- 评估 S2/S3/S4 使用 structured handoff，而不是 full handoff。
- 每个 prompt 的重复块计数必须进入 timing analysis。

### 6. 端到端总耗时优化

目标：把用户可感知的总耗时从小时级压到可接受范围。

措施：

- 建立 `totalWallClockMs`、`userVisibleWaitMs`、`generationThroughputCharsPerSec` 三个核心指标。
- 优化后重跑端到端 run，对比 before/after。
- 不允许只报告“请求数减少”而总耗时未下降。
- 不允许只报告“token 减少”而用户可见速度未提升。

## Phase 5E 验证方案

### 单元与回放验证

- 每个新增观测字段必须有“生产事件 → runTrace 入口 → 存储导出”链路断言。
- 覆盖成功、重试、失败三类路径。
- 计时字段必须证明不重叠、不负数、不冒充。

### Electron 真实 UI 验证

- 可见窗口真实操作。
- SKILL 通过真实下拉选择。
- 每层真实 UI 启动一次成功 run。
- 端到端至少一次完整流水线。

### 真实 API live 验证

- 每层至少一次成功 run + 一次重试路径。
- 端到端至少一次完整 run。
- 采集流式吞吐、首 token、总耗时、物理请求数。
- 供应商波动必须记录，不允许把单次波动当结论。

### before/after 对比

优化前后各至少一次同环境 run：

1. 同一项目。
2. 同一供应商。
3. 同一模型。
4. 同一 SKILL 配置。
5. 同一并发策略。

对比字段：

- 端到端总耗时。
- 每层耗时。
- 物理请求数。
- 重试请求数。
- 首 token。
- 流式输出吞吐。
- 上下文字符数。
- 产物质量契约通过率。

## 停止条件

以下条件全部满足才允许结束：

1. Step 0、1、3、4、记忆抽取全部有 `stepTimingLedger`。
2. 每层至少一次真实 Electron + 真实 API 成功 run。
3. 端到端至少一次完整 run，能拆出四类耗时归因。
4. 优化后 before/after 数据同环境可对比。
5. 产物契约不降低，生成质量不因速度优化被牺牲。
6. 无重复上下文块异常膨胀。
7. 无负数计时、无分段重叠、无观测冒充。

## 非目标

- 不以省 token 作为目标，token 只是手段。
- 不为速度牺牲产物质量。
- 不允许未采数据前直接改并发策略。
- 不允许凭单一供应商样本直接改模型路由。
- 不允许跳过 Electron 真实 UI 验证。

## 成熟度

**成熟，附执行证据边界。**

依据：

- 观测设计、验证方法、执行顺序、停止条件均已明确。
- 目标不是省 token，而是用户可见的加载、首 token、流式吞吐、请求形态和端到端总耗时，与用户最新纠偏一致。
- 范围覆盖 Step 0、Step 1、Step 2、Step 3、Step 4、记忆抽取和层间等待，不是单层方案。
- 已有可复用证据链：本地毫秒级变换、1M 窗口单次请求的反面教训、卷纲真实 timing ledger、Phase 4 重复块观测、章节契约模式、产物契约统一方向。
- 风险控制明确：先观测、后采样、再优化；所有优化必须同环境 before/after；不允许牺牲产物质量。
- 验证方式明确：单元与回放、Electron 真实 UI、真实 API、失败路径、before/after、deep trace 对账。

执行证据边界：

- Step 0、1、3、4、记忆抽取的真实耗时数据尚未采集，属于 Phase 5A/5B 的执行输入。
- Phase 4 的 live 复证尚未执行，不能把本地测试通过表述为 live 已通过。
- 在 Phase 5B 采样完成前，不允许对未采样层下优化结论。

放行条件：用户确认后按 5A → 5B → 5C → 5D → 5E 顺序执行；发现新缺陷时先登记并评估是否阻断，不得边采样边隐藏问题。
