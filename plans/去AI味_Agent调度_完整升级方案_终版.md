# 去AI味 Agent调度模式 完整升级方案（终版）

## 一、需求来源与演进

### 第三方原始反馈

第三方指出：当前去AI味的 Agent 只是一个配置容器，存了 {name, model, temperature, maxTokens, systemPrompt}，没有任何调度逻辑。链式调用是固定 for 循环：SKILL1输出 -> SKILL2输入 -> SKILL3输入，串行走到底。速度慢，Agent形同虚设。

第三方提出方案：加一个"切分+并行+拼接"模式，用Agent负责调度，让去AI味从串行变并行。

### 讨论中的关键决策

决策1：切分由本地代码做，不调API
- 第三方原方案第一步调API让模型切分文章，多花一次调用、有延迟、有格式解析失败风险
- 改为本地代码切分：省一次调用、零延迟、零格式风险
- 段落本身就是天然语义边界，不需要AI来判断在哪切

决策2：Agent的价值在于"每段怎么处理"而非"怎么切"
- 用户问：切分由本地做，Agent存在还有什么意义？
- 答案：Agent负责每段重述时的系统提示、模型选择、温度控制，它是每段重述的核心引擎
- 切分大小：用户在UI填数字，本地代码执行
- SKILL：输出约束，每段重述的方法论
- 并行调度：应用代码并发执行，限流3个

决策3：切分用语义边界，不硬切字数
- 用户提出核心问题：用户填1000字，但994-1025字处是一个完整句义，切了就破坏语义
- 三层切分逻辑：
  1. 段落优先：按换行符分隔段落，累积到目标字数后在段落边界断开
  2. 句号兜底：长段落内部从目标字数往后找最近的句号断开
  3. 容错回退：找不到句号往前找，再找不到直接断（极端情况）

决策4：浮动窗口机制
- 用户提出：用户选1000字，但语义可能在1100字完成，就切到1100字
- 用户填的字数是"期望值"不是"硬限制"
- 实际切分范围 = 期望值上下浮动30%（填1000字则可切区域700-1300字）
- 在可切区域内找最近的段落边界或句号
- 找到就切，实际切口可能落在800字或1100字，由语义决定

决策5：并行容错
- 限制并发数最多3个（防止429限流）
- 每段独立catch，失败的段落保留原文，不中断整体流程
- 不用Promise.all（一个失败全崩），改用手动队列+计数器实现

决策6：拼接还原原始排版
- 切分时记录每段之间的原始连接符
- 拼接时用原始连接符还原，不强行加双换行

## 三、技术架构

### 两种模式对比

串行链式模式（现有，完全不动）：
- 全文 -> SKILL1 -> SKILL2 -> SKILL3 -> 硬规则 -> 输出
- 3次API串行调用，总延迟 = 3倍单次
- 适合需要多步骤处理的场景（如白虎S1-S2-S3链式）

Agent调度模式（新增）：
- 全文 -> 本地切分N段 -> N段并行重述（限流3个）-> 拼接 -> 输出
- 1次API级别的延迟（3段并行只需等最慢的一段）
- 适合单SKILL重述的长文本场景

### _splitText 三层切分逻辑

第一层 段落优先：
- 按换行符分割成段落
- 累积段落到目标字数后，在段落边界断开
- 这是最自然的切分方式，不会切断任何句子

第二层 句号兜底：
- 当单个段落超过maxSize时，在段落内部找句号
- 从minSize位置往后找最近的句号
- 找到就切，保证不切断句子

第三层 容错回退：
- 往前找句号
- 再找不到就硬切（极端情况，几乎不会发生）

浮动窗口：
- minSize = 目标字数 x 0.7
- maxSize = 目标字数 x 1.3
- 在minSize到maxSize之间找最近的语义边界
- 尾部碎片合并：最后一段如果太短（小于 minSize/2），合并到前一段

### _deAiSplitMerge 并行调度

核心流程：
1. 获取Agent配置（model, temperature, systemPrompt）
2. 获取输出SKILL（只需1个）
3. 本地切分文章 -> segments数组
4. 并行重述（限流3个并发）
5. 拼接还原 -> 写回编辑器

并发控制（手动队列+计数器）：
- maxConcurrent = 3
- queue数组存放待处理段索引
- schedule函数：有空闲位就取下一段处理
- 每段处理完running减1，检查是否还有待处理
- 全部完成 -> 拼接 -> 关闭进度条

每段处理：
- prompt = 段落文本 + 换行 + 技能约束 + SKILL模板
- system = Agent的systemPrompt（或默认提示）
- stream: true（强制流式，进度条实时更新）
- maxTokens: _getAgentMaxTokens()（至少128000）
- onChunk: 根据已接收字符数更新进度
- onReasoning: 显示AI思考中
- catch: 失败保留原文，不中断

### 进度条适配

串行链式进度：
- 按步骤数均分（SKILL1 + SKILL2 + SKILL3 + 硬规则）
- 每步内subRatio = 已接收字符数/预估输出长度

Agent调度进度：
- 按已完成段数/总段数计算
- 每段内subRatio = 已接收字符数/预估输出长度
- 步骤列表显示：段落1 (1218字) / 段落2 (1215字) / 段落3 (1113字)

## 四、用户体验流程

### 串行链式模式（现有，不变）
1. 设置页 -> 去AI味选项卡
2. 添加多个SKILL（如白虎S1-S2-S3）
3. 选Agent（可选）
4. 硬规则开关（默认开）
5. 保存
6. 编辑器正文 -> 点去AI味按钮
7. 进度弹窗显示SKILL1 -> SKILL2 -> SKILL3 -> 硬规则
8. 结果写回编辑器

### Agent调度模式（新增）
1. 设置页 -> 去AI味选项卡
2. 模式选择：Agent调度
3. 填切分字数（如1000，范围500-3000）
4. 添加1个输出SKILL（如白虎重述师）
5. 选Agent（控制模型/温度/系统提示）
6. 硬规则开关（默认开）
7. 保存
8. 编辑器正文 -> 点去AI味按钮
9. 进度弹窗显示段落1/3 -> 段落2/3 -> 段落3/3（并行推进）
10. 结果写回编辑器

## 六、风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| 并发触发429 | 限流3个，每段独立catch |
| 跨段上下文断裂 | 接受此代价（分段独立处理的本质） |
| 切分不均匀 | 浮动窗口30%，由语义边界决定实际切口 |
| API返回空 | 保留原文，不中断 |
| 取消操作 | AbortController传给每个请求 |
| 进度条卡0% | stream:true强制，onChunk实时更新 |

## 九、与第三方方案的差异

| 第三方原方案 | 我们的方案 | 原因 |
|-------------|-----------|------|
| 调API让模型切分文章 | 本地代码切分 | 省一次调用、零延迟、零格式风险 |
| 用Agent的systemPrompt做切分指令 | Agent只做重述引擎 | 切分是机械操作不需要AI |
| Promise.all并行 | 手动队列限流3个 | 防止429，单段失败不崩全局 |
| 硬切字数 | 浮动窗口30%+语义边界 | 不破坏句子完整性 |
| 固定切分大小 | 用户可配置500-3000 | 灵活适配不同正文长度 |
| 拼接加双换行 | 还原原始连接符 | 保持排版格式不变 |
