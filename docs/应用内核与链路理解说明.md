# 应用内核与链路理解说明

> 审查对象：`D:\codex\novel-workshop-vue3`（神意助手）
> 当前版本：`3.118.0`
> 结论性质：本轮为源码静态深度解析，覆盖数据、UI、编排器、契约、执行器与持久化链路；未执行真实供应商调用或完整 Electron UI 实测。运行时验证结论必须另跑应用实测后才能声明。

## 1. 一句话内核

应用以“项目态 + 锁定大纲 + 流水线分层契约 + SKILL/Agent 可插拔执行”为核心。大纲一旦锁定，会冻结为 `outlineLockedText` 并成为后续所有层的上游事实源；流水线按“大纲字数确认 → 设定 → 卷纲 → 章节 → 正文”顺序逐层物化，层与层之间不靠自由聊天承接，而是靠结构化契约、验收器、修复循环、断点和 RunTrace 保障可复跑。

## 2. 技术栈与工程结构

- Vue 3 + Pinia + Electron + Vite + TypeScript。
- 核心状态集中在 `src/stores/project.ts` 与 `src/stores/pipeline.ts`。
- 大部分编排逻辑不在 Vue 组件里内联，而是在 `src/services/*` 的独立可测模块中。
- Electron IPC 主要负责存储、SKILL 加载、RunTrace 等桌面侧能力。
- 服务层存在大量 `.spec.ts`，说明契约层以纯函数测试为主要防线。

关键目录：

| 目录 | 职责 |
|---|---|
| `src/stores/project.ts` | 项目、大纲、锁定态、设定/卷/章/正文、防抖保存 |
| `src/stores/pipeline.ts` | 步骤注册、断点、层配置、Skill/Agent/模式 |
| `src/components/common/OutlineWorkspace.vue` | 大纲工作台 |
| `src/components/pipeline/PipelinePanel.vue` | 五层流水线 UI 与编排入口 |
| `src/services/` | 各层协议、验收、上下文闭包、执行包、SKILL 执行器 |
| `electron/ipc/storage.js` | 原子持久化与备份恢复 |

## 3. 数据模型与持久化

### 3.1 项目事实源

`src/stores/project.ts` 是项目数据的中枢：

- `outlineText`：当前可编辑大纲。
- `outlineLocked`：是否锁定。
- `outlineLockedText`：锁定时的冻结文本。
- `bookWordCountChars`：全书字数，单位为字符。
- `settings`、`volumes`、`chapters`、正文状态：流水线逐层物化后的数据。
- `pipelineConfig`：卷数、总字数、章节字数等基础配置。

关键函数：

- `setOutline()`：更新大纲文本。
- `lockOutline()` / `unlockOutline()`：切换冻结态。
- `pipelineOutlineText`：上游文本 getter。锁定时返回 `outlineLockedText`，这是所有流水线生成器的统一输入。
- `saveProject()`：防抖保存项目态。

源码证据：`src/stores/project.ts:1095`、`src/stores/project.ts:1100`、`src/stores/project.ts:1112`。

### 3.2 Electron 存储链路

`electron/ipc/storage.js` 提供 `storage:read/write/remove/list/export/import/getDataDir/openDataDir` 等 IPC。

存储特点：

- 主写入路径为 tmp → rename → primary → bak → tmp，形成原子写与备份恢复。
- primary 缺失或 JSON 损坏时可从 bak 恢复，并写 corruption log。
- 存储键统一 `wa_` 前缀，项目键形如 `wa_project_{id}`。
- 自定义数据目录可通过 `SHENYI_DATA_DIR` 控制。

## 4. 大纲工作台

`OutlineWorkspace.vue` 是大纲的导入、编辑、AI 共创、锁定入口。

### 4.1 用户主链路

1. 用户导入或粘贴大纲文本。
2. 编辑器写入 `projectStore.outlineText`。
3. 用户点击锁定。
4. 锁定动作除了切换状态外，还同步流水线树并触发一次自动拆解。

源码证据：

- 导入链路：`src/components/common/OutlineWorkspace.vue:4095` 起。
- 锁定函数：`src/components/common/OutlineWorkspace.vue:4622` 起。
- 锁定后同步与自动拆解：`src/components/common/OutlineWorkspace.vue:4649`、`:4657`。

### 4.2 锁定语义

锁定不是普通编辑开关，而是一次事实源提交：

1. 当前 `outlineText` 冻结到 `outlineLockedText`。
2. `pipelineOutlineText` 从“可变文本”切换为“冻结文本”。
3. 工作台同步树结构到流水线。
4. 自动提取设定与伏笔类信息。

因此，外部生成的大纲必须在导入后先完成审校，再锁定。锁定后若大纲需要改，应该显式解锁并重新走同步链路，不能假设流水线会自动感知旧锁定文本外的修改。

### 4.3 完整性守卫

`src/services/outlineIntegrity.ts` 负责检测：

- 结构覆盖缺失。
- 标题丢失。
- 正文内容骤减，低于阈值时阻断。
- 章数爆炸，超过阈值时警告。
- 重复标题。

删除类编辑还有独立授权契约：

- `outlineDeletionContract.ts`
- `outlineDeletionAuthorization.ts`

这保证大文档、AI 改写和删除操作不会静默吞掉标题或成段内容。

## 5. 生成流水线总控

`PipelinePanel.vue` 是流水线主界面，`src/stores/pipeline.ts` 是步骤注册与运行态中心。

### 5.1 五个步骤

| 步骤 | 名称 | 输入 | 产物 |
|---|---|---|---|
| 0 | 大纲层 | 外部/工作台大纲 | 锁定大纲 + 全书字数 |
| 1 | 设定层 | 冻结大纲 | 设定卡 |
| 2 | 卷纲层 | 冻结大纲 + 设定 + 字数计划 | 卷纲数组 |
| 3 | 章节层 | 冻结大纲 + 设定 + 当前卷纲 + 历史事实 | 章节数组 |
| 4 | 正文层 | 章节执行包 + 单元闭包 + 记忆/前章概要 | 章节正文 |

### 5.2 步骤确认与字数分配

`PipelinePanel.vue:4028` 的 `confirmStep()` 是步骤闸门。

在大纲层：

1. 用户填写全书字数。
2. `bookWordCount.value` 换算为字符写入 `projectStore.bookWordCountChars`。
3. 若大纲未锁，确认时会先触发锁定。
4. 保存配置后进入下一层。

这意味着“大纲字数分配”不是松散 UI 值，而是会进入项目态并被卷纲字数完整性校验消费。

### 5.3 每层独立配置

`pipeline.ts` 为每一层维护：

- Skill ID 列表：`setStepSkills()`。
- Agent：`setStepAgents()`。
- 执行模式：`setStepModes()`，支持 chain / compose。
- 层配置写入：`mutateStepConfig()`，底层是 `wa_pipeline_step_config` 的事务化更新。

源码证据：`src/stores/pipeline.ts:341`、`:399`、`:416`、`:430`。

### 5.4 断点与可恢复

流水线支持按 ownerKey 保存断点：

- `saveBreakpoint()`
- `refreshBreakpoint()`
- `refreshBreakpointFromStorageKey()`
- `clearBreakpoint()`

章节层还有独立的生成台账，用于判断区间是否断档、重叠、覆盖完整。

源码证据：`src/stores/pipeline.ts:276` 至 `:323`。

### 5.5 供应商通道

每一层可以绑定独立供应商通道。UI 侧会通过 `buildProviderChannelConfigSnapshot(layer)` 构建当前层快照。因此同一本书可以给设定层、卷纲层、章节层、正文层分别指定模型或供应商。

### 5.6 RunTrace

每层执行都会建立 RunTrace，关键事件包括：

- prompt-built
- attempt
- context-scope
- memory-context
- chain-step
- chain-context-slim
- chain-handoff-delivery
- body-generator-step
- contract-review
- deai
- write
- failed

`runTraceDiff.ts` 还可以对比两次 Run 的 API 调用、提示快照、物理调用和工具调用差异。这个机制对调大纲→正文衰减非常有价值。

## 6. SKILL 与 Agent 执行层

### 6.1 路由

`src/services/skillRouter.ts` 将技能分为三类：

1. text：模板注入型。
2. folder：真实文件夹 SKILL，交由 `executeRealSkill()` 执行。
3. composite：组合技能。

### 6.2 `runStepSkills()`

`PipelinePanel.vue:4362` 的 `runStepSkills()` 是 1-4 层的公共执行入口。每层传入 prompt、fallback template、executionPlan、traceRunId、pipelineRunId，然后按层配置执行技能链。

每层技能可单独配置：

- Agent
- injectMode
- inputSchema
- outputFormat
- validationRules

### 6.3 Folder SKILL 执行器

`src/services/realSkillExecutor.ts` 是核心执行器。

主要行为：

1. 读取文件夹 SKILL 的 `template.md`。
2. 注入调用方提供的模板变量。
3. 执行 preProcess。
4. 构建最终 prompt。
5. 调用 AI。
6. 做 schema/post-process 校验。
7. 失败时按重试上限重跑。
8. 重试耗尽时保留最佳候选，但把状态降级为未通过，交由上层产物契约门裁决。

重要守卫：

- folder 模板中未解析的占位符会阻断请求，不会静默把 `{{var}}` 发给模型。
- 变量为空会给出诊断。
- folder 模板优先，但流水线变量仍然注入。
- 末步可按 polish 角色做最终修复。

源码证据：`src/services/realSkillExecutor.ts:741` 起，模板守卫约在 `:598` 至 `:665`，候选保留逻辑约在 `:1590` 至 `:1665`。

## 7. 设定层

### 7.1 输入与协议

设定层从 `pipelineOutlineText` 提取设定卡。核心文件：

### 7.2 语义分类

`settingsLayerSemantics.ts` 将设定分为 8 类：

| 分类 | 语义 |
|---|---|
| character | 人物 |
| scene | 场景 |
| world | 世界 |

| item | 物品 |
| event | 事件 |
| style | 风格 |

### 7.3 验收

设定层验收包含：

- 名称非空。
- 名称不能是纯符号。
- 内容非空。
- 同分类内名称去重。
- 跨分类同名报错。

### 7.4 分层投影

设定会按下游层做预算投影，源码中的参考字符预算：

| 下游层 | 预算 |
|---|---|
| volume | 1200 字符 |
| chapter | 1500 字符 |
| body | 1800 字符 |

这个设计的意义是：设定不是一次性全文塞给所有层，而是按下游层任务裁剪。

## 8. 卷纲层

### 8.1 协议字段

卷纲层标准 JSON 数组字段为：

```json
{
  "name": "卷名",
  "outline": "卷纲内容",
  "summary": "卷摘要",
  "allocatedWords": 0,
  "readerExpectations": "读者期待",
  "mainPlotLine": "主推线",
  "unlockMilestone": "本卷解锁里程碑",
  "forbiddenFinalCards": [],
  "contractRisk": "contract_safe"
}
```

源码证据：`src/services/volumeBatchOrchestrator.ts:55` 起。

### 8.2 双模式

卷纲层有两种执行形态：

1. batch：直接让模型输出完整 JSON 数组。
2. single-volume：逐卷生成，适合长篇或 folder SKILL 链。

`PipelinePanel.vue:5738` 的 `genVolumes(mode)` 支持：

- `auto/all`
- `single/next`
- `continue/next`

### 8.3 字数完整性

`volumePlanIntegrity.ts` 校验：

- 所有卷 `allocatedWords` 之和必须等于全书总字数。
- 已分配字数超过总字数会报冲突。
- `clampVolumeWordsToPlan()` 会把超额卷字数钳制回计划。

### 8.4 契约语义

`volumeGenerationContract.ts` 强制每卷提供：

- 读者期待。
- 主推线。
- 解锁里程碑。
- 禁碰终局底牌数组。
- 契约风险状态。

允许 `[待补充]`，但不能缺字段。写入项目时还会提取 `VolumeContractSemantics`，供后续章节与正文层消费。

### 8.5 历史锚点

逐卷生成时会构建历史事实：

```text
已生成 N 卷
上一卷锚点
已有卷名
已有摘要与字数
```

验收器会检查：

- 卷名与历史重复。
- 批内卷名重复。
- 契约字段缺失。
- 字数非负整数。
- 台账区间是否合法。

## 9. 章节层

### 9.1 协议与验收

章节层标准协议字段为 `title` 和 `plot`：

```json
{
  "title": "章节标题",
  "plot": "章节剧情/细纲"
}
```

核心文件：

- `chapterBatchOrchestrator.ts`
- `chapterGenerationContract.ts`
- `chapterGenerationLedger.ts`

验收点：

- 生成数量与目标数量一致。
- 标题非空且批内去重。
- 剧情点非空。
- 相似剧情概要重复告警。
- 台账区间不断档、不重叠、覆盖目标章数。

### 9.2 章数仲裁

`resolveChapterCountContract()` 从三个来源仲裁：

1. 卷纲声明。
2. 用户/流水线配置。
3. 字数推算。

因此如果外部大纲或卷纲已经声明了章数，章数会优先被卷纲事实驱动。

### 9.3 批次与断点续跑

`PipelinePanel.vue:5977` 的 `genChapters(mode)` 按批生成。

默认批次：

- `chapterBatchSize = 5`
- 最大 20

每批提交时会做 `mergeChapterCommit()` 合并，避免并发覆盖。生成成功的章节会带 `pipelineGenerated=true` 标记。

### 9.4 历史事实

章节层会构建：

```text
已生成章标题清单
上一章事实
当前卷范围
```

这能减少章节漂移和重复开题。

## 10. 正文层

### 10.1 执行包

正文层不是直接把整本大纲塞给模型，而是先构建 `ChapterExecutionPackage`。

`src/services/chapterExecutionPackage.ts` 定义了执行包结构，核心字段包括：

| 字段 | 作用 |
|---|---|
| `contextScope.closure` | 当前章节可用的卷纲闭包 |
| `volume` | 所属卷信息 |
| `chapter` | 当前章信息 |
| `settings` | 裁剪后的设定 |
| `style` | 风格约束 |
| `memory` | 已抽取记忆 |
| `prevChapterSummary` | 上一章概要 |
| `sourceRefs` | 来源引用 |

`buildChapterExecutionPrompt()` 明确要求闭包必须存在。闭包为空会报错，不会回退为全书大纲。

源码证据：`src/services/chapterExecutionPackage.ts:140` 起。

### 10.2 单元闭包解析

`src/services/outlineContextScope.ts` 是正文层最关键的上下文控制机制。

可识别的 Markdown 结构：

```markdown
## 标题
> 作用域：卷级常任

## 剧情单元 U001：xxx
> 作用域：单元级 U001｜章节范围：第 1-10 章

## 某段草稿
> 作用域：批次底稿 U001
```

闭包构成：

1. `卷级常任` 段。
2. 当前单元段。
3. 未声明作用域的段落，按保守策略纳入。

预算：

- 目标约 12KB。
- 上限约 24KB。
- 超预算时按段裁剪，不截断半段。

守卫：

- 没有 `##` 段会报 `closure_empty`。
- 作用域声明无效会报 `scope_invalid`。
- 找不到单元 ID 不静默降级。
- 旧大纲完全没有作用域声明时会显式降级为 legacy outline，只保留卷概要和当前章细纲。

源码证据：`src/services/outlineContextScope.ts:55`、`:95` 至 `:170`、`:242` 起。

### 10.3 正文契约

`bodyArtifactContract.ts` 与 `bodyArtifactOrchestrator.ts` 控制正文产物。

核心契约：

- `targetWords`
- `minWords`
- `maxWords`
- 字数比率
- CJK + ASCII 字数统计

`resolveProseWordContract()` 使用目标 ±20% 的容差模型。

### 10.4 修复策略

`generateBodyArtifact()` 使用多层修复：

1. 先判断失败是否可以 targeted repair。
2. targeted 修复只重跑 generator 步。
3. targeted 失败或没有旧正文时，切 full chain。
4. full chain 仍失败则给明确报错。

`planBodyArtifactExecution()` 会根据失败类型选择 `none / targeted / full_chain / post_process`。

源码证据：`src/services/bodyArtifactOrchestrator.ts:47`、`:203`、`:296` 至 `:500`。

### 10.5 SKILL 链与角色裁决

正文层可挂 folder SKILL 链。链内输出使用 `【正文交接】` 区块交接。

链路控制包括：

- `slimChainUpstreamPrompt()`：非主消费者用结构图替代全文，减少污染。
- `dedupeChainIntermediateOutput()`：中间产物去重。
- `detectChainOutputEcho()`：回声检测，超过阈值告警，达到极高标准触发终步修复。
- NOT_READY 门禁：材料不足时不重试、不改写，而是显式等待材料。

### 10.6 生成后处理

正文生成成功后，`PipelinePanel.vue:6258` 的 `genBody()` 还会执行：

1. `runProseHardSignalNet()`。
2. 降 AI 诊断。
3. 契约复核。
4. 写入 `ch.body`。
5. 写入 `ch.generationMetadata`。
6. 编辑器自动插入正文。

## 11. 终稿与长文档机制

应用还有一条独立的终稿/长文档执行线，主要用于超大文档任务：

- `finalDraftRunner.ts`
- `finalDraftService.ts`
- `finalDraftCheckpoint.ts`
- `longDocumentExecutionPlanner.ts`
- `longDocumentWriteProtocol.ts`
- `longDocumentWriteCoverage.ts`

核心能力：

1. 把长任务切分为段落。
2. 支持检查点持久化。
3. 支持任务恢复和段落重试。

## 12. 运行时诊断与调试面

调试时优先看三个东西：

1. RunTrace：看每层 prompt、attempt、契约和失败事件。
2. `wa_pipeline_step_config`：确认每层 Skill/Agent/模式/供应商是否指向预期配置。
3. 断点与章节台账：确认区间是否连续、是否重复、是否覆盖完整。

如果层间结果异常，不要先改 prompt。应按顺序检查：

```text
大纲是否锁定
pipelineOutlineText 是否为冻结版本
bookWordCountChars 是否写入
当前层 Skill/Agent/通道是否正确
产物 JSON 是否通过层契约
RunTrace 中 prompt 是否已经衰减或截断
```

## 13. V124 大纲交接包映射

### 13.1 应用侧消费面

应用最直接消费的不是 V124 的自定义 JSON，而是以下字段：

| 应用字段 | 来源建议 | 说明 |
|---|---|---|
| `outlineText` | V124 完整 Markdown 大纲 | 这是导入主体，必须自包含 |
| `outlineLockedText` | 锁定后自动生成 | 所有下游只消费冻结文本 |
| `bookWordCountChars` | 全书字数配置 | 卷纲字数计划必须等于该值 |
| `settings` | 大纲中的设定、势力、世界观、规则、风格 | 设定层自动提取或人工补录 |
| `volumes[].allocatedWords` | V124 卷级字数预算 | 总和必须等于全书字数 |
| `volumes[].readerExpectations` | V124 卷级读者期待 | 契约字段 |
| `volumes[].mainPlotLine` | V124 卷级主推线 | 契约字段 |
| `volumes[].unlockMilestone` | V124 卷级解锁里程碑 | 契约字段 |
| `volumes[].forbiddenFinalCards` | V124 禁碰终局底牌 | 正文闭包会继续消费 |
| `chapters[].title` | V124 章级标题 | 章节层标准字段 |
| `chapters[].plot` | V124 章级剧情/细纲 | 章节层标准字段 |
| `ch.body` | 正文层产物 | 生成后写入 |

### 13.2 最重要的 Markdown 兼容点

V124 大纲若要最大化适配正文层，必须保留或转换出应用可解析的作用域结构：

```markdown
## 卷级常任：主线、禁碰、核心人物、核心规则
> 作用域：卷级常任

## 剧情单元 U001：开局危机与第一次升级
> 作用域：单元级 U001｜章节范围：第 1-10 章

### 第 1 章
剧情、冲突、节拍、增量、章尾钩
```

关键规则：

1. `##` 标题必须存在。
2. `> 作用域：` 声明必须符合 `outlineContextScope.ts` 的解析语法。
3. 单元级建议使用 `单元级 U001` 或 `批次底稿 U001`。
4. 卷级常任段写 `卷级常任`。
5. 如果一个单元 ID 都解析不到，正文层不会静默回退全书大纲，而是显式报错。

### 13.3 对 V124 的适配建议

1. 导入前把 V124 大纲组织成应用可解析的 `##` + `> 作用域：` 结构。
2. 保证卷级字数总和与流水线填写的全书字数完全一致。
3. 卷纲字段若由外部 JSON 导入，必须补齐 `readerExpectations / mainPlotLine / unlockMilestone / forbiddenFinalCards / contractRisk`。
4. 章节字段优先使用 `title` 和 `plot`，不要只给自由散文。
5. 单元 ID 在大纲、卷纲、章节三处保持一致。
6. 避免在大纲中放外部候选原文、原作摘录或原语种片段，否则正文层闭包会把这些内容视为合法事实源。
7. 导入后先用 RunTrace 检查 `context-scope` 事件，确认闭包大小、单元 ID 和纳入段落正确，再跑正文。

## 14. 与自有 V124 链式机制的对照

| 自有机制 | 应用对应物 | 对齐情况 |
|---|---|---|
| 大纲唯一事实源 | `outlineLockedText` + `pipelineOutlineText` | 高度一致 |
| 卷纲从大纲提取 | 设定层 + 卷纲层 + `buildVolumePrompt()` | 一致，但应用要求显式卷契约字段 |
| 章节从卷纲分配 | 章节层 + 章数仲裁 + 台账 | 一致，且应用比普通 prompt 链多了批次恢复 |
| 正文从章节生成 | `ChapterExecutionPackage` + 单元闭包 | 一致，且应用强制闭包存在 |
| 跨模型交接 | 每层供应商通道 + Skill/Agent 配置 | 应用侧已经支持 |
| 修复循环 | 层内 JSON 契约修复 + 正文 targeted/full-chain 修复 | 应用侧已经支持 |
| 追踪对比 | RunTrace + RunTraceDiff | 应用侧能力完整 |

结论：V124 的“全书结构总纲 + 事件总纲双融合”可以进入该应用，但要发挥正文层最大能力，必须在 Markdown 大纲中显式提供卷级常任、单元作用域、章节范围和单元 ID。

## 15. 当前理解下的主要风险

1. **47MB 级大纲导入风险**：应用支持大文本，但超大文档会考验编辑器、保存、树同步和 RunTrace。导入前应准备可分卷使用的导出版。
2. **作用域不匹配风险**：V124 的自有单元命名如果不匹配应用解析语法，正文层会降级或报错。
3. **卷契约字段缺失风险**：外部大纲如果只给自然语言卷纲，不会自动填满 `readerExpectations / mainPlotLine / unlockMilestone / forbiddenFinalCards / contractRisk`，可能反复触发修复。
4. **字数守卫风险**：卷纲分配字数总和必须严格等于全书字数，否则完整性校验会阻断或钳制。
5. **旧架构文档风险**：部分 docs 中标注为旧版架构，不能作为当前实现权威；应以源码和本轮解析结论为准。
6. **未做真实 UI 实测**：本文静态确认的是源码链路，未验证真实点击、真实导入、真实生成和真实供应商调用。

## 16. 推荐验证步骤

为了把本文从“静态理解说明”升级为“运行时闭环证明”，建议按以下顺序实测：

1. 打开应用，新建测试项目。
2. 导入一份裁剪后的 V124 大纲。
3. 检查大纲工作台编辑态、锁定态、树同步。
