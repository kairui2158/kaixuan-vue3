# 神意助手执行面板模式判定

> 结论：**可以用神意助手做执行面板，但这属于“大纲原生链路验证”，不是 V124 章包外部验证。**

## 1. 两种目标不能混用

### A. 大纲原生链路验证

目标：把 V107 大纲作为唯一事实源导入神意助手，锁定后由应用自己的设定层、卷纲层、章节层、正文层逐级解析，验证大纲是否足以指导下游生成。

这符合我们最初目标：

1. 大纲越完善，下游信息越足。
2. 卷纲从大纲提取，不自行发明。
3. 章节从卷纲分配，不越级改写。
4. 正文从章节和闭包生成，不回退成自由写作。

这个模式下，神意助手是执行面板和链式验证器。

### B. V124 章包外部验证

目标：外部 LLM 只读取 `LLM章包/*.json`，按章卡直接生成正文。

这个模式下，应用当前不是原生验证器，除非另做章包桥接导入器。前一份 `V124外部验证符合性判定.md` 的结论针对 B 模式，不否定 A 模式。

## 2. A 模式的正确使用方式

1. 导入 V107 大纲到大纲工作台。
2. 审校后锁定，使其成为 `outlineLockedText`。
3. 在流水线大纲层确认全书字数。
4. 让应用执行设定层。
5. 让应用根据大纲生成或校验卷纲。
6. 让应用根据卷纲分配章节。
7. 选择章节生成正文。
8. 用 RunTrace 检查每层 prompt、上下文、契约和写入结果。

这是应用原生的“大纲→卷纲→章节→正文”链路。

## 3. 需要注意的事实

V107 大纲当前是“段层 + 章卡”结构，112 段，5591 章。神意助手的原生语义是“卷 → 章”。如果直接导入，应用不会自动保证 112 个段一定映射为 112 个卷。因此 A 模式要获得最高准确性，最好先把 V107 转成应用可解析的卷级结构，并补上：

```markdown
## 卷级常任：xxx
> 作用域：卷级常任

## 剧情单元 V107-S001：xxx
> 作用域：单元级 V107-S001｜章节范围：第 3-52 章
```

同时每章仍保留：

```markdown
### 第 3 章
- 主目标
- 对抗
- 代价
- 状态变化
- 章尾钩
```

这不是把大纲改成另一套事实，而是把 V107 的段层语义翻译成应用能稳定消费的卷/章格式。

## 4. 判定

| 问题 | 判定 |
|---|---|
| 神意助手能否作为大纲执行面板？ | 可以 |
| 是否符合“大纲驱动卷纲、章节、正文”的原始目标？ | 符合 |
| 当前应用是否原生验证 V124 章包？ | 不符合 |
| 是否应直接导入 V107 跑 A 模式？ | 可以做小规模实测，但全书直接导入前应先做卷级/作用域适配 |
| V124 是否因此作废？ | 不作废；它仍然是零源外部验证基准 |

## 5. 推荐推进

1. 生成一份 `V107 大纲应用适配版`，保留唯一事实源语义，但按神意助手卷/章/作用域语法重组。
2. 先用一个小段，例如 `V107-S001`，在应用里跑完设定 → 卷纲 → 章节 → 正文。
3. 检查正文是否符合章级事实，而不是先看文笔。
4. 小段跑通后，再做全书 112 段导入策略。
